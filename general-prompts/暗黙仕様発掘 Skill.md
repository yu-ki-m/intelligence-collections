# implicit-spec-discovery

## 目的

コードベースから、画面・API・業務用語だけを見ても理解しにくい内部仕様を発見し、新規参入者がシステムの実際の振る舞いを理解できる形で説明する。

この Skill は一般的なコード解説を目的としない。

特に次のような仕様を発見する。

- 楽観ロック・悲観ロック・ロックなし
- 現在値と履歴値の使い分け
- Snapshot / History / Event / Master のどれを正本として利用しているか
- 更新・削除・参照時の特殊条件
- トランザクション境界
- 非同期処理と結果反映タイミング
- キャッシュによる表示差異
- 論理削除
- 冪等性
- リトライ時の振る舞い
- 状態遷移制約
- 権限によるデータ可視性
- デフォルト値
- null / 空文字 / 未指定の違い
- 派生値・計算値
- データ取得元の違い
- 更新対象と表示対象の違い
- API と UI の意味上の違い
- 時刻の基準
- ソート・最新判定の基準
- Eventually Consistent な処理
- Feature Flag や設定値による振る舞いの変化

最重要目的は、

> 新規参入者が「普通はこうだろう」と無意識に仮定してしまう部分を発見し、その仮定と実装との差を説明すること

である。

---

# 基本原則

## 1. コード構造ではなく振る舞いを説明する

次のような説明だけで終了してはいけない。

- TicketController が存在する
- TicketService が TicketRepository を呼ぶ
- TicketHistoryRepository が存在する

代わりに、

> チケット詳細画面は Ticket テーブルの値をそのまま表示しない。  
> TicketHistory から対象チケットの最新履歴を取得し、その値を画面表示用データとして使用する。

のように説明する。

---

## 2. 「普通ならどう思うか」を必ず生成する

実装を調査するときは、実装を見る前または実装とは独立して、新規参入者が持ちそうな自然な認識を生成する。

例:

### UI

「チケット詳細」と表示されている。

自然な認識:

> 現在の Ticket レコードが表示される。

### 実装

TicketHistory の最新レコードを取得している。

### 発見される暗黙仕様

> 詳細画面が表示する値の正本は Ticket 本体ではなく、TicketHistory の最新履歴である。

この「自然な認識」と「実装」の差を重要な仕様候補として扱う。

---

# 調査アルゴリズム

## Phase 1: 対象機能を利用者視点で分解する

対象機能について、最初にコード構造ではなく利用者の操作単位を列挙する。

例:

チケット機能なら、

- 一覧を見る
- 詳細を見る
- 新規作成する
- 編集する
- ステータスを変更する
- 削除する
- 履歴を見る
- コメントする
- 再読み込みする
- 同時に複数人で操作する

など。

Controller / Service / Repository の一覧から始めてはいけない。

---

# Phase 2: 暗黙仕様仮説を生成する

各操作について、最低でも以下の観点から仮説を生成する。

## データ取得元

確認する。

- どのテーブル・API・キャッシュを参照するか
- Current と History のどちらを利用するか
- Snapshot を利用するか
- 複数のデータソースを合成するか
- 表示用に再計算する値があるか

問い:

> 「画面に見えている値は、どこから来ているのか？」

---

## 更新

確認する。

- 全項目更新か差分更新か
- null と未指定を区別するか
- version を確認するか
- updatedAt を比較するか
- 他ユーザーによる更新を検出するか
- 更新可能な状態が限定されているか

問い:

> 「画面を開いたあと別ユーザーが更新していたら何が起こるか？」

---

## 同時実行

確認する。

- Optimistic Lock
- Pessimistic Lock
- DB Lock
- Application Lock
- Compare-and-Swap
- ロックなし

特に version、revision、etag、updatedAt、lockForUpdate、FOR UPDATE などを調べる。

ロックが存在しないと結論する場合、一つの更新経路だけを見て判断してはいけない。

---

## 履歴

確認する。

- 履歴が監査用か
- 履歴が現在状態の正本か
- 履歴から状態を復元するか
- 更新前を保存するか更新後を保存するか
- 履歴登録と本体更新が同一トランザクションか
- 最新履歴の決定方法

問い:

> 「History テーブルがなくなった場合、通常機能は動作するか？」

動作しないなら、History は単なる監査ログではない可能性が高い。

---

## 削除

確認する。

- DELETE 文を実行するか
- deleted フラグを変更するか
- status を変更するだけか
- 子データも削除するか
- 削除済みデータを検索対象から除外する場所はどこか

問い:

> 「削除したデータは本当に消えるのか？」

---

## トランザクション

確認する。

- どこからどこまでが同一トランザクションか
- 本体更新と履歴登録が一体か
- 外部 API 呼び出しがトランザクション内か
- 途中失敗した場合に何が残るか

問い:

> 「処理の半分だけ成功する状態は存在するか？」

---

## 非同期処理

確認する。

- Queue
- Event
- Scheduler
- Worker
- Message Broker
- Transactional Outbox
- Async annotation
- background job

問い:

> 「API が成功した瞬間に、すべての画面から更新結果が見えるか？」

---

## 冪等性・リトライ

確認する。

- 同一リクエストを2回送るとどうなるか
- Idempotency Key があるか
- Unique Constraint が二重登録を防止するか
- Retry が副作用を重複させないか

問い:

> 「タイムアウト後に同じ操作を再実行しても安全か？」

---

## 状態遷移

確認する。

- 任意の状態へ直接変更できるか
- 状態遷移表がコード内に存在するか
- 特定状態では編集禁止になるか
- 状態変更によって別処理が発火するか

問い:

> 「ステータス値を変更することと、ステータス変更操作は同じ意味か？」

---

## 権限と可視性

確認する。

- Controller だけで権限確認するか
- Query 自体がユーザー単位で絞られるか
- Tenant 条件が自動挿入されるか
- 管理者だけ別データソースを見るか

問い:

> 「存在するレコードが、利用者によって存在しないように見えることはあるか？」

---

## 時刻

確認する。

- createdAt
- updatedAt
- effectiveAt
- occurredAt
- DB 時刻
- Application 時刻
- UTC / Local Time

問い:

> 「このシステムにおける『現在』『最新』『当日』は何を基準に決まるか？」

---

## 最新判定

`ORDER BY created_at DESC LIMIT 1`

だけを見て「最新履歴」と説明してはいけない。

確認する。

- createdAt が同値になり得るか
- ID を第二ソート条件にしているか
- revision を使うか
- transaction sequence を使うか

---

## キャッシュ

確認する。

- Redis
- Local Cache
- HTTP Cache
- ORM Cache
- frontend cache
- React Query / SWR 等

問い:

> 「DB が更新されたあとでも古い値が表示される可能性があるか？」

---

## デフォルト・暗黙変換

確認する。

- DB DEFAULT
- ORM の初期値
- API のデフォルト
- Frontend のデフォルト
- null → empty 変換
- enum fallback
- timezone conversion

問い:

> 「利用者が指定していない値を、誰が決めているか？」

---

# Phase 3: Counterfactual Probe

通常系だけを読むのではなく、意図的に条件を変えた質問をコードへぶつける。

最低限、関連するものを確認する。

- 2人が同時に更新したら？
- 更新直前に別の人が削除したら？
- 履歴と本体の内容が違ったら？
- 同じリクエストが2回来たら？
- トランザクション途中で例外が発生したら？
- キャッシュだけ古かったら？
- API 成功直後に検索したら？
- null を指定したら？
- 項目自体を送信しなかったら？
- 同じ timestamp の履歴が2件あったら？
- 権限が途中で変更されたら？
- Feature Flag が無効なら？
- 外部 API がタイムアウトしたら？

これらをすべて仕様として出力する必要はない。

実装上、通常の直感と異なる結果になるものだけを暗黙仕様候補として残す。

---

# Phase 4: 実際の呼び出し経路を追跡する

仕様候補について、可能な限り以下を追跡する。

UI

↓

Frontend state / API client

↓

Controller / Endpoint

↓

Application Service / UseCase

↓

Domain Logic

↓

Repository

↓

ORM / SQL

↓

Database / External System

クラス名だけから判断してはいけない。

実際に呼び出されている経路を確認する。

---

# Phase 5: 証拠を集める

以下を証拠として利用する。

優先度の高い順:

1. 実際の実行経路
2. SQL / Query
3. Domain Logic
4. Repository
5. Integration Test
6. Unit Test
7. API Schema
8. DB Schema / Migration
9. ORM Annotation
10. コメント
11. 名前

コメントやクラス名だけを根拠に仕様を断定してはいけない。

---

# Phase 6: 反証する

暗黙仕様候補を発見したら、その結論を否定するコードが存在しないか確認する。

例:

「Ticket 更新は楽観ロックである」

を発見した場合、

- 別更新 API
- Batch
- Admin API
- Import
- Scheduler
- Migration
- Repository の別メソッド

が version check を回避していないか確認する。

一つでも例外経路が存在する場合、

> 通常の画面更新では楽観ロックを使用する。ただし XXX 経由では version check を行わない。

と記載する。

---

# Phase 7: 独立検証

可能なら、最初の調査とは別コンテキストのエージェントに主要な発見を検証させる。

検証担当には結論をそのまま信じさせず、

> 以下の主張をコードから独立に検証し、反証可能なコードパスを探せ。

と指示する。

特に次を独立検証対象とする。

- データ正本
- ロック方式
- トランザクション境界
- 履歴の意味
- 状態遷移
- 非同期処理
- 削除方式
- 権限制御

Subagent を利用できない環境では、一度結論から離れ、反証探索フェーズを別途実行する。

---

# 重要度判定

発見したものをすべて説明してはいけない。

次の観点で優先する。

## Surprise

新規参入者の自然な予想とどれだけ異なるか。

## Impact

知らないことで、

- 障害
- データ不整合
- バグ
- 誤改修
- 誤調査

につながる可能性があるか。

## Breadth

複数機能へ影響するか。

## Confidence

コード上の証拠が十分か。

Surprise と Impact が高いものを最優先する。

---

# 出力形式

コードファイルの説明順ではなく、利用者が理解しやすい機能単位で説明する。

## 概要

対象機能が内部でどのような特徴を持つかを3〜10件程度に要約する。

---

## 暗黙仕様

### [仕様名]

#### 新規参入者が持ちやすい認識

通常はどう動くと思うか。

#### 実際の仕様

コード上、実際に何が起こるか。

#### 具体例

実際の操作例を一つ示す。

#### なぜ注意が必要か

この仕様を知らないと何を誤解するか。

#### 根拠

- `FooController#update`
- `FooService#update`
- `FooRepository#update`
- `xxx.sql`
- `Vxxx__add_version.sql`

のようにコード上の証拠を示す。

可能なら行番号も示す。

#### 確信度

- High
- Medium
- Low

Low の内容を確定仕様として扱ってはいけない。

---

# 出力例

## チケット更新は楽観ロック

### 新規参入者が持ちやすい認識

編集画面で保存すると、その時点の入力内容によってチケットが上書きされる。

### 実際の仕様

更新 API は、画面取得時の `version` と DB 上の現在の `version` を比較する。

別ユーザーが先に更新して DB の version が変化している場合、後から保存した更新を拒否する。

つまり、最後に保存した人が無条件で勝つ Last Write Wins ではない。

### 具体例

1. A と B が version=5 のチケットを開く。
2. A が保存する。
3. DB の version が6になる。
4. B が version=5 の状態で保存する。
5. B の更新は競合として拒否される。

### なぜ注意が必要か

画面上では通常の更新処理に見えるため、version の存在を知らずに API やバッチ処理を追加すると、既存画面とは異なる競合制御になる可能性がある。

### 根拠

- `TicketController#update`
- `TicketService#update`
- `TicketRepository#update`
- `Ticket.version`

### 確信度

High

---

## 詳細画面は Ticket 本体ではなく最新履歴を表示する

### 新規参入者が持ちやすい認識

チケット詳細画面なので `Ticket` テーブルの現在値を表示している。

### 実際の仕様

詳細取得処理は `TicketHistory` を更新日時順に検索し、最新履歴の内容を画面表示値として利用する。

したがって、Ticket 本体の値と最新履歴の値が異なる場合、画面には最新履歴側の値が表示される。

### なぜ注意が必要か

Ticket テーブルだけを調査すると「DB には正しい値があるのに画面表示がおかしい」という誤った調査結果になる可能性がある。

### 根拠

- `TicketDetailService#get`
- `TicketHistoryRepository#findLatest`
- `TicketDetailMapper#fromHistory`

### 確信度

High

---

# 禁止事項

以下を行ってはいけない。

## 単なるコード要約

「Controller → Service → Repository」という説明だけで終了しない。

## 名前からの推測

`HistoryService` という名前だけを見て履歴仕様を判断しない。

## 単一経路から全体仕様を断定

画面 API だけを見て Batch や Admin API も同じ仕様だと判断しない。

## 理由の創作

コードから確認できるのは主として「どう動くか」である。

「なぜこの設計にしたか」は、ADR、Issue、Commit、設計書等の証拠がなければ断定しない。

## 証拠なしの仕様化

可能性を発見しただけの場合、

「〜である」

ではなく、

「〜である可能性がある。以下の確認が必要」

と明示する。

---

# 最終チェック

調査終了前に必ず以下を確認する。

- [ ] 正常系だけでなく同時実行を確認した
- [ ] Current / History / Snapshot の関係を確認した
- [ ] 表示元と更新先が同じか確認した
- [ ] 削除方式を確認した
- [ ] トランザクション境界を確認した
- [ ] 非同期処理を確認した
- [ ] Retry / Idempotency を確認した
- [ ] null / 未指定 / 空値の違いを確認した
- [ ] 状態遷移制約を確認した
- [ ] 権限制御を確認した
- [ ] 時刻・最新判定を確認した
- [ ] キャッシュを確認した
- [ ] 通常経路を回避する別経路を確認した
- [ ] 新規参入者が誤解しそうな点を明示した
- [ ] 主要な結論について反証探索を行った

---

# 完了条件

コードを大量に説明したことを完了条件にしてはいけない。

次を満たしたときに完了とする。

1. 対象機能について利用者視点の操作を整理した。
2. 各操作に対して暗黙仕様仮説を生成した。
3. Counterfactual Probe を実施した。
4. 実際のコードパスによって主要仕様を検証した。
5. 新規参入者の自然な認識との差を特定した。
6. 重要な仕様について反証探索を実施した。
7. 高価値な暗黙仕様を、新規参入者が理解できる形で説明した。

最終成果物は「コード解説書」ではなく、

> このシステムでは、見た目から想像すると間違えやすいこと

をまとめた内部仕様ガイドとする。
