 
# 汎用ワークフロー図・高密度技術図スタイル再現プロンプト

参考画像の内容そのものは使用せず、 **図の表現方法・構成方法・視覚文法だけを参考にして** 、指定されたワークフローを1枚の高密度な技術図として表現してください。

この図は、一般的な単純フローチャートではありません。

以下を1枚に統合した、設計図・技術アーキテクチャ図に近い表現にしてください。

* 全体ワークフロー
* 処理の階層構造
* サブプロセス
* モジュール境界
* 分岐・合流
* 並列処理
* 反復
* 条件判定
* 詳細展開図
* 入出力
* 状態
* 成果物
* 補助的な技術注記

# 2. 図全体の基本構造

図は、中央に主要な処理の流れを配置し、その周囲に補助情報や詳細構造を展開してください。

基本的な読み順は、

`上 → 下`

としてください。

中央または中央よりやや左に、ワークフロー全体の骨格となる主幹フローを配置してください。

読者が中央部分だけを見ても、

* どこから開始するか
* 何を順番に処理するか
* どこで分岐するか
* どこで処理が合流するか
* 最終的に何が生成されるか

を理解できる構成にしてください。

---

# 3. 主幹フロー

主要処理を縦方向に並べてください。

基本形は以下です。

```text
Input
  ↓
Process
  ↓
Process
  ↓
Decision
  ↓
Process
  ↓
Output
```

ただし、対象ワークフローに応じて以下を使用してください。

* 直列処理
* 条件分岐
* 並列処理
* 合流
* 再試行
* フィードバック
* ループ
* 中断
* エラー処理
* 人手確認
* 外部システム連携
* 非同期処理

単純な一直線だけではなく、実際の処理構造が分かるようにしてください。

---

# 4. 階層構造

大きな処理の内部に複数の処理が存在する場合、すべてを同じ粒度で主幹に並べないでください。

処理を次のように階層化してください。

```text
Workflow
 ├─ Phase
 │   ├─ Process
 │   ├─ Process
 │   └─ Process
 │
 ├─ Phase
 │   ├─ Process
 │   └─ Process
 │
 └─ Phase
```

上位レベルでは概要を示し、必要な箇所だけ詳細展開してください。

---

# 5. 論理グループ

関連する処理群を、薄い色の破線矩形で囲ってください。

例えば以下です。

* Phase
* Stage
* Subsystem
* Team
* Responsibility
* Processing Layer
* Validation Layer
* External System
* Human Operation

グループ枠には短いタイトルを付けてください。

グループ内部は比較的高密度に配置して構いません。

ただし、グループ同士の間には明確な余白を確保してください。

---

# 6. 詳細展開図

主幹フローの中でも、内部処理が複雑なモジュールについては、左右に詳細展開図を配置してください。

例えば主幹に、

```text
[Processing]
```

という箱がある場合、その横に、

```text
Processing Detail

Input
  ↓
Normalize
  ↓
Validate
  ↓
Transform
  ↓
Result
```

のような内部構造を描いてください。

詳細展開図と元の処理は、細い破線で接続してください。

この破線は処理フローを意味しません。

「この処理の内部構造がここに展開されている」

という参照関係を意味します。

---

# 7. 線の意味を分離する

線には明確な役割を持たせてください。

## 実線矢印

実際の処理、データ、成果物の流れを表現します。

```text
A
↓
B
↓
C
```

## 破線

以下を表現します。

* 詳細展開
* 参照関係
* 補助関係
* 論理的関連
* 説明対象との対応

## フィードバック線

再処理や修正を意味します。

```text
Process
   ↓
Validate
   │
   └──── Failed ────→ Process
```

実行フローと説明用の線を混同しないでください。

---

# 8. 分岐

条件によって処理が変わる場合は、小型の分岐ノードを使用してください。

例えば、

```text
          Condition
             ●
          ／     ＼
       Yes       No
        ↓         ↓
     Process A  Process B
```

分岐線には可能であれば、

* Yes / No
* Success / Failure
* Valid / Invalid
* Approved / Rejected

など、条件を短く記載してください。

---

# 9. 合流

複数の処理が同じ後続処理へ進む場合は、一度合流させてください。

```text
Process A ─┐
           ├─●─→ Next Process
Process B ─┘
```

複数の線を直接次工程へ大量に接続しないでください。

---

# 10. 並列処理

同時に実行される処理は、横方向へ展開してください。

```text
               Start
                 │
          ┌──────┼──────┐
          ↓      ↓      ↓
          A      B      C
          │      │      │
          └──────┼──────┘
                 ↓
               Merge
```

直列処理と並列処理を視覚的に区別してください。

---

# 11. 反復処理

同じ種類の処理が複数回繰り返される場合、すべてを冗長に描画しないでください。

例えば、

```text
┌───────────┐
│ Process   │
├───────────┤
│ Process   │
├───────────┤
│ Process   │
└───────────┘
      ×N
```

または、

```text
[Process] × N
```

としてください。

反復回数が重要な場合だけ具体的な数値を記載してください。

---

# 12. ノード形状

処理の種類によってノード形状を使い分けてください。

## 処理

角丸長方形。

```text
┌────────────┐
│  Process   │
└────────────┘
```

## 分岐・合流

小さな円または小型ノード。

```text
●
```

## 入力・出力・成果物

通常処理より少し大きい長方形。

```text
┌────────────────┐
│    Artifact    │
└────────────────┘
```

## グループ

薄い破線矩形。

```text
┌ - - - - - - - - - ┐
   Group
└ - - - - - - - - - ┘
```

## 外部システム

必要に応じて独立した境界を持つ箱として描いてください。

---

# 13. ノードのサイズ

すべての箱を同じサイズにしないでください。

処理の重要度や粒度に応じて、

* 主処理
* 補助処理
* 小処理
* 分岐点
* 成果物

でサイズを変えてください。

ただし、大きな説明文を箱の中へ入れるためだけに箱を巨大化させないでください。

---

# 14. テキスト配置

箱の中には、処理名だけを簡潔に記載してください。

悪い例:

```text
┌──────────────────────────────────┐
│ 入力データを検証して不正な値が   │
│ 含まれていないか確認する処理      │
└──────────────────────────────────┘
```

良い例:

```text
┌──────────────┐
│   Validate   │
└──────────────┘

input: raw_data
output: validated_data
```

説明は可能な限りノードの外側に小さく記載してください。

---

# 15. 技術注記

必要に応じてノード周辺へ、小さい文字で技術注記を付けてください。

例えば、

```text
input: request
output: result[]

state: pending

condition: score >= threshold

retry: max 3

owner: operator

source: system A

destination: system B
```

ただし、図の主要な読みやすさを損なうほど注記を増やさないでください。

---

# 16. 色の使い方

色は装飾ではなく、意味を区別するために使用してください。

対象ワークフローに適した分類を自動的に決めてください。

例えば、

* グレー = 共通処理・基盤
* 青 = 中核処理
* 水色 = 情報・データ処理
* 緑 = 外部連携・ツール・リソース
* 橙 = 判定・検証・承認
* 紫 = 制御・オーケストレーション
* 赤 = エラー・例外・停止条件

ただし、対象によってより適切な分類がある場合は変更してください。

重要なのは、

「同じ意味の要素には必ず同じ色を使う」

ことです。

---

# 17. グループと色の対応

グループの見出し、枠線、内部の主要ノードは同系色にしてください。

例えば、

```text
青いタイトル
↓
青系の破線枠
↓
青系のノード
```

とすることで、離れた場所に存在する要素でも所属関係を理解できるようにしてください。

---

# 18. 配線

線は可能な限り、

* 垂直
* 水平
* 直角折れ線

で構成してください。

不必要な斜線を大量に使用しないでください。

斜線は、

* 詳細展開への参照
* 遠い要素との補助接続

などに限定してください。

---

# 19. 線の交差を避ける

関連するノードを近くへ配置してください。

長い矢印で画面全体を横断しないでください。

線が交差する場合は、

* ノード位置を変更する
* 合流ノードを追加する
* グループ単位で整理する
* 補助経路を別領域へ移動する

などによって整理してください。

---

# 20. 情報密度

図全体は比較的高密度にしてください。

ただし、

「情報量が多い」

と

「整理されていない」

は別です。

各モジュール内部は高密度でも構いませんが、モジュール間には十分な余白を確保してください。

次のリズムを意識してください。

```text
高密度領域
    ↓
余白
    ↓
高密度領域
    ↓
余白
    ↓
高密度領域
```

---

# 21. 視覚的階層

文字サイズには明確な階層を付けてください。

大きい順に、

1. 図全体のタイトル
2. サブシステム / フェーズ名
3. 処理名
4. 入出力・条件・補足情報

としてください。

すべての文字を同じ大きさにしないでください。

---

# 22. 読み方の階層

この図は、読者が3段階で理解できるように設計してください。

## Level 1

図全体を眺めて、

「何のワークフローなのか」

を理解できる。

## Level 2

中央の主幹フローを追って、

「どのような順序で処理されるのか」

を理解できる。

## Level 3

左右の詳細展開や注記を読んで、

「各処理内部で具体的に何が起きるのか」

を理解できる。

---

# 23. 視覚的トーン

以下の方向性を維持してください。

* 技術設計図
* システムアーキテクチャ図
* 研究資料
* エンジニアリングドキュメント
* 精密
* 高密度
* 構造的
* ミニマル
* 専門的

以下の方向にはしないでください。

* 子供向け
* ポップ
* キャラクター中心
* 広告
* プレゼンテーション向けの巨大な文字
* アイコン主体のインフォグラフィック

---

# 24. 禁止事項

以下を避けてください。

* 参考画像の内容そのものをコピーする
* 参考画像固有の名称を使用する
* 参考画像固有の数値を流用する
* すべての処理を同じ箱で表現する
* 箱と矢印だけの単純図にする
* 不必要に巨大な矢印を使用する
* 色をランダムに割り当てる
* 処理フローと参照線を同じ線種にする
* 詳細説明をすべて箱の中へ詰め込む
* 大量の線を交差させる
* すべてを同じ粒度で表現する
* 不要な3D表現
* 過剰な影
* グラデーション主体の装飾
* 写実的なイラスト
* 人物イラスト中心の構成

---

# 25. 最終的な完成イメージ

最終成果物は、

「通常のフローチャートよりも情報量が多く、システムアーキテクチャ図よりも処理順序が明確で、詳細設計図よりも全体像を理解しやすい」

図にしてください。

1枚の図の中に、

```text
全体像
+
処理順序
+
モジュール境界
+
サブプロセス
+
詳細展開
+
データフロー
+
分岐
+
並列処理
+
反復
+
入出力
+
補足情報
```

を統合してください。

最重要事項は、

**中央の主幹を見るだけで全体を理解でき、必要になったときだけ周辺の詳細へ視線を移せること**

です。
