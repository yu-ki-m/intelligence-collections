「ユーザーが与えた目的を、検証可能な完了状態まで確実に持っていく」ための汎用Agent Skillを設計・実装してください。

私は、単なるTODO実行スキルや「最後まで頑張る」という精神論を求めていません。

このスキルの目的は、

「要求を理解する」
→「完了条件を定義する」
→「計画する」
→「実行する」
→「成果物を検証する」
→「不足を発見する」
→「修正する」
→「独立した観点から再検証する」
→「完了条件を満たしたことを証明する」

という閉ループを、AIエージェントに強制することです。

# 最重要原則

AI自身の「終わりました」という自己申告を、完了の根拠として認めないでください。

完了とは、

「事前に定義された完了条件について、客観的な証拠を使って、すべて満たしていることを確認できた状態」

と定義してください。

成果物を作ったことと、目的を達成したことを区別してください。

例えば、

- コードを書いた
- ファイルを作った
- テストを書いた
- コマンドを実行した
- 文書を作成した

だけでは完了としてはいけません。

それらがユーザーの目的を本当に満たしていることまで検証してください。

# このスキルが解決すべき問題

AIエージェントには、以下の失敗が頻繁に発生します。

- 途中まで実行して完了したと判断する
- 要求の一部を忘れる
- 実装しただけで動作確認しない
- テストを書いただけで実行しない
- テストが通っただけで要求を満たしたと思う
- 正常系だけ確認する
- 失敗系・境界値を確認しない
- 自分が書いたコードを自分で評価して問題なしと判断する
- 「おそらく動く」「たぶん問題ない」で終了する
- エラーを回避しただけなのに原因を解決したと思う
- TODOや未実装を残したまま終了する
- サブタスクを完了したことで全体目的も完了したと誤認する
- コンテキスト圧縮などによって当初要求を忘れる
- 修正によって別の場所を壊す
- ユーザーが指定した方法を実行しただけで、本来の目的達成を確認しない
- 途中でツール/APIが失敗すると、そのまま作業を縮退させる
- 「できなかったこと」を明示せず成功扱いする
- 証拠を提示せず完了宣言する

これらを構造的に防止してください。

# 必須設計

## 1. Goal Contract

開始時にユーザー要求を以下へ変換してください。

- Goal
- Deliverables
- Acceptance Criteria
- Constraints
- Non-Goals
- Required Evidence
- Unknowns
- Risks

ユーザーが明示していない完了条件も、目的達成に不可欠なら推定候補として提示してください。

ただし、推定した要求を勝手に確定しないでください。

重大な解釈差が発生する場合だけ確認してください。

## 2. Completion Ledger

要求を追跡可能な台帳として管理してください。

各要求について最低限、

- ID
- Requirement
- Status
- Evidence
- Verification Method
- Remaining Work

を保持してください。

Statusは最低でも、

- PENDING
- IN_PROGRESS
- BLOCKED
- IMPLEMENTED_NOT_VERIFIED
- VERIFIED
- FAILED
- NOT_APPLICABLE

を区別してください。

IMPLEMENTED_NOT_VERIFIED を VERIFIED と同一視してはいけません。

## 3. Plan

要求とタスクの対応関係を明示してください。

各タスクが、どのAcceptance Criteriaを満たすためのものか追跡可能にしてください。

要求に紐づかない作業を大量に増やさないでください。

逆に、タスクに変換されていない要求が残っていないか確認してください。

## 4. Execution Loop

以下をループしてください。

PLAN
→ EXECUTE
→ OBSERVE
→ VERIFY
→ GAP ANALYSIS
→ REPLAN
→ EXECUTE

「一度実装して終わり」にしないでください。

検証で不足を発見した場合、その不足を新しいタスクとしてCompletion Ledgerへ戻してください。

## 5. Independent Verification

成果物を作ったコンテキストと、検証するコンテキストを可能な限り分離してください。

サブエージェントが利用できる場合、

実装担当
と
検証担当

を分けてください。

検証担当には、実装担当の自己評価を渡さず、

- 元の要求
- 完了条件
- 成果物
- 実行結果

を中心に渡してください。

検証担当は「問題を発見すること」を役割としてください。

単なる追認者にしないでください。

## 6. Adversarial Verification

正常に動くことだけではなく、

「どのように失敗し得るか」

を検証してください。

最低でも必要に応じて、

- 正常系
- 異常系
- 境界値
- 空入力
- 大量入力
- タイムアウト
- 部分失敗
- 再実行
- 重複実行
- 中断→再開
- 外部依存失敗
- 権限不足
- 不正入力
- 既存機能への回帰
- 並行実行
- 状態不整合

などを検討してください。

すべてを機械的に実行するのではなく、対象に relevant なものを選択してください。

## 7. Counterfactual Verification

「成功した」という仮説だけを検証しないでください。

最低限、

「もしこの成果物が要求を満たしていないとしたら、どこに問題がある可能性が高いか」

という逆方向の検証を行ってください。

さらに、

- 別の入力では壊れないか
- 別の環境では壊れないか
- 偶然テストが通っただけではないか
- モックによって問題を隠していないか
- テスト対象そのものが間違っていないか
- 検証方法に盲点がないか

を確認してください。

## 8. Evidence-First Completion

完了宣言には証拠を要求してください。

例えばソフトウェアなら、

- 実行したコマンド
- テスト結果
- lint/build結果
- 実際の出力
- 差分
- 該当ファイル
- 期待値と実測値

などです。

文書なら、

- 要求項目との対応
- 欠落チェック
- 矛盾チェック
- 必須章の存在
- 引用元確認

などを証拠として扱ってください。

「確認しました」という文章だけをEvidenceとして認めないでください。

## 9. Regression Guard

修正によって元々動いていたものを壊していないことを確認してください。

局所テストだけではなく、必要に応じて関連範囲の回帰確認をしてください。

## 10. Stop Condition

以下をすべて満たすまで正常終了しないでください。

- Acceptance Criteria がすべて VERIFIED または明示的な NOT_APPLICABLE
- PENDING が0
- IMPLEMENTED_NOT_VERIFIED が0
- 未解決の重大な FAILED が0
- BLOCKED が存在する場合、その理由と影響をユーザーへ明示
- 独立検証が完了
- 重大なRegressionがない
- Required Evidenceが揃っている

「時間がかかった」
「かなり作業した」
「主要部分はできた」

などを終了条件にしないでください。

# 完遂性

途中で失敗した場合でも、即座に作業全体を終了しないでください。

回復可能な失敗なら、

原因分類
→ 再試行
→ 別手段
→ スコープ再評価
→ 再検証

を行ってください。

ただし無限ループは禁止します。

再試行回数だけではなく、

「同じ失敗を同じ方法で繰り返していないか」

を判断してください。

同一原因で再試行しても成功可能性が上がらない場合、別アプローチへ変更してください。

# ユーザー指示との関係

ユーザーが指定した手段と、ユーザーの目的を区別してください。

ユーザーの手段が明らかに目的達成に不利であり、

- 効果
- コスト
- 安全性
- 実行可能性
- 保守性

のいずれかで重大な問題がある場合、

実行前に代替案とトレードオフを提示してください。

ただし、「本当はこうしたいはず」と勝手に目的を書き換えないでください。

# 不確実性

確認できていないことを、確認済みとして扱わないでください。

以下を区別してください。

- FACT
- INFERENCE
- ASSUMPTION
- UNKNOWN

UNKNOWNが重要な完了条件に影響する場合、完了宣言を禁止してください。

# コンテキスト喪失対策

長時間タスクでも要求を失わないよう、

Goal Contract
Completion Ledger
重要な設計判断
未解決事項
次のアクション

を永続的な作業状態として管理する仕組みを設計してください。

コンテキスト圧縮・サブエージェント委譲・セッション長期化後にも復元できる形式にしてください。

# サブエージェント

利用可能な場合は積極的に利用してください。

特に以下は分離してください。

- 実装
- 調査
- テスト
- 要求照合
- 反証
- 回帰確認
- 最終監査

ただし、サブエージェントを増やすこと自体を目的にしないでください。

サブエージェントの結果も無条件で信用せず、統合時に検証してください。

# 最終監査

終了直前に、実装担当とは別の視点で最終監査を実施してください。

最終監査では、

「この仕事を失敗扱いにするとしたら、その理由は何か？」

から開始してください。

その後、

1. 元の要求を再読する
2. Acceptance Criteriaを1件ずつ確認する
3. 成果物との対応を見る
4. Evidenceを確認する
5. 未検証箇所を探す
6. 回帰を探す
7. 暗黙の未完了を探す
8. TODO/FIXME/仮実装/モック/ハードコードを確認する
9. ユーザー要求からの逸脱を確認する
10. 完了宣言が証拠によって成立するか判定する

という工程を必須化してください。

# 出力時の完了報告

完了時には単に

「完了しました」

と書かないでください。

最低でも、

- 何を達成したか
- 何を検証したか
- Acceptance Criteriaの達成状況
- 主要なEvidence
- 残存リスク
- 未完了事項の有無

を簡潔に報告してください。

未完了がある場合は「完了」と表現しないでください。

# スキル自体の品質要求

このSkill自体についても、

「このSkillが本当にエージェントの途中終了・自己評価バイアス・検証不足を防げるか」

を検証してください。

単なる長いSKILL.mdを作るだけで終わらせないでください。

以下も作成してください。

- SKILL.md
- 必要なreferences
- 必要ならscripts
- 状態管理テンプレート
- Completion Ledgerテンプレート
- Verification Checklist
- Final Audit Checklist
- 使用例
- 失敗例
- テストシナリオ

さらに最低20種類程度の異なるタスクを想定して、Skillの設計を机上検証してください。

例:

- 小規模コード修正
- 大規模リファクタリング
- バグ修正
- 複数コミット調査
- API統合
- インフラ変更
- 文書作成
- 調査レポート
- データ分析
- UI変更
- 移行作業
- テスト追加
- 性能改善
- セキュリティ修正
- 障害原因調査
- 長時間タスク
- 外部API失敗を含むタスク
- 複数エージェントタスク
- ユーザー要求が曖昧なタスク
- 一部しか検証できないタスク

これらを使って設計上の欠陥を洗い出し、Skillを改善してください。

# 最後の要求

既存の一般的な「plan → execute → test」程度のSkillにはしないでください。

私は、

「AIが目的を達成したつもりになる問題」

そのものを解決する、汎用的な実行・検証基盤を作りたいです。

十分に考え抜いたうえで設計してください。

必要なら設計を何度でも壊して作り直してください。

最終成果物についても、このSkill自身が定義する完了条件を使って自己適用し、検証してください。
