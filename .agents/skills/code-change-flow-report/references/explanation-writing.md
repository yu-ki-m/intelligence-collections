# 説明文規則

## 全説明へそのまま適用するプロンプト

次のプロンプトを省略、要約、言い換えせず、コミット全体の概要、処理フロー説明、概説、変更理由、処理仕様、備考へそのまま適用する。未変更ステップの変更理由に設定する固定値`変更なし`だけは対象外とする。

```text
私は、前提や論理展開を省略した説明を理解しにくい。

以下のルールで説明すること。

- 最初に「つまり何なのか」を1〜2文で説明する。
- 専門用語を使う場合、その用語がこの文脈で何を意味するのか説明する。
- 抽象語だけで説明しない。
- 「AによってBが可能になる」と書く場合、Aの何がBを可能にするのか説明する。
- 主語を省略しない。「誰・何が、何を、どうする」の形を基本とする。
- 前提知識を暗黙に要求しない。説明に必要な前提を先に示す。
- 抽象的な説明の直後に具体例を1つ示す。
- 複数の概念を一度に説明せず、1つずつ説明する。
- 「柔軟」「高度」「効率的」「最適化」など、具体的な意味が不明な形容を避ける。
- 結論に至るまでの因果関係を飛ばさない。
- 用語の羅列で説明しない。
- 私が「分からない」と言った場合、同じ説明を言い換えるだけではなく、説明の粒度を1段階下げる。
```

## 各欄の役割

### コミット全体の概要

各コミットに1件記載し、個別の比較表を読む前に変更全体の意味を理解できる文章にする。最初の1〜2文で「つまり何が変わり、誰または何へどの結果が生じるのか」を説明する。次に、理解に必要な用語と前提を、それらを使用する説明より前へ置く。複数の変更箇所がある場合は、各変更がどの順序で作用し、直前の変更が次の結果を生む理由を説明する。

冒頭の1〜2文は概要全体の上限ではない。前提、用語、原因、変更内容、結果の説明に必要な文章を省略せず、コミット概要だけを短い差分要約として扱わない。文字数を満たすための文章は追加しない。

抽象的な説明を使った場合は、その直後に具体的な条件、入力値、保存値、レスポンスなどを1つ示す。具体例を導入する語句は固定せず、`例えば`という文字列を必須にしない。説明自体が具体的であれば、別の具体例を機械的に追加しない。

コミット全体の概要では、ファイル名、クラス名、メソッド名、変更件数の列挙だけを記載しない。各変更箇所の詳細は比較表へ分け、概要には変更全体を読むために必要な結論、前提、因果関係、観測できる結果を記載する。

### 第1階層の処理フロー説明

複数テーブルまたは入れ子で構成する処理フローには、タイトルと1〜2文の説明を記載する。タイトルは処理の開始と結果を識別できる名称にする。説明は、何が処理を開始し、どの主要処理を経て、誰または何へどの結果を返すかを実行順に示す。コミット全体の変更意図や各テーブルの詳細を繰り返さない。

単独テーブルにはタイトルだけを記載する。単独テーブルに、存在しない呼び出し経路や後続処理の説明を加えない。

### 概説

最初の1〜2文で「つまり何が変わったのか」を説明する。未変更ステップでは変更の有無を繰り返さず、そのコードが処理フローで何を担当するかだけを説明する。未変更であることは変更理由欄の`変更なし`で示す。

### 変更理由

変更前に起きていた事実、変更した処理、変更後に得られる結果を因果順に記載する。未変更ステップでは、他の文章を加えず`変更なし`とだけ記載する。表へ含めた理由の説明が必要な場合は備考へ記載する。

### 処理仕様

コードの実行順を日本語へ置き換えるだけで終わらせない。処理仕様を`summary`と`steps`に分け、抽象的な説明を使う場合は`example`も記載する。

- `summary`: その処理が業務データ、利用者、後続処理にとって何を意味するかを1〜2文で説明する。メソッド名や呼び出し順から書き始めない。
- `steps`: 実コードの実行順に2件以上の手順を記載する。1項目では、1つの入力、判定、状態変化、呼び出し、戻り値または外部結果だけを扱う。HTMLが`1.`、`2.`の番号を付けるため、手順本文には番号を書かない。
- `example`: 任意。`summary`または`steps`で抽象的な説明を使う場合に、具体的な入力値と、レスポンス、保存内容、ログなど外部から確認できる結果を1つ示す。導入語句は固定しない。説明自体が具体的であれば、項目を省略する。

各手順では「誰または何が、どの値を受け取り、何を行い、直後に何が生じるか」を説明する。呼び出しがある場合は、呼び出し先へ渡す値と、呼び出し元へ戻る値または例外を説明する。条件分岐がある場合は、条件と選択される結果を別の手順にする。該当しない入力や判定を、手順数を増やす目的で作らない。

## 処理仕様を意味中心で書く

処理仕様は、コードを隠して読んでも処理の目的と結果を理解できる文章にする。クラス名、メソッド名、変数名は、意味を説明した後でコードとの対応を示すために使う。

次の順序で記載する。

1. `summary`で、この処理が何を成立させるか、または何を保証するかを説明する。
2. `steps`で、入力、前提、判定、状態変化、呼び出し、戻り値を実行順に分ける。
3. `steps`の各項目で、使用する値と、その値が直後の結果を生む理由を説明する。
4. 抽象的な説明を使った場合は、`example`で具体的な入力例と、保存内容、レスポンス、ログなど外部から確認できる結果を示す。`例えば`から書き始める必要はない。

次の書き方だけで処理仕様を終えない。

- メソッドAを呼び、次にメソッドBを呼ぶという実行順の列挙。
- クラス名、メソッド名、変数名を日本語の助詞でつないだ説明。
- コードと同じ情報しか持たない逐語的な言い換え。
- 「設定する」「処理する」「連携する」だけで、その結果を示さない説明。

### 悪い例

`OrderServiceはmapper.toEntity(request)でOrderを生成し、order.initializeStatus()で状態をRECEIVEDに設定してから、repository.save(order)を呼び出す。`

この文は呼び出し順を説明しているだけで、RECEIVEDを保存する意味や、後続処理が何を判断できるようになるかを説明していない。

### 良い例

```json
{
  "summary": "この処理は、新しく受け付けた注文を「受付済み」として保存し、後続処理が未受付のデータと区別できる状態にする。",
  "steps": [
    "OrderServiceがAPI入力を保存用のOrderへ変換する。Orderは、注文IDや商品情報など業務処理が使用する値を保持する。",
    "OrderServiceがOrderの状態へRECEIVEDを設定する。RECEIVEDは、システムが注文を受け付けた直後を表す。",
    "OrderServiceが状態設定済みのOrderをOrderRepositoryへ渡す。OrderRepositoryは、注文IDとRECEIVEDを同じ注文レコードへ保存する。"
  ],
  "example": "注文IDが1001の注文を登録直後に照会するとstatusはRECEIVEDとなり、後続の出荷処理はその注文を処理対象として判定できる。"
}
```

### 備考

理解に必要な用語、前提、影響範囲、対象外、運用上の注意を記載する。変更箇所と周辺処理の調査で懸念点、バグ、考慮漏れを確認した場合は、`[懸念点]`、`[バグ]`、`[考慮漏れ]`のいずれかを先頭に付けて記載する。

指摘には、根拠となるコードまたは条件、問題が発生する条件、利用者・データ・後続処理への影響、必要な確認または対応を記載する。追加確認が必要な内容は`[懸念点]`とし、確認できていない内容を`[バグ]`と断定しない。該当する指摘がない場合は、指摘を作らない。別の欄と同じ内容を繰り返さない。

記載例: `[考慮漏れ] request.itemsが空の場合を拒否する判定がないため、空の注文が保存される。APIが空の商品一覧を受け付けない仕様であれば、入力検証と境界値テストを追加する必要がある。`

## 文章の規則

この資料の先頭に記載したプロンプトが文章の規則である。言い換えた短縮版を代用せず、各説明を作成するときと生成後に同じ原文へ照合する。

- 「最初の1〜2文」は、説明全体の文数制限ではなく、結論を先に示す位置の指定として扱う。
- 抽象的な説明へ具体例を続ける場合も、`例えば`など特定の導入語句を要求しない。
- 説明に必要な前提がない場合は架空の前提を作らない。必要な前提がある場合は、その前提を使う文章より先に記載する。

## 未変更ステップの記載例

- 概説: `OrderControllerはHTTPリクエストを受け取り、注文データをOrderServiceへ渡す入口である。`
- 変更理由: `変更なし`
- 処理仕様の`summary`: `この処理は、API利用者が送った注文を業務処理へ渡し、登録結果が確定してから応答する入口である。`
- 処理仕様の`steps`: `OrderControllerがHTTPリクエストからOrderRequestを受け取る。`、`OrderControllerがOrderRequestをOrderServiceへ渡し、結果または例外が戻るまで待つ。`、`OrderControllerが戻り値を後続のHTTPレスポンス作成へ渡す。`
- 処理仕様の`example`: `保存処理が失敗した場合、OrderControllerは成功レスポンスを返さず、既存の例外処理へ制御を渡す。`
- 備考: `Controllerとは、この処理ではHTTPリクエストをJavaメソッドへ受け渡すクラスを指す。`

## 「分からない」と指摘された場合

同じ説明の単語だけを置き換えない。対象処理を入力、前提条件、判定、中間値、呼び出し先、戻り値に分割する。各項目を別の文または別のテーブルとして示し、具体的な変数名と値の例を追加する。
