# 処理フローの追跡

## 1. 比較単位を確定する

各タブは1コミットを表す。通常のコミットは、そのコミットと第1親を比較する。マージコミットに複数の親があり、選ぶ親によって説明が変わる場合は、比較する親をユーザーへ確認する。

複数コミットを指定された場合は、範囲全体を1つの差分にまとめない。各コミットをそれぞれの親と比較し、コミットの意図と処理フローを分離する。

## 2. 変更箇所を特定する

`git show`または`git diff`で変更ファイルと変更行を確認する。ファイル名やメソッド名だけから処理内容を推測しない。親コミットと対象コミットの両方から実際のコードを取得する。

変更された値について、次の情報を1つずつ確認する。

- 何が値を受け取るか。
- 何が値を検証または変換するか。
- 何が条件分岐を選ぶか。
- 何がデータベースや外部APIへ値を渡すか。
- 何が結果を戻り値へ変換するか。

## 3. 入口を特定する

このスキルでいう入口とは、対象処理を最初に開始するコードを指す。WebアプリケーションではControllerやHTTP Handlerが入口になる。メッセージ処理ではListenerやConsumer、定期処理ではJob、コマンドライン処理ではCommandが入口になる。

変更メソッドから呼び出し元を逆方向にたどる。シンボル検索、LSPの参照検索、`rg`による呼び出し検索を使用し、実際の呼び出し箇所を確認する。変更メソッドが複数の入口から利用される場合は、変更の影響を受ける入口ごとに1段目のフローを作る。

呼び出し元の調査では、最低2種類の探索方法を使う。1つ目はLSPのCall Hierarchyや参照検索など、コードのシンボルを識別する意味解析である。2つ目は`rg`による文字列検索、ルーティング設定、DI設定、イベント購読設定など、1つ目とは異なる情報源を使う。各探索方法、探索範囲、検索対象、検出した呼び出し箇所IDを`callerCoverage.targets[].evidence`へ記録する。

探索で見つけた呼び出し箇所は、次のいずれかに分類する。

- `included`: 変更の影響を受けるため、入口から変更箇所までのフローを表へ掲載する。
- `excluded`: 変更の影響を受けないことをコードで確認できるため、具体的な除外理由を記録する。
- `unresolved`: インターフェースの実装先、リフレクション、フレームワークによる動的呼び出しなどが原因で、入口または呼び出し先を確定できない。

`unresolved`が1件でも残る場合、HTML生成を完了しない。推測によって`excluded`へ変更しない。必要なビルド設定、DI設定、イベント定義などを追加調査し、呼び出し関係を確定する。

同じ変更対象に複数の`included`がある場合は、呼び出し箇所ごとに変更ステップを複製し、それぞれ異なる`id`を付ける。各呼び出し箇所は、自分の入口ステップ、呼び出し元ステップ、変更ステップへ関連付ける。これにより、検証処理は複数の呼び出し元が1つの変更表へ不正に集約されていないか判定できる。

## 4. 未変更コードを選ぶ

未変更コードは、処理の連続性を説明するために含める。次のいずれかに該当する未変更ステップを表へ入れる。

- 入口が入力を受け取り、変更箇所を含む処理を呼び出す。
- 入力値を変更箇所が使用する形式へ変換する。
- 条件分岐が変更箇所を実行するかどうかを決める。
- 変更箇所の結果を後続処理へ渡す。
- 保存結果や外部APIの結果をレスポンスへ変換する。
- Controllerなどの入口が最終結果を利用者へ返す。

未変更という理由だけで全コードを表へ入れない。変更箇所への到達または変更結果の理解に関係しないログ、補助メソッド、別分岐は除外する。

未変更ステップでは、親コミットと対象コミットから取得した同一コードを`beforeCode`と`afterCode`の両方へ設定する。概説と処理仕様は、そのステップが担う処理を示す。変更理由は`変更なし`とだけ記載する。表へ含めた理由の説明が必要な場合は備考へ記載する。

## 5. 実行順を表へ変換する

各テーブルは、連続して実行される1つのコード断片を表す。1つのメソッドが別メソッドを呼び出してから処理を続ける場合は、呼び出しまでの断片と、呼び出しから戻った後の断片を別テーブルにする。

例えば、ControllerがServiceを呼び出した後でHTTPレスポンスを返す場合、Controllerの上段はService呼び出しまでを記載する。Service配下の処理を入れ子で記載した後、同じ1段目へ戻り、Controllerの`return`を別テーブルとして記載する。

呼び出し先は親ステップの`calls`へ入れる。呼び出し先から戻った後の処理は、親と同じ`steps`配列の次要素へ入れる。実行上つながらない1段目を続ける場合は、そのステップへ`connectFromPrevious: false`を設定する。

コミットの先頭と`connectFromPrevious: false`を設定した第1階層ステップは、新しい表示単位の開始になる。開始ステップには`flowTitle`を設定する。同じ表示単位が複数の第1階層ステップを線で接続する場合、または開始ステップから入れ子の呼び出しを表示する場合は、`flowDescription`へ「何が処理を開始し、どの処理を経て、何を結果として返すか」を1〜2文で記載する。呼び出しも接続先も持たない単独テーブルには`flowTitle`だけを設定する。

すべての`calls`について、呼び出し元メソッドの実コードを呼び出し行からメソッド終了まで確認する。通常の制御が呼び出し元へ戻り、その後にレスポンス生成、値の加工、別処理の呼び出しなどが実行される場合は、そのコードを親と同じ`steps`配列の次要素へ入れる。次要素は呼び出し元と同じ`filePath`を持ち、呼び出し箇所より後の行を示す。

呼び出し文が`return service.execute()`のように戻り値をそのまま返す場合、呼び出し文がメソッドの最終文である場合、`throw`などによって通常の制御が戻らない場合は、架空の後続テーブルを作らない。呼び出しが非同期境界を越え、呼び出し元へ戻った後の同期処理として扱えない場合も、独立フローとして表現する。

HTML生成後は、`generate-report.sh`が出力した各`[後続処理確認]`を1件ずつ検証する。入れ子を展開し、子テーブルの終了後に親階層の後続テーブルが表示されること、接続線が続くこと、ファイルパスと行番号が実コードに一致することを確認する。接続された後続テーブルがない項目は、メソッド末尾、直接`return`、例外終了、非同期境界のどれに該当するかを実コードで確認する。

## 6. 分岐と非同期処理を扱う

条件分岐ごとに変更の影響が異なる場合は、条件と選択される処理を別ステップとして示す。すべての分岐を並べる必要はなく、変更の影響を受ける分岐と比較に必要な分岐だけを含める。

イベント発行とConsumerの実行のように呼び出しが非同期の場合は、備考で同期呼び出しではないことを説明する。イベントが後続処理を開始する因果関係を確認できる場合は入れ子で示し、同じ実行フローとして断定できない場合は独立した1段目として示す。
