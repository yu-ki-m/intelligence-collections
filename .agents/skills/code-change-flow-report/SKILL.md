# コード変更フロー表

コミットごとに変更前後を比較し、変更行だけでは分からない実行経路を単体のHTMLファイルで示す。対象リポジトリは読み取り専用で調査し、ユーザーが明示的に依頼しない限りソースコード、Git履歴、リモートリポジトリを変更しない。

最終成果物は自己完結したHTMLファイルだけにする。JSONはHTMLを生成するための内部入力として扱い、ユーザーが明示的に求めない限り納品しない。Webサーバー、開発サーバー、HTTPサーバーを起動せず、ポートを待ち受けない。Node.jsはHTMLを生成して終了する単発処理にだけ使用する。

## 必ず読む資料

1. 調査前に [処理フローの追跡](references/flow-tracing.md) を読む。
2. JSONを書く前に [JSON仕様](references/review-data-schema.md) と [説明文規則](references/explanation-writing.md) を読む。
3. HTMLを生成する前に [HTMLテンプレート要件](references/report-template-requirements.md) を読む。
4. HTML生成後に [検証項目](references/verification.md) を読む。

## 実行手順

1. 対象リポジトリ、コミットまたはコミット範囲、出力先を確定する。対象が指定されていない場合は、結果が変わる推測をせずユーザーへ確認する。
2. 各コミットを親コミットと比較し、変更されたファイル、メソッド、条件分岐、データ項目を特定する。
3. 変更箇所の呼び出し元を実コードで逆方向にたどり、Controllerなどの入口を特定する。意味解析を使う参照検索と、文字列検索またはフレームワーク設定の確認を別々に実施し、両方の探索結果を`callerCoverage`へ記録する。次に入口から変更箇所、後続処理、戻り値までを実行順にたどる。各呼び出しについて、呼び出し元メソッドの呼び出し行からメソッド終了までを実コードで確認し、呼び出しから戻った後に実行される文の有無を判定する。
4. 変更箇所へ到達するため、または変更結果が利用者へ返るまでを理解するために必要な未変更コードも表へ含める。変更行だけを並べたレポートを完成扱いにしない。
5. コミットごとのJSONを作成する。すべてのステップへ重複しない`id`を設定し、探索で検出した各呼び出し箇所を`included`、`excluded`、`unresolved`のいずれかに分類する。`included`は入口、呼び出し元、専用の変更ステップへ関連付ける。`excluded`は除外理由を記録する。`unresolved`を残したまま生成しない。各コミットの`overview`には、個別の変更表を読む前に変更全体の意味を把握できる説明を書く。コミット先頭と`connectFromPrevious: false`を指定した第1階層ステップには`flowTitle`を設定する。接続された第1階層ステップまたは入れ子を含む場合は`flowDescription`も設定し、処理の開始から結果までを説明する。独立した1段目の処理には`connectFromPrevious: false`を設定し、呼び出し先は`calls`へ入れる。
6. 次のコマンドでJSONを検証し、HTMLを生成する。HTMLを直接組み立てず、過去に生成したHTMLや別テンプレートを流用しない。

```bash
bash <skill-root>/scripts/generate-report.sh <review-data.json> <review-report.html>
```

7. 検証処理が「未変更コードのステップがない」と通知した場合は、入口から終点までを再調査する。未変更ステップが本当に不要な場合だけ、その理由を最終回答へ記載する。
8. コマンド出力の`Root section self-test passed`、`Caller coverage passed`、`Continuation structure passed`、`HTML verification passed`を確認する。いずれか1つでも表示されないHTMLを完成扱いにしない。
9. コマンドが出力する各`[後続処理確認]`について、実コードと展開したHTMLを照合する。呼び出し後の文がある場合は、同じ親階層の次テーブルが呼び出し元と同じファイル・同じメソッドの後続行を示し、線で接続されていることを確認する。呼び出し後の文がない場合は、直接`return`、メソッド末尾、`throw`、非同期境界など、後続テーブルを置かない根拠を実コードで確認する。
10. 出力したHTMLファイルを直接開き、コミットタブ、差分色、接続線、独立フロー、入れ子の開閉、文章の折り返しを確認する。確認のためにサーバーを起動しない。最終回答には`後続処理検証: 呼び出しN件、後続ありM件、後続なしK件`を記載し、後続なしが1件以上ある場合は対象ステップIDと理由も記載する。

## 完了条件

- 各コミットが独立したタブになっている。
- 各コミットの先頭に`概要`があり、変更全体の意味、前提、因果関係、具体例を説明している。
- 第1階層の各開始テーブルの直前にタイトルがある。複数テーブルまたは入れ子を含む処理フローには説明があり、単独テーブルには説明がない。
- 各処理フローがControllerなどの実際の入口から始まっている。HTTP処理でない場合は、Listener、Consumer、Job、Commandなど実際の入口を使い、その理由を備考へ書く。
- `analysisMode`が`callers`の各変更対象について、種類の異なる2つ以上の探索方法で呼び出し元を確認している。直接呼び出されない設定値などは、その根拠を`not-applicable`へ記録している。
- 探索で検出した呼び出し箇所がすべて`callerCoverage`へ登録され、掲載対象は入口、呼び出し元、変更ステップへ関連付けられている。
- 同じ変更対象を呼び出す箇所が複数ある場合は、呼び出し箇所ごとに専用の変更ステップを配置している。
- 除外した呼び出し箇所には具体的な理由があり、未解決の呼び出し候補が残っていない。
- 変更へ到達する経路と変更結果が戻る経路に必要な未変更ステップが含まれている。
- 未変更ステップでは`beforeCode`と`afterCode`が同一である。
- 未変更ステップでは`reason`が`変更なし`の5文字だけである。
- 未変更ステップの`overview`では変更有無を繰り返さず、処理の役割だけを説明している。
- 同じメソッド内の呼び出し前と戻り後を別ステップに分け、上段へ実行後の`return`を書かない。
- 呼び出し後の処理がある場合、次の接続テーブルが呼び出し元と同じファイル・同じメソッドの後続行を示している。呼び出し後の処理がない場合、その根拠を実コードで確認している。
- すべての説明がユーザー指定の説明文規則を満たしている。
- 処理仕様がコードの逐語訳ではなく、処理の意味、因果関係、具体的な結果を説明している。
- 納品物が外部ファイルやサーバーを必要としない単体HTMLになっている。
- サーバープロセスが起動しておらず、ポートを待ち受けていない。
- JSON検証、呼び出し元網羅性検査、呼び出し後の構造検査、10,000段の深度検査、HTML生成、生成後HTML検査が成功している。
- 生成後HTMLが`2026.09.12.14`のテンプレート要件を満たしている。

ユーザーが説明を「分からない」と指摘した場合は、既存文の言い換えだけで済ませない。入力、判定、中間値、呼び出し、戻り値を分割し、説明の粒度を1段階下げてJSONとHTMLを再生成する。
