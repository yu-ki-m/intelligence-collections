# Stage D: GTMと成長（P18〜P25）

Stage D では、製品を顧客に届け、試してもらい、使い続けてもらい、さらに次の顧客を連れてきてもらう仕組みを設計する。話題になることと、使われ続けることは別の問題である。

---

## P18: GTM Motion

### 目的

製品を主にどのような方法で売るかを決める。売り方によって、必要な製品の作り（無料枠、セルフサービス、管理機能）も、組織（営業、開発者向けの担当者）も、指標も変わる。以降の Stage D のPhaseは、この選択を前提にする。

### 入力

P5のICP（利用者・意思決定者・予算保有者、導入のしやすさ）。

### 手順

**Step 1. 4つの Motion の条件を確認する**

| Motion | 向いている条件 | 主な指標 |
| --- | --- | --- |
| **Product-Led (PLG)** | 利用者が自分で試せる / 導入が軽い / 価格が低〜中 / 利用者と購入者が近い | Signup、Activation、有料転換率 |
| **Sales-Led** | 導入に組織的な判断が必要 / 契約単価が高い / セキュリティ・調達の審査がある / 業務の変更を伴う | パイプライン、商談化率、受注率、セールスサイクル |
| **Community-Led** | 開発者・専門家のコミュニティがある / OSS / 知識の共有で価値が増える | コミュニティの規模・活動量、貢献者数 |
| **Partner-Led** | 既存のプラットフォームやSIに乗ると顧客に届きやすい / 補完的なポジション（P8） | パートナー経由の導入数・売上 |

**Step 2. 年間契約額の見込みから判断する**

1顧客あたりの年間契約額（ACV）の見込みは、Motion の選択に強く影響する。以下は一般的な目安であり、製品や市場によって変わる。

| ACVの目安 | 向いている売り方 | 理由 |
| --- | --- | --- |
| 年数十万円以下 | セルフサービス（PLG） | 営業担当者の人件費を回収できない |
| 年数十万〜数百万円 | インサイドセールス＋PLG | オンラインの商談で完結できる |
| 年数百万円以上 | フィールドセールス | 複数の関係者との調整が必要で、その費用を回収できる |

**Step 3. 役割の関係から判断する**

* 利用者・意思決定者・予算保有者が **同じ人**: PLG が向いている
* 利用者と予算保有者が **別の人**: PLG で利用者を獲得し、組織導入は営業が進めるハイブリッドが向いている
* 利用者が導入前に製品に触れられない（本番データが必要など）: Sales-Led が向いている

**Step 4. 切り替えの条件を決める（ハイブリッドの場合）**

PLG で獲得した利用者の中から、営業が接触すべき組織を見つける条件（PQL: Product Qualified Lead）を決める。

```text
例: 同じドメインのアカウントが5つ以上ある
    かつ 直近1か月の判断回数の合計が10万回を超えた（無料枠の合計を上回る水準にする）
    → 営業が接触し、組織契約を提案する
```

**Step 5. Sales-Led の場合に追加で決めること**

* 意思決定プロセスと関与者（利用者、技術評価者、予算保有者、調達、セキュリティ）
* PoC（試験導入）の設計: 期間、成功基準、評価者
* 営業資料: ROI試算（P1の現状コストとの比較）、役割ごとのメッセージ（P10）、セキュリティ資料、導入事例
* 導入までの期間と、その間の資金への影響（P27）

### 深掘りの問い

* ICPの利用者が、上司の承認なしに今日から使い始められるか。
* 1顧客を獲得するのに、営業担当者は何時間使えるか（ACVから逆算する）。
* 最初の10社は、どの Motion で獲得するか。それは、最初の1,000社を獲得する Motion と同じか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「PLGで広げる」 | 「PLGとSales-Ledのハイブリッド。開発者はAPIキーを無料で発行し、クレジットカードの登録なしで月1万回まで判断できる。同じ組織で5アカウント以上、かつ月10万回を超えたら、営業が接触してボリューム契約とSLAを提案する。ACVの見込みは、個人で年数万円、組織で年数百万円（仮置き）」 |

### よくある失敗

* 「PLGが流行っているから」という理由で、ACVや購買プロセスに合わない Motion を選ぶ。
* ハイブリッドにしたのに、PLG から営業に切り替える条件を決めない。
* 最初の10社の獲得方法と、その後の拡大の方法を区別しない。

### 出力

```text
■ 選んだ Motion と、その理由
■ ACVの見込み
■ 切り替えの条件（ハイブリッドの場合）
■ Sales-Led の追加事項（該当する場合）
```

### 次への受け渡し

* Motion → P19〜P25の前提、P26の指標、P27のCAC

## P19: Pricing & Monetization

### 目的

何に対して、いくらを課金するかを決める。価格は、売上を決めるだけでなく、**製品の位置付けを顧客に伝えるシグナル** でもある。課金単位がP7の比較軸とずれていると、「価値」と「支払い」がつながらず、顧客は価格の妥当性を判断できない。

### 入力

P1の現状のコスト、P7の比較軸、P18の Motion。

### 手順

**Step 1. 課金単位（Value Metric）を選ぶ**

候補を出し、以下の4条件で評価する。

| 条件 | 問い |
| --- | --- |
| 価値との連動 | 顧客が得る価値が増えると、課金単位も増えるか |
| わかりやすさ | 顧客が、自分がいくら払うことになるかを予測できるか |
| 測定可能性 | 自社と顧客の両方が、同じ数値を確認できるか |
| 比較軸との一致 | P7の比較軸と同じ単位か |

| 課金単位の型 | 向いている製品 | 注意点 |
| --- | --- | --- |
| 席数（ユーザー数） | 人が毎日使う業務アプリ | 自動化が進むほど席数が減り、売上が減る |
| 利用量（API呼び出し、処理量） | 開発者向け、インフラ | 請求額が予測しにくく、予算を取りにくい |
| 成果（削減額、処理件数） | 成果が明確に測れる製品 | 成果の測り方で顧客ともめやすい |
| 定額 | 利用量のばらつきが小さい製品 | ヘビーユーザーで赤字になる |

**Step 2. 価格の上限と下限を出す**

* **上限**: 顧客が現在払っているコスト（P1の総コスト）。これを超えると、乗り換える理由がない。
* **下限**: 自社の提供コスト（インフラ、サポート）＋必要な粗利。
* **目安**: 顧客が得る価値（削減できるコスト、増える売上）の一部を価格にする。どの程度の割合にするかは、競合の価格と顧客の予算の枠で決める。

**Step 3. 無料枠・トライアルを設計する（PLGの場合）**

* 無料枠の中で、**最初の価値体験（P22）まで到達できる** 量にする。
* 機能ではなく、利用量で制限するほうが、PLGでは有料への移行が自然に起きやすい。
* クレジットカードの登録を求めるかどうかを決める（求めると登録が減り、求めないと有料への移行率が下がる）。

**Step 4. プランの構成を決める**

```text
個人（無料／低価格）→ チーム → 組織（Enterprise）
```

各プランの間で、何が変わると上位に移るのか（利用量、管理機能、SLA、セキュリティ機能など）を書く。

**Step 5. 価格が伝えるシグナルを確認する**

* 安すぎる価格は「価値が低い」というシグナルになる。
* Sales-Led の場合、安すぎると営業コストを回収できない（P27）。
* 新カテゴリーの場合、最初の価格がそのカテゴリーの相場になる。後から上げるのは難しい。

**Step 6. 価格を検証する方法を決める**

* 顧客インタビューでは「いくらなら払うか」ではなく、「今この問題にいくら払っているか」を聞く（P1）。
* 価格ページの複数パターンを試す、デザインパートナーに実際の見積もりを出す、などで実際の支払い行動を見る（P32）。

### 深掘りの問い

* 顧客の利用が10倍になったとき、請求額はどうなるか。顧客はそれを喜ぶか、困るか。
* 顧客の経理担当者は、この課金単位の請求書を見て、何の費用か理解できるか。
* 競合が価格を半分にしたら、自社はどう対応するか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「月額980円から」 | 「課金単位は判断回数（P7の比較軸『判断1回あたりのコスト』と一致）。100万回あたり○円。上限の根拠は、同じ判断を大型LLMで行った場合のコスト（約1/100の水準にする）。無料枠は月1万回で、デモと同じ使い方を試せる量。組織プランはSLAとログの保存期間で差を付ける（数値は仮置き）」 |

### よくある失敗

* 競合の価格を見て、根拠なく少し安くする。
* 課金単位が比較軸とずれていて、価値と支払いがつながらない。
* 無料枠が小さすぎて、最初の価値体験に届かない。または大きすぎて、有料に移る理由がない。

### 出力

```text
■ 課金単位と、4条件での評価
■ 価格の上限・下限・案
■ 無料枠・トライアル
■ プラン構成
■ 価格の検証方法
```

### 次への受け渡し

* 価格 → P27（Unit Economics）
* 無料枠 → P22

## P20: Launch Compression

### 目的

ローンチ時に、複数の材料を同じ時期に投入して、注目を最大化する。単発のニュースは1日で忘れられるが、複数の材料が重なると、メディア・SNS・コミュニティの複数の経路で同時に話題になり、「何か大きなことが起きている」という印象が生まれる。

### 入力

P10〜P17の結論（P17 の批判への回答は、T-1週の準備に使う）。

### 手順

**Step 1. 材料を洗い出す**

製品公開 / ベンチマーク / 顧客事例 / 資金調達 / 新カテゴリーの発表 / Founder Story / 技術記事 / デモ / OSS / API / 連携（Integration） / パートナー発表 / 顧客のコメント / 第三者のレビュー

| 材料 | 準備状況 | ローンチまでに用意できるか | 担当 | 届く相手 |
| --- | --- | --- | --- | --- |

「届く相手」を書くことで、材料ごとに違う層（開発者、投資家、メディア、顧客）に届くかを確認する。

**Step 2. ローンチの規模を決める**

材料が揃わない場合は、無理に大きなローンチにしない。

| 規模 | 条件 |
| --- | --- |
| 大規模 | 新カテゴリー＋数値の証拠＋第三者（パートナーや顧客）の参加が揃っている |
| 中規模 | 製品公開＋ベンチマーク＋デモが揃っている |
| 小規模 | 製品公開のみ。早期ユーザーからフィードバックを得ることが目的 |

**Step 3. 時系列の計画を作る**

```text
T-8週: 材料の準備開始。デザインパートナー・第三者（P25）に早期アクセスを提供
T-4週: パートナーと発表内容をすり合わせる。メディアへの事前説明
T-1週: デモ・記事・ベンチマークの最終確認。批判への回答（P17）を準備
T日  : 同時公開（製品、記事、デモ、パートナー発表）
T+1週: 早期ユーザーの成果を共有。批判に回答
T+4週: 第2波（揃わなかった材料、最初の顧客事例）
```

**Step 4. 第2波を計画する**

揃わなかった材料は、ローンチ後の「第2波」として計画する。第2波があると、ローンチの注目が一時的に終わらず、継続的な話題になる。

**Step 5. 成功の基準を事前に決める**

ローンチの前に、何をもって成功とするかを決めておく。View数ではなく、試用・Activation などの行動の指標で決める（P26）。

### 深掘りの問い

* ローンチ当日に、最初に話題にしてくれる第三者は誰か。その人は、事前に製品を触っているか。
* ローンチで注目が集まったとき、製品はその負荷に耐えられるか（サーバー、サポート）。
* ローンチの翌週に、話題を続ける材料はあるか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「プレスリリースを出して、SNSで告知する」 | 「規模は大規模。当日に、製品公開・カテゴリーの Point of View 記事・公開ベンチマーク・Viral Demo・資金調達・AI Gateway との統合を同時に発表する。T-8週から開発者20人に早期アクセスを提供し、当日に投稿してもらう。第2波は T+4週の最初の顧客事例。成功の基準は、当日から2週間での Activation 数」 |

### よくある失敗

* 材料が揃わないまま大規模なローンチをして、話題が1日で終わる。
* 当日のアクセス集中に製品やサポートが耐えられず、最初の体験が悪くなる。
* ローンチ後の第2波がなく、注目が続かない。

### 出力

```text
■ 材料の表
■ ローンチの規模
■ 時系列の計画
■ 第2波の計画
■ 成功の基準
```

### 次への受け渡し

* 成功の基準 → P26

## P21: Distribution

### 目的

ICPが **すでにいる場所** で、製品に出会えるようにする。新しいチャネルを作るより、顧客がすでに使っているプラットフォームに乗るほうが、到達コストも導入の手間も小さい。

### 入力

P5のICPと到達チャネル、P8のパートナー候補、P18の Motion。

### 手順

**Step 1. チャネルの候補を出す**

Marketplace / Cloud platform / IDE / Framework / Package manager / AI Gateway / GitHub / App Store / 既存SaaSのエコシステム / OSS integration / API aggregation service / 直販・営業 / SI・リセラー

**Step 2. チャネルを評価する**

| チャネル | ICPの到達数 | 導入の手間 | 既存の課金との統合 | 認証の手間 | 認知度 | 技術的な統合の難しさ | チャネル側の動機 | 評価 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

「チャネル側の動機」は、そのプラットフォームが自社製品を載せる理由である。動機がないチャネルは、載せてもらえても目立つ場所に置いてもらえない。

**Step 3. 統合の深さを決める**

同じチャネルでも、統合の深さで効果が大きく変わる。

| 深さ | 内容 | 効果 |
| --- | --- | --- |
| 掲載 | Marketplace に載っている | 小さい。見つけてもらう必要がある |
| 連携 | ワンクリックで接続できる | 中 |
| 組み込み | プラットフォームの標準機能の一部として使える | 大きい |
| 既定値 | プラットフォームで、何も設定しなければ自社製品が使われる | 最大 |

**Step 4. 上位2〜3チャネルを選ぶ**

最初からチャネルを増やしすぎない。上位2〜3チャネルに集中し、それぞれで深い統合を目指す。

**Step 5. チャネルへの依存のリスクを確認する**

1つのチャネルに売上の大部分を頼ると、そのチャネルの方針変更で事業が揺らぐ。依存度と、代替チャネルを書く。

### 深掘りの問い

* ICPの利用者は、新しいツールを探すとき、最初にどこを見るか。
* そのチャネルの提供企業にとって、自社製品を目立たせるメリットは何か。
* 数年後、そのチャネルの提供企業が同じ機能を自分で作ったら、どうなるか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「SNSとMarketplaceで広める」 | 「上位チャネルは AI Gateway と Agent フレームワーク。ICPの開発者は、すでにこの2つを使ってLLMを呼んでいる。AI Gateway では既存の課金にまとめられるので、新しい契約が要らない。フレームワークでは、Routing の標準部品として組み込んでもらうことを目指す。AI Gateway 側の動機は、判断用途での利用拡大」 |

### よくある失敗

* チャネルを増やしすぎて、どれも浅い掲載で終わる。
* チャネル側の動機を考えず、載せてもらえるはずだと思い込む。
* 1つのチャネルに依存し、その方針変更で事業が揺らぐ。

### 出力

```text
■ チャネルの評価表
■ 選んだチャネルと、目指す統合の深さ
■ 依存のリスクと代替チャネル
```

### 次への受け渡し

* 選んだチャネル → P22（導入の入り口）、P25（パートナー）、P29（Distribution の Moat）

## P22: Time-to-First-Value

### 目的

顧客が製品を見つけてから、**最初に価値を実感するまでの時間** を短くする。この時間が長いと、試用した顧客の多くが価値を感じる前に離脱する。デモ（P13）やローンチ（P20）で集めた関心も、ここで止まれば無駄になる。

### 入力

P5の成功の定義、P9のPrimitive、P18の Motion、P19の無料枠、P21の選んだチャネル（導入の入り口）。

### 手順

**Step 1. 「最初の価値」を定義する**

登録の完了や設定の完了ではなく、**顧客が「これは使える」と実感する瞬間** を定義する（Aha Moment）。

```text
例: 自分のデータで最初の判断結果が返ってきて、その速さと正しさを確認した瞬間
```

この定義は、P26の Activation の定義と同じにする。

**Step 2. 段階ごとの時間を測る**

```text
製品を見つける → 登録 → 認証 → 導入・設定 → 最初の価値
```

| 段階 | 所要時間（中央値） | 所要時間（遅い人、上位10%） | 離脱率 | 主な障害 |
| --- | --- | --- | --- | --- |

中央値だけでなく、遅い人の時間も見る。遅い人が詰まっている箇所に、改善の余地が大きい。

**Step 3. 目標を決める**

* Developer Product・PLG: **5分以内に最初の価値を体験できる**
* Sales-Led: PoC開始から **2週間以内に成功基準の達成を確認できる**

（製品に合わせて調整する）

**Step 4. 短縮策を選ぶ**

| 障害 | 短縮策の例 |
| --- | --- |
| 登録が面倒 | 既存のアカウント（GitHub、Google）で登録できる / 登録なしで試せる Playground |
| 支払い情報の入力 | 無料枠ではクレジットカードの登録を求めない |
| 設定が複雑 | コピーして貼るだけで動くコード / 1行で導入できるSDK |
| 自分のデータがない | サンプルデータ、テンプレートを用意する |
| 何を試せばいいかわからない | 用途別のテンプレート、チュートリアル |
| 社内の承認が必要 | データを社外に出さない構成 / セキュリティ資料を事前に用意する |

### 深掘りの問い

* 製品を初めて見た開発者が、ドキュメントを読まずに最初の結果を得られるか。
* 最初の価値を体験した人は、次に何をするか。その次の行動への導線はあるか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「導入が簡単」 | 「最初の価値の定義: 自分の入力で最初の判断結果が返ること。現状: 登録1分、APIキー発行30秒、SDKインストールとコード記述に8分（中央値）。上位10%は20分以上かかり、主な障害はサンプルコードが自分の言語にないこと。対策: 主要4言語のコピー用コードと、ブラウザの Playground を用意し、中央値3分を目指す（数値は仮置き）」 |

### よくある失敗

* 「登録完了」を最初の価値と定義し、本当の価値体験を測らない。
* 中央値だけを見て、詰まっている人の障害に気付かない。
* デモやローンチで関心を集めたのに、試す入り口が複雑で離脱させる。

### 出力

```text
■ 最初の価値の定義
■ 段階ごとの時間と障害
■ 目標
■ 短縮策
```

### 次への受け渡し

* 最初の価値の定義 → P26（Activation）
* 短縮策 → P13（デモからの導線）

## P23: UGC Potential

### 目的

ユーザー自身が、製品の新しい用途を発明し、共有する仕組みを作る。自社が考えつかない用途をユーザーが見つけると、それがそのまま新しい市場の発見になり、同時に宣伝にもなる。

### 入力

P9のPrimitive、P13の Viral Demo（用途の発明のきっかけ）。

### 手順

**Step 1. 用途を発明しやすいかを評価する**

| 項目 | 問い | 評価（1〜5） |
| --- | --- | --- |
| 入力の自由度 | 入力を自由に変えられるか | |
| APIの単純さ | P9のPrimitiveがそのまま使えるか | |
| 組み合わせやすさ | 他の製品と組み合わせられるか | |
| 組み込みやすさ | 他の製品の中に組み込めるか | |
| 実験の手軽さ | 小さな実験を、短時間・低コストで試せるか | |
| 共有のしやすさ | 結果を他の人に見せやすいか | |

**Step 2. 弱い項目の改善策を決める**

| 弱い項目 | 改善策の例 |
| --- | --- |
| 実験の手軽さ | 無料枠、Playground、テンプレート |
| 共有のしやすさ | 結果を共有できるリンク、埋め込み用のウィジェット、成果物に製品名が自然に入る仕組み |
| 組み合わせやすさ | 主要なフレームワーク用のパッケージ、サンプルの組み合わせ |

**Step 3. 発明された用途を集めて見せる場を作る**

* ユーザーが作った用途を紹介するギャラリー
* 用途ごとのテンプレートとして公開し、他のユーザーが使えるようにする
* 優れた用途を作ったユーザーを紹介する（ユーザーにとっての報酬になる）
* テーマを決めたコンテストやハッカソン

**Step 4. 用途の発明を市場の発見につなげる**

ユーザーが発明した用途のうち、利用が多いものを定期的に確認し、それを新しいセグメントや新しいメッセージの候補にする（P5の隣接セグメント）。

### 深掘りの問い

* 製品を使った人が、SNSに投稿したくなる成果物は何か。
* 自社が想定していない用途で使われたとき、それを知る仕組みはあるか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「ユーザーが自由に使える」 | 「Primitive が単純なので、入力の自由度・APIの単純さは5。弱いのは共有のしやすさ（2）で、結果を見せる手段がない。対策: 判断の結果を共有リンクにでき、リンク先から同じ設定で試せるようにする。ユーザーが作った用途を毎月ギャラリーで紹介し、利用が多い用途を隣接セグメントの候補にする」 |

### よくある失敗

* 用途を自社で決めすぎて、ユーザーが発明する余地がない。
* ユーザーが作った用途を集める仕組みがなく、発明が埋もれる。
* 共有された成果物から、試す入り口へのリンクがない。

### 出力

```text
■ 評価表
■ 改善策
■ 用途を集めて見せる場
■ 市場の発見につなげる仕組み
```

### 次への受け渡し

* 共有の仕組み → P24（Growth Loop の「共有」の部分）
* 発明された用途 → P5（隣接セグメント）

## P24: Growth Loop

### 目的

利用が次の利用を生む循環を作る。広告で1人ずつ獲得する一方向の流れ（Funnel）と違い、循環（Loop）は、ユーザーが増えるほど獲得が加速する。

### 入力

P18の Motion、P22の最初の価値、P23の共有の仕組み。

### 手順

**Step 1. Loop の型を選ぶ**

| 型 | 循環 | 向いている製品 |
| --- | --- | --- |
| バイラル | 利用 → 招待・共有 → 新しい利用者 | 複数人で使う製品、成果物を共有する製品 |
| コンテンツ | 利用 → 成果物・事例の公開 → 検索・SNSでの発見 → 新しい利用者 | UGCが生まれる製品 |
| 連携 | 利用者増 → 連携先の増加 → 連携先経由の利用者増 | プラットフォーム型の製品 |
| 事例 | 導入 → 成果 → 事例の公開 → 同業他社の関心 → 商談 | Sales-Led の製品 |
| 収益 | 売上 → 広告・営業への投資 → 新しい顧客 → 売上 | どの製品でも。ただし最も遅く、コストがかかる |

主な Loop を **1つ** 選ぶ。最初から複数の Loop を回そうとすると、どれも中途半端になる。

**Step 2. Loop の各矢印を具体化する**

```text
利用 → 価値の発見 → 成果物の生成 → 共有 → 第三者の認知 → 試用 → 利用
```

各矢印について、以下を書く。

| 矢印 | 何が次の行動を起こさせるか | 転換率（見込み） | 所要時間 | 途切れる理由 | 対策 |
| --- | --- | --- | --- | --- | --- |

**Step 3. Loop を数値で見積もる**

* **1周の時間**: Loop を1周するのにかかる時間。短いほど成長が速い。
* **1周あたりの増加**: 1人の利用者が、1周で何人の新しい利用者を連れてくるか。

1周あたりの増加が1を超えると自走する。多くの製品では1を下回るが、その場合でも、他の獲得手段（広告、営業）のコストを下げる効果がある。

**Step 4. 最も弱い矢印を特定する**

転換率が最も低い、または時間が最もかかる矢印を特定し、そこに集中して改善する。

### 深掘りの問い

* ユーザーが製品を使ったことを、周りの人はどうやって知るか。
* 共有された成果物を見た人は、どこをクリックすれば試せるか。
* Loop の中で、自社がコントロールできない矢印はどれか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「ユーザーが増えれば口コミで広がる」 | 「主な Loop はコンテンツ型。開発者が意外な用途（ゲーム操作など）を作る → SNSに動画を投稿（動機: 技術力を見せたい）→ 見た開発者が『自分も試したい』と思う → 投稿内のリンクから Playground へ → 3分で自分の用途を試す → 新しい用途を作る。最も弱い矢印は『投稿を見た → 試す』で、投稿にリンクが入っていないことが多い。対策: 成果物の共有機能にリンクを自動で入れる」 |

### よくある失敗

* Loop を描くだけで、各矢印で何が次の行動を起こさせるのかを書かない。
* 複数の Loop を同時に回そうとして、どれも中途半端になる。
* Loop の中で、自社がコントロールできない矢印に頼りきる。

### 出力

```text
■ 選んだ Loop の型
■ 各矢印の表
■ 1周の時間と、1周あたりの増加の見積もり
■ 最も弱い矢印と、その対策
```

### 次への受け渡し

* Loop の各矢印 → P26（指標）
* Loop が生むデータや連携 → P29（Moat）

## P25: Third-Party Amplification

### 目的

自社以外の主体が、カテゴリーと製品を説明し始める状態を作る。自社がカテゴリーの重要性を語っても宣伝にしか聞こえないが、第三者が語ると、市場の事実として受け取られる。

### 入力

P6のカテゴリーと Point of View、P8のパートナー候補、P11の数値と条件、P12の証拠、P14の Founder Story（メディア・投資家への説明）、P16の主張（第三者の議論のきっかけ）、P21の選んだチャネル（パートナー）。

### 手順

**Step 1. 第三者を洗い出し、動機を書く**

| 第三者 | その人にとってのメリット | 働きかけ方 | 優先度 |
| --- | --- | --- | --- |
| Platform Vendor | 自社プラットフォームの利用拡大、新しい用途 | 共同発表、統合 | |
| OSS Maintainer | プロジェクトの機能向上、利用者増 | 統合のコード提供、スポンサー | |
| Developer Influencer | 新しい話題、フォロワーへの価値提供 | 早期アクセス、技術的な説明 | |
| Researcher | 研究の題材、新しい手法の検証 | 研究用の無償提供、データ公開 | |
| Customer | 先進的な取り組みとしての評価、採用へのアピール | 事例の共同作成、登壇の機会 | |
| Investor | 投資先の価値向上、市場の見立ての発信 | 市場の Point of View の共有 | |
| Analyst | 新しい市場区分の発見 | カテゴリーの説明、データ提供 | |
| Community | 知識の共有、交流 | イベント、ハッカソン | |

**Step 2. 第三者が説明しやすい材料を用意する**

第三者は、自分で一から調べて説明する時間がない。以下を用意する。

* カテゴリーの Point of View（P6）を1ページにまとめた資料
* 自由に使えるベンチマークのデータと図
* 試すためのクレジットや早期アクセス
* 引用できる数値と、その条件（P11）

**Step 3. 順序を決める**

一般的には、以下の順で広がる。

```text
作り手（開発者、研究者）が触る → 発信者（インフルエンサー）が紹介する → プラットフォームが統合する → アナリスト・メディアが市場として扱う
```

最初の段階の第三者に、ローンチ前（P20のT-8週）から触ってもらう。

**Step 4. 第三者の発信を測る**

* 第三者がカテゴリー名を使った回数
* 自社以外が書いた記事・動画・チュートリアルの数
* 第三者の発信のうち、正しく説明されているものの割合

### 深掘りの問い

* 第三者が、自社製品を批判的に紹介した場合でも、カテゴリー名は使われるか。
* 第三者の説明が誤っていた場合、どう訂正するか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「インフルエンサーに紹介してもらう」 | 「最初は Agent フレームワークの開発者と、AI分野の研究者。フレームワーク側の動機は Routing 部品の追加で、統合のコードを自社で書いて提供する。研究者には無償の利用枠と公開ベンチマークのデータを渡す。ローンチの8週前から触ってもらい、当日に投稿や記事を出してもらう。第三者によるカテゴリー名の使用回数を月次で追う」 |

### よくある失敗

* 第三者にとってのメリットを考えず、紹介をお願いするだけになる。
* 説明しやすい材料を用意せず、第三者が誤った説明をする。
* 有料の宣伝を第三者の意見のように見せる（発覚すると信頼を失う）。

### 出力

```text
■ 第三者の表（動機・働きかけ方・優先度）
■ 用意する材料
■ 順序
■ 測り方
```

### 次への受け渡し

* 第三者の発信 → P30（Category Ownership の指標）
