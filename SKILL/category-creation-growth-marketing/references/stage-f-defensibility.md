# Stage F: 防御と所有（P28〜P32）

Stage F では、成功した後に真似されても勝ち続けられるかを確かめ、戦略全体の弱点を正直に指摘し、次に何を検証するかを決める。

---

## P28: Competitive Response & Big-Tech Replication

### 目的

製品が成功したときに、既存の競合や大手がどう反応するかを予測し、事前に対応を決めておく。新しいカテゴリーが話題になれば、必ず真似される。真似されたときに何が残るかが、会社の価値を決める。

### 入力

P0.5の先行事例の表（競合の一覧として使う）、P2の構造原因の種類と P3の「なぜ大手が動いていないか」（Step 2 の手がかり）、P6の市場定義、P7の比較軸と追随の難しさ、P8のパートナーと依存のリスク、P17の「大手が作れば終わる」への事実確認。

### 手順

**Step 1. 競合の反応を、動機・能力・時間で予測する**

競合の洗い出しは P0.5 で済んでいる。このPhaseでは同じ調査を繰り返さず、P0.5 の表にある主要な競合と代替手段ごとに、ローンチ後の反応を評価する。P0.5 の後に新しい参入者の発表があった場合だけ、追加で調べる。

| 競合 | 動機（真似する理由の強さ） | 能力（技術・人材・チャネル） | 時間（同等のものを出すまでの期間） | 予想される反応 | 自社への影響 |
| --- | --- | --- | --- | --- | --- |

* **動機**: 自社の成功が、その競合の主力の売上を脅かすか。脅かさないなら、真似する動機は弱い。
* **能力**: 同じものを作る技術と、顧客に届けるチャネルを持っているか。
* **時間**: 研究開発、組織の意思決定、既存製品との調整にかかる時間。

反応の型: 無視 / 「それはすでにできる」と主張 / 機能を追加 / 値下げ / 買収 / 提携

**Step 2. 大手が動きにくい構造を探す**

大手が、能力があっても動きにくい理由がある場合、それは自社の防御になる。

| 構造 | 例 |
| --- | --- |
| 自社の売上との衝突 | トークン量で課金している企業は、トークン量を減らす製品を出しにくい |
| 既存顧客との衝突 | 既存顧客が使っている方法を否定することになる |
| 組織の優先順位 | 市場が小さく見えるうちは、大企業の中で優先されない |
| ブランドとの衝突 | 「最高性能」を売りにしている企業は、「必要十分」を売りにしにくい |

**Step 3. Big-Tech Replication Test を行う**

必ず以下を問う。

> Google、Microsoft、Amazon、OpenAI、Anthropic などが、同等の機能を6か月後に無料または低価格で提供した場合、この会社は存続できるか？

製品領域に応じて、関係する大手を入れ替える（例: 会計ならIntuit、CRMならSalesforce）。

* **YES** の場合: 理由を具体的に書く（P29のどのMoatが、6か月後までにどの程度育っているか）。
* **NO** の場合: P29で、6か月以内に何を育てれば YES になるかを検討する。

**Step 4. シナリオごとの対応を事前に決める**

| シナリオ | 発生の兆候 | 対応 |
| --- | --- | --- |
| 大手が同等機能を無料で提供 | 大手の開発者会議での発表、ベータ版の公開 | |
| 大手が自社を買収しようとする | | |
| 既存の競合が値下げする | | |
| パートナー（P8）が同じ機能を自分で作る | | |

事前に対応を決めておくと、実際に起きたときに慌てずに済み、顧客や投資家にも説明できる。

### 深掘りの問い

* 大手が同等の機能を出したとき、自社の既存顧客は乗り換えるか。乗り換えない理由は何か。
* 大手が参入することで、カテゴリー自体の認知が広がり、自社にとって有利になる可能性はあるか。
* 自社の成功が、大手にとってどれくらい目立つか。目立たないうちに何を育てられるか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「大手が参入しても、技術力で勝てる」 | 「最も可能性が高いのは、LLM提供企業が Structured Outputs の延長として、軽量な判断モードを出すこと（動機: 中、能力: 高、時間: 6〜12か月）。ただし、トークン課金との衝突で大幅な値下げはしにくい。6か月後の存続: 条件付きで YES。条件は、主要な AI Gateway とフレームワークで標準の Routing 部品になっていること（P29の Distribution と Workflow の Moat）」 |

### よくある失敗

* 「技術力で勝てる」と、大手の能力と動機を過小評価する。
* 大手が真似した場合の対応を、起きてから考える。
* パートナー（P8）が競合になる可能性を見ない。

### 出力

```text
■ 競合の反応の予測表
■ 大手が動きにくい構造
■ Big-Tech Replication Test の結果と理由
■ シナリオごとの対応
```

### 次への受け渡し

* テストの結果 → P29（育てるべき Moat）
* シナリオ → P31（リスク）

## P29: Defensibility & Standardization

### 目的

競合が機能を真似しても、顧客が自社を選び続ける理由（Moat）を育てる。機能は真似できるが、時間をかけて積み上がるもの（データ、習慣、エコシステム、標準の地位）は真似しにくい。

### 入力

P21のチャネル、P24の Loop、P28のテスト結果。

### 手順

**Step 1. Moat の候補を評価する**

| Moat候補 | 今の強さ（1〜5） | 12か月後に目指す強さ | 利用とともに強くなるか | 強くするための施策 |
| --- | --- | --- | --- | --- |
| Distribution（チャネルの独占・優先的地位） | | | | |
| Data（利用から得られる独自データ） | | | | |
| Workflow（顧客の業務への組み込み） | | | | |
| Ecosystem（連携、サードパーティ） | | | | |
| Standard（API、評価基準、ベンチマーク） | | | | |
| Community | | | | |
| Switching cost（乗り換えのコスト） | | | | |
| Developer habit（開発者の習慣） | | | | |
| Brand association・Category terminology | | | | |
| Documentation・SDK | | | | |

**「利用とともに強くなるか」** が最も重要な列である。利用が増えるほど強くなる Moat（データ、エコシステム、習慣）は、時間とともに差が広がる。一度作れば終わりの Moat（ドキュメント、ブランドの初期の印象）は、競合もいずれ追いつく。

**Step 2. Moat の型で整理する**

一般的に使われる Moat の型（Hamilton Helmer の 7 Powers）で整理すると、見落としを防げる。

| 型 | 内容 | 初期の会社での使いやすさ |
| --- | --- | --- |
| Counter-Positioning | 既存企業が、自社のビジネスを壊さずには真似できない方法を取る | **高い。** 初期の会社が最も使いやすい |
| Switching Costs | 顧客が乗り換えると、手間・コスト・リスクが生じる | 中。顧客の業務に組み込まれるほど強くなる |
| Network Economies | 利用者が増えるほど、1人あたりの価値が増える | 中。一定の規模が必要 |
| Scale Economies | 規模が大きいほど、1単位あたりのコストが下がる | 低い。大手のほうが有利 |
| Branding | 同じ製品でも、ブランドによって高い価値を感じる | 低い。時間がかかる |
| Cornered Resource | 独占的に使える資源（人材、特許、データ） | 場合による |
| Process Power | 真似しにくい組織の能力 | 低い。時間がかかる |

P28の「大手が動きにくい構造」は、Counter-Positioning に当たる。

**Step 3. 見せかけの Moat を除く**

以下は、Moat のように見えて Moat ではない。

* 「技術的に優れている」（数か月で追いつかれる）
* 「先に始めた」（先行者の優位は、何かを積み上げていなければ消える）
* 「チームが優秀」（競合も優秀な人を雇える）
* 「特許を出願中」（ソフトウェアの特許は、回避されやすい）

**Step 4. エコシステムを設計する**

* 誰が、自社製品の上に何を作ると得をするか
* そのための仕組み（SDK、API、Marketplace、収益の分配、認定制度など）
* エコシステムの参加者が増えると、自社の顧客にとって何が良くなるか

**Step 5. 標準化の戦略を決める**

* 自社が標準にしたいもの（API仕様、評価方法、用語、ベンチマークなど）
* それを他社が採用するメリット
* オープンにする部分と、自社で持つ部分の境界

オープンにしすぎると、競合が同じ標準の上で自社と同じものを作れる。閉じすぎると、標準として採用されない。一般的には、**インターフェース（API仕様、評価方法）をオープンにし、実装（モデル、データ、運用）を自社で持つ** ことが多い。

### 深掘りの問い

* 1年後、顧客が自社から乗り換えるときに失うものは何か。
* 自社の利用が増えると、自社製品はどのように良くなるか。競合の製品は、同じように良くなるか。
* 自社が定義した標準を、競合が採用したら、自社にとって得か損か。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「技術力とブランドがMoat」 | 「最も重要な Moat は Workflow と Standard。開発者が判断APIの形式（State＋Question＋Allowed Answers）を前提にコードを書くほど、乗り換えのコストが増える。API仕様と評価方法を公開し、フレームワークに標準の形式として採用してもらう。モデル本体と判断ログから得た改善データは自社で持つ。Counter-Positioning: トークン課金の大手は、判断回数あたりの課金に移りにくい」 |

### よくある失敗

* 「技術的に優れている」「先に始めた」を Moat として挙げる。
* 今の強さだけを見て、利用とともに強くなるかを見ない。
* 標準化を狙って仕様をすべてオープンにし、自社の持ち分がなくなる。

### 出力

```text
■ Moat候補の評価表
■ 7 Powers での整理
■ 見せかけの Moat の除外
■ エコシステムの設計
■ 標準化の戦略（オープンにする部分と持つ部分）
```

### 次への受け渡し

* Moat → P28の Big-Tech Replication Test の再評価、P30

## P30: Category Ownership

### 目的

「このカテゴリーといえば自社」という状態を作る。カテゴリーの代表として思い出されると、顧客が問題を認識したときに最初に検討され、比較の基準にもなる。

### 入力

P6のカテゴリー、P25の第三者、P29の Moat。

### 手順

**Step 1. 目指す状態を確認する**

```text
顧客が問題を認識 → カテゴリー名を思い出す → カテゴリーを検索する → 自社を思い出す
```

**Step 2. 所有の指標を決める**

| 指標 | 測り方 |
| --- | --- |
| カテゴリー名の検索 | カテゴリー名の検索量と、その検索結果に占める自社の割合 |
| 第三者の使用 | 記事、SNS、論文でカテゴリー名が使われる回数と、そのうち自社が言及される割合 |
| 比較の基準 | 競合が「○○（自社）のような」「○○の代替」と自社を基準に説明しているか |
| アナリストの分類 | 調査会社の市場区分に、カテゴリーが載っているか |
| 顧客の言葉 | 顧客が、社内の稟議や求人でカテゴリー名を使っているか |

**Step 3. 所有するための活動を決める**

| 活動 | 内容 |
| --- | --- |
| カテゴリーの定義文書 | Point of View（P6）を公開し、定期的に更新する |
| 定期的な市場レポート | カテゴリーの利用状況や、ベンチマークの結果を年1回などで公開する |
| 用語集・教育コンテンツ | カテゴリーに関する用語と、使い方を説明する |
| コミュニティ・イベント | カテゴリーに関わる人が集まる場を主催する |
| ベンチマークの管理 | カテゴリーの標準的な評価方法を管理する（P29） |

**Step 4. 他社の参加を歓迎する**

カテゴリーに他社が参加することは、カテゴリーが本物の市場になった証拠である。他社の参加を歓迎し、その中で自社が代表であり続ける状態を目指す。自社しかいないカテゴリーは、市場として認識されにくい。

P6でC（既存カテゴリー内の再ポジショニング）を選んだ場合は、「既存カテゴリーの中で、○○なら自社」という想起を作る方法を書く。

以下の問いに答える。

> 「この市場カテゴリーを聞いたとき、最初に自社名が思い浮かぶ状態を、どう作るか？」

### 深掘りの問い

* 顧客が問題を感じたとき、検索窓に何と入力するか。それはカテゴリー名か。
* 競合がカテゴリーに参加したとき、自社が代表であり続ける理由は何か。
* カテゴリー名が一般的になりすぎて、自社と結び付かなくなるリスクはあるか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「カテゴリーのリーダーを目指す」 | 「指標は、カテゴリー名の検索結果での自社の割合、第三者の記事での自社の言及割合、競合が自社を基準に説明している回数。活動は、年1回の『判断モデルのベンチマーク報告』の公開と、評価方法の管理。他社の参加を歓迎し、ベンチマーク報告に他社製品も載せることで、カテゴリーの中立的な基準を持つ立場を取る」 |

### よくある失敗

* カテゴリー名を自社の製品名と同じにして、他社が参加できない。
* 所有の状態を測る指標を決めない。
* 他社の参加を排除しようとして、カテゴリーが市場として認識されない。

### 出力

```text
■ 所有の指標
■ 所有するための活動
■ 他社の参加への姿勢
■ 問いへの答え
```

### 次への受け渡し

* 所有の指標 → P26の Advocacy・Ecosystem の指標に追加

## P31: Reality Check

### 目的

戦略全体を振り返り、成り立たない点や弱い点を正直に指摘する。**マーケティングで製品価値の不足を隠してはいけない。** ここで指摘しないと、戦略が実行されてから問題が表に出て、より大きな損失になる。

最初に **反証パス** を行う。構想を作った後は、その構想を支える情報ばかりが目に入る。反証パスは、構想を作った思考の流れから切り離して、構想を否定する事実だけを探す手順である。

### 入力

実行したすべてのPhaseの結論。P0.5の調査の記録。

### 手順

**Step 0. 反証パスを行う**

1. **立場を切り替える。** ここからは、この構想を否定したい人（競合の担当者、懐疑的な投資家、その分野の研究者）として作業すると明記する。サブエージェントなど別の担当に任せられる環境では、構想の結論だけを渡し、「この構想を否定する事実を探す」ことだけを依頼する。構想を作った経緯や、支える根拠は渡さない。
2. **否定するための問いを立てる。** 構想の中心となる主張（P2の再定義、P3の反対仮説、P6の判定、P7の比較軸、P11の主役の数値）ごとに、「これが間違いだとすれば、どんな事実があるはずか」を書く。
   ```text
   例: 主張「この領域には先行事例がない」
       → 間違いだとすれば: 別の用語で呼ばれている既存製品がある / 研究で解決済みである / 大手が直近に同じ機能を発表している
   ```
3. **その事実を探す。** P0.5 で使わなかった言い方、情報源の種類、期間で調べる。P0.5 と同じ検索を繰り返しても、新しい反証は見つからない。
4. **結果を記録する。**

   | 主張 | 間違いだとすれば存在する事実 | 調べたこと | 見つかった反証 | 扱い |
   | --- | --- | --- | --- | --- |

   「扱い」には、反証なし（調査範囲を書く） / 主張の範囲を狭める / `SKILL.md` 4.4 に従って上流に差し戻す、のいずれかを書く。

反証が1つも見つからなかった場合も、調べた範囲を書く。「反証なし」は、調べた範囲の中での結論である。

**Step 1. リスクの候補を確認する**

以下に当てはまるものがないかを確認する。

* 技術的に成立しない
* 性能の差が小さい
* 顧客にとっての価値が小さい
* 乗り換えのコストが大きい
* 市場が小さい
* 利益率が低い
* 顧客獲得コストが高い
* 継続利用されない
* 大手のコピーに弱い
* 市場教育のコストに対して、資金・時間が足りない
* 重要な前提が、すべて [仮説] のままである
* 先行事例の確認（P0.5）が未実施、または調査範囲が狭い

**Step 2. 深刻度と可能性で評価する**

| リスク | 深刻度（1〜5） | 可能性（1〜5） | 根拠 | 関連Phase | 対応 |
| --- | --- | --- | --- | --- | --- |

深刻度は、そのリスクが現実になったときに、戦略全体がどれくらい崩れるかで評価する。

**Step 3. 3段階に分ける**

```text
致命的な問題（戦略の前提が崩れる）:
重大な問題（対策が必要）:
注意点（監視が必要）:
```

該当がなければ「該当なし」と書き、その判断の根拠を添える。

**Step 4. 全体の判定を出す**

```text
判定: 進める / 条件付きで進める（条件: …） / 見直す（見直す点: …）
理由:
```

「条件付きで進める」の場合、その条件をP32の実験で検証する。

### 深掘りの問い

* この戦略が1年後に失敗していたとしたら、最も可能性の高い理由は何か。
* 戦略の中で、最も楽観的な前提はどれか。
* ユーザーが聞きたくないが、知っておくべきことは何か。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「大きなリスクはない」 | 「重大な問題: 実業務での精度を示す証拠がなく、『ただの分類器』という批判が定着するおそれがある（深刻度4、可能性3）。注意点: 有料転換率と継続率が公開されていない。判定: 条件付きで進める。条件は、主要3用途でのベンチマーク公開（P32 #1）」 |

### よくある失敗

* 戦略を作った後で、弱点を指摘することを避ける。
* 反証パスで、構想を支える情報を探してしまう（「やはり正しかった」という確認作業になる）。
* 「リスクはあるが、施策で対応できる」とだけ書き、どのリスクにどの施策が効くのかを示さない。
* [仮説] のまま進めている前提を、リスクとして挙げない。

### 出力

```text
■ 反証パスの結果（主張ごとの表）
■ リスクの評価表
■ 致命的・重大・注意点
■ 全体の判定と理由
```

### 次への受け渡し

* 致命的・重大な問題 → P32（最優先の実験）

## P32: Next Experiments

### 目的

未検証の項目と [仮説] を、実行できる実験に変える。戦略は、検証されるまでは仮説の集まりである。どの仮説から検証するかを決めることが、次の行動になる。

### 入力

実行したすべてのPhaseの [仮説] と未検証の項目、P27の最も重要な前提、P31の致命的・重大な問題。

### 手順

**Step 1. 仮説を集める**

すべてのPhaseから、[仮説] と「未検証」の項目を集める。

**Step 2. 最もリスクの大きい仮説を特定する**

各仮説について、以下を評価する。

* **外れたときの影響**: 外れると、戦略のどこまでが崩れるか
* **確信度**: 今ある証拠で、どれくらい確かか

外れたときの影響が大きく、確信度が低い仮説が、最初に検証すべきものである。

**Step 3. 反証できる形に書き直す**

```text
もし【仮説】が正しいなら、【方法】を行ったときに、【指標】が【基準】以上になる。
```

例: 「もし ICP の開発者が判断のコストに困っているなら、AI Gateway のユーザー1,000人に無料枠を案内したときに、2週間以内に50人以上が Activation に達する」

**Step 4. 実験を設計する**

| # | 検証する仮説 | 関連Phase | 方法 | 指標 | 成功基準 | 判断ルール | コスト・期間 | 優先度 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | | | | | | | | |

**判断ルール** には、成功した場合と失敗した場合に何をするかを、実験の前に書く。

```text
成功: ○○に進む
失敗: △△を見直す（どのPhaseに戻るか）
結果があいまい: 期間を延ばす／サンプルを増やす
```

判断ルールを事前に決めないと、結果が出た後に都合よく解釈してしまう。

**Step 5. 実験の方法を選ぶ**

| 検証したいこと | 方法の例 |
| --- | --- |
| 課題が存在するか | 顧客インタビュー（P1の方法）、回避策の観察 |
| 顧客が興味を持つか | ランディングページの登録率、事前登録 |
| 顧客が使えるか | プロトタイプの試用、Playground での Activation 率 |
| 顧客が使い続けるか | 限定的な試験導入、コホートの継続率 |
| 顧客が払うか | 有料の事前予約、デザインパートナーへの見積もり |
| 主張が正しいか | 公開ベンチマーク、第三者による検証 |

**Step 6. 優先度を付ける**

* **高**: 外れると戦略の前提が崩れる（P31の致命的な問題、P2の再定義、P5のICP、P27の事業性）かつ、安く速く検証できる
* **中**: 外れると一部の施策の変更が必要
* **低**: 外れても影響が小さい

優先度「高」を上から並べ、最初の1件は **今週中に始められる** 粒度にする。

### 深掘りの問い

* この実験の結果が出たら、実際に行動を変えるか。変えないなら、その実験は不要である。
* もっと安く、もっと速く、同じことを確かめる方法はないか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「市場の反応を見る」 | 「仮説: ICPの開発者は判断コストに困っている。方法: AI Gateway ユーザー1,000人に無料枠を案内。指標: 2週間以内の Activation 数。成功基準: 50人以上。判断ルール: 成功なら有料プランの設計（P19）に進む。20人未満なら P5 の ICP を見直す。20〜50人なら、Activation しなかった人10人にインタビューする。コスト: 案内メールの作成のみ、2週間。優先度: 高」 |

### よくある失敗

* 「市場の反応を見る」のように、成功基準のない実験を書く。
* 結果が出てから判断ルールを決め、都合よく解釈する。
* 検証しやすいが重要でない仮説から始め、最も危険な仮説を後回しにする。

### 出力

```text
■ 仮説の一覧と、リスクの評価
■ 実験の表（判断ルールつき）
■ 最初に始める実験
```
