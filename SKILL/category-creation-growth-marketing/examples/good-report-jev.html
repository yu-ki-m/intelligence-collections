結論

TypeSafe AI は、Jev を「文章を作らずに、決められた選択肢から答えを1つ選ぶだけのAI」として売り出し、そのための新しい市場の名前（System One Model）を作った。この売り方が成り立つかは、長くて整理されていない入力でも、Jev が文章を作るAI（LLM）と同じくらい正しく選べるかにかかっており、その点はまだ確かめられていない。

第0章

このレポートを読むための前提

粒度 1（標準）
結論

このレポートを読むには、「LLM が答えを作る方法」「Agent が判断を繰り返すこと」「このレポートでいう判断の意味」の3つの知識と、根拠の強さを示すラベルの読み方が必要である。この章では、それらを1つずつ説明し、最後にこの分析の限界を示す。

前提1〜3の説明は、LLM や Agent の一般的な仕組みであり、この分析の主張ではない。

前提1: LLM は、答えを小さな単位に分けて、1つずつ順番に計算して作る

LLM（大規模言語モデル）は、文章を作るAIである。ChatGPT や Claude の中で動いているのが LLM である。LLM は、答えの文章を「トークン」という小さな単位（単語や、単語の一部）に分け、1つずつ順番に計算して作る。

多くの LLM の料金は、LLM に渡した文章の量と、LLM が作った文章の量（どちらもトークンの数）で決まる。そのため、LLM が作る文章が長いほど、答えが返るまでの時間と料金が増える。

例（仮の場面）

開発者が LLM に「この問い合わせは billing（請求）と technical（技術）のどちらの担当に回すべきか」と聞く。欲しい答えは "billing" の1語だけでも、LLM はその答えを、長い文章を作るときと同じ方法で、トークンを計算して作る。

前提2: Agent は、1つの作業の中で、判断を何度も繰り返す

Agent（AIエージェント）は、1つの作業を終えるまでに、「次に何をするか」を繰り返し決めながら動くプログラムである。Agent が判断のたびに LLM を呼ぶと、LLM を呼んだ回数だけ、時間と料金がかかる。Agent が判断を繰り返す流れを、このレポートでは Agent Loop と呼ぶ。

  1. 判断 1

    どの担当に回すか

    Agent が LLM を呼ぶ（1回目）。

  2. 判断 2

    追加の情報を聞くか

    Agent が LLM を呼ぶ（2回目）。

  3. 判断 3

    返信を送ってよいか

    Agent が LLM を呼ぶ（3回目）。

例（仮の場面）

問い合わせに対応する Agent は、1件の問い合わせについて、上の図の3つの判断を順番に行う。3つの判断のたびに LLM を呼ぶと、1件で LLM を3回呼ぶことになり、料金も3回分かかる。

前提3: このレポートでいう「判断」は、決められた選択肢から1つを選ぶこと

このレポートでいう判断は、あらかじめ決めた選択肢の中から、答えを1つ選ぶことを指す。判断の答えは選択肢のどれかであり、文章ではない。

例（仮の場面）

選択肢が billing と technical の2つなら、判断の答えは billing か technical のどちらかである。「この問い合わせは請求に関するものなので……」のような説明の文章は、判断の答えに含まない。

この分析では、主な主張に、根拠の強さを示すラベルを付けている。ラベルは次の4種類である。

第1章

すでに解かれている部分はどこか

粒度 1（標準）

分析の該当箇所: P0.5 先行事例の確認（Prior Art Sweep）

結論

「答えを決まった形式で返すこと」と「選択肢をその場で指定して分類すること」は、Jev より前からある手段ですでにできる。Jev に残る違いは、長くて整理されていない入力について、LLM と同じくらい正しい判断を、LLM よりけた違いに安く速く返せるかどうかだけであり、この点はまだ確かめられていない。

用語

先行事例

この文脈での意味
Jev と同じ問題（判断の答えを得ること）を、Jev より前から解いている製品や手法。
例
下の3枚のカード（構造化出力、分類器、小型の LLM）。

この分析では、3つの先行事例について、「できること」と「できないこと」を分けて確認した。

先行事例 1

LLM の構造化出力（Structured Outputs、Tool Calling）

何か
LLM の提供企業が用意している機能である。LLM の答えを、あらかじめ決めた形式（JSON。プログラムが読み取りやすいデータの書き方）に合わせて返させる。
できること
開発者は、判断の結果を、プログラムが読める決まった形式で受け取れる。
できないこと
Agent が判断のたびに LLM を呼ぶことは変わらないので、判断を繰り返すと遅くなり、料金も高くなる。[事実: LangChain blog]
確認の状況
二次資料（LangChain の記事）で確認した。各 LLM 提供企業の公式の説明書では、まだ確認していない。
先行事例 2

分類器（zero-shot 分類器・専用の分類器）

何か
分類器は、入力を、決まった選択肢のどれかに振り分けるモデルである。分類器は文章を作らない。zero-shot 分類器は、選択肢を、学習のときではなく、使うときに言葉で指定できる分類器である。
できること
開発者は、使うときに選択肢を指定して、分類器に判断させられる。分類器は、LLM より安く分類できる。
できないこと
分類器は、長くて整理されていない入力について、LLM と同じくらい正しく判断することはできない（まだ確かめていない）。[仮説]
確認の状況
コミュニティでの比較の議論で確認した。[事実: OpenChamber] 各ライブラリ（開発者が使う部品）の公式の説明書では、まだ確認していない。
先行事例 3

小型・軽量の LLM

何か
大型の LLM より小さく、安く速く動く LLM である。
できること
開発者は、大型の LLM より安く速く、小型の LLM に判断させられる。
できないこと
小型の LLM も文章を作る方法で答えるので、判断だけが必要な用途では、文章を作る分の時間と料金が残る。[推定]
確認の状況
まだ確認していない。本来は、各モデルの公式の料金表と仕様で確認する。

3つのカードを並べると、先行事例は、Jev が提供するものの一部をすでに提供していることが分かる。構造化出力は決まった形式の答えを、分類器は文章を作らない判断を、小型の LLM は安さと速さを、それぞれすでに提供している。3つのどれも提供していないのは、長くて整理されていない入力について、LLM と同じくらい正しく、しかも安く速く判断することである。

Jev に残る違い（残る隙間）

用語

残る隙間

この文脈での意味
先行事例がまだ解いていない部分。Jev が新しさを主張できるのは、この部分だけである。
例
下の図の3つの条件を、すべて満たす判断。
  1. 条件 1

    入力が長く、決まった項目に整理されていない。

  2. 条件 2

    判断の答えが、LLM と同じくらい正しい。

  3. 条件 3

    LLM を呼ぶよりけた違いに安く、速く答えを返す。

3つの条件をすべて満たす判断が、Jev に残る違いである。[仮説: 第8章の検証1で確かめる]

3つの条件は、すべてを同時に満たす必要がある。入力が短く整理されている判断（条件1を満たさない判断）なら、既存の分類器で足りる。LLM と同じくらい正しくても、料金と時間が LLM と変わらなければ（条件3を満たさない場合）、開発者が LLM から Jev に切り替える理由がない。[推定]

例（仮の場面）

Agent がそれまでに行った操作の記録や、顧客とのやり取りの全文は、「金額」「日付」のような決まった項目に分かれていない長い文章である。このような入力を見て「次に何をするか」を選ぶことが、条件1に当たる判断である。

この分析は、この領域を「部分的に解決済み」と判定した。部分的に解決済みとは、既存の手段はあるが、特定の条件（上の3つ）ではまだ解けていない状態を指す。以降の章は、この残る隙間だけを対象にする。

この結論が間違いだとわかる条件

公式の資料を確認して、既存の手段が上の3つの条件をすでに満たしているとわかった場合、Jev に残る違いはなくなり、以降の章の結論も変わる。

第2章

市場は何を当たり前だと思っているか

粒度 1（標準）

分析の該当箇所: P1 既存の前提（Existing World）

結論

Agent を作る開発者は、「AI に判断させるには、LLM に文章を作らせる必要がある」と考えている。この考えのもとで、判断のたびに LLM を呼ぶ設計が当たり前になっている。

分析は、公開情報から、今の設計を支えている3つの前提を推定した。[推定] 下の図は、3つの前提が、今の設計を支えている関係を示す。

  • 今の設計Agent は、判断のたびに LLM を呼ぶ。
    • 支えている前提 1開発者は、「AI の判断を得るには、LLM に文章を作らせる必要がある」と考えている。
    • 支えている前提 2開発者は、「答えの形式を守らせるには、構造化出力で LLM の文章の作り方を制限すればよい」と考えている。
    • 支えている前提 3開発者は、「いろいろな判断に対応するには大きな汎用の LLM が必要で、専用の分類器は判断の種類ごとに作るものだ」と考えている。

3つの前提は、どれも「判断には LLM が必要だ」という同じ方向を向いている。そのため、開発者は、判断のたびに LLM を呼ぶ設計を、ほかの選択肢と比べずに選んでいる。[推定]

例（仮の場面）

開発者は、問い合わせの振り分けに構造化出力を使い、LLM に {"team": "billing"} という形式で答えさせる。答えの形式は守られるが、LLM を1回呼ぶ時間と料金は変わらない。これは、前提2に従った設計である。

まだ確かめていないこと

この3つの前提は、公開情報からの推定であり、開発者への聞き取りで確かめたものではない。開発者の実際の作業の流れと、判断にかかっている今の費用も、公開情報からは得られていない（第9章）。

次の章へ → 次の章では、この当たり前のもとで何が起きているかを、目に見える症状から原因へと1段ずつたどる。

第3章

本当の問題は何か

粒度 1（標準）

分析の該当箇所: P2 問題の再定義（Problem Discovery）

結論

問題は、LLM が十分に賢くないことではない。長くて整理されていない入力を正しく判断できる手段が LLM しかないため、文章が要らない判断にまで、文章を作る時間と料金を払っていることが問題である（仮説）。

よく言われる説明

LLM が十分に賢くない。モデルが大きすぎる。指示の文章（プロンプト）が長い。

この分析の見方

長い入力を正しく判断できる手段が LLM しかないため、文章が要らない判断にまで、文章を作る時間と料金を払っている。[仮説]

左側の説明は、LLM そのもの（賢さ、大きさ、指示の長さ）に原因を求めている。右側のこの分析の見方は、LLM の使い方（文章が要らない判断にまで LLM を使っていること）に原因を求めている。原因の置き場所が変わると、解決策も「LLM を改良する」から「文章が要らない判断には LLM を使わない」に変わる。

症状から原因へのたどり方

下の図は、目に見える症状から、1段ずつ「なぜ」をたどったものである。

  1. 症状

    Agent の動きが遅く、料金が高い。[事実: LangChain blog]

  2. なぜ遅く、高いのか？
  3. 第1原因

    Agent が、判断のたびに LLM を呼んでいる。

  4. なぜ、判断のたびに LLM を呼ぶのか？
  5. 第1原因の理由

    長くて整理されていない入力を、十分に正しく判断できる手段が、LLM しかない。[仮説]

  6. LLM を呼ぶと、判断で何が起きるのか？
  7. 第2原因

    欲しい答えは billing のような選択肢1つなのに、LLM は文章を作るときと同じ方法で、トークンを1つずつ計算して答えを作る。

  8. なぜ、この無駄が今になって大きくなったのか？
  9. 構造原因

    AI の提供の形が、人との会話（Chat）に合わせて作られている。Agent が1つの作業で判断を何度も繰り返すようになり、この無駄が、判断の回数の分だけ積み重なるようになった。[推定]

  10. その結果、本当に解くべき問題は
  11. 本当の問題

    長い入力を LLM と同じくらい正しく判断し、しかも文章を作る時間と料金を払わずに答えを返す手段がない。[仮説: 第8章の検証1で確かめる]

図の5つの段のうち、「第1原因の理由」の段は、まだ確かめていない仮説である。この段が間違っていれば（長い入力でも分類器で十分に正しく判断できれば）、開発者は分類器を使えばよく、第2原因から先の無駄も生まれない。この章の問題の見方は、この1つの仮説に支えられている。

用語

構造原因

この文脈での意味
1回の失敗ではなく、製品の作られ方や市場の仕組みから、同じ無駄が繰り返し生まれる原因。

「AI の提供の形が Chat に合わせて作られている」ことが、判断のたびに文章を作る無駄を、どの Agent でも繰り返し生んでいる。

問い合わせ対応の Agent が、1件ごとに「担当」「緊急度」「返信の要否」の3つを判断する。1日に1,000件の問い合わせがあれば、Agent は1日に3,000回 LLM を呼ぶ。LLM は3,000回とも、答えの選択肢1つを、トークンを計算して作る。

この結論が間違いだとわかる条件

既存の分類器が、長くて整理されていない入力でも、LLM と同じくらい正しく判断できるとわかった場合、この問題の定義は成り立たない（第8章の検証1で確かめる）。

第4章

Jev はどんな反対の仮説を立てたか

粒度 1（標準）

分析の該当箇所: P3 反対仮説（Contrarian Thesis）

結論

TypeSafe AI は、「判断だけが必要な場合、文章を作ること自体が要らないのではないか」という、市場の常識と反対の仮説を立てた。TypeSafe AI が公表した数値は、料金と速さの証拠にはなるが、正しさが LLM と同じであることの証拠にはならない。

用語

反対の仮説

この文脈での意味
市場の多くの人が当たり前だと思っていること（第2章）の反対で、証拠によって正しいと示せるかもしれない考え。
例
下の図の右側の「文章を作ること自体が要らないのではないか」。
市場の常識（第2章の前提1）

AI の判断を得るには、LLM に文章を作らせる必要がある。

反対の仮説

判断だけが必要な場合、文章を作ること自体が要らないのではないか。

市場の常識は、「文章を作ること」を、判断を得るための手段だと考えている。反対の仮説は、判断だけが目的なら、文章を作る手順そのものを省けると考える。2つの考えの違いは、LLM の性能ではなく、判断を得るための手順にある。

公表された数値が示すこと、示さないこと

以下の数値は、TypeSafe AI 自身が公表した数値（自社公表値）であり、第三者が確かめたものではない。

数値数値が示すこと数値が示さないことラベル
入力100万トークンあたり 0.042ドルJev に渡す入力の料金が低いことを示す。Jev の答えが正しいかどうかは示さない。[事実: TypeSafe blog（自社公表値）]

  1. Jev の性質

    Jev は、答えとして文章を作らず、選択肢から答えを選ぶ。

  2. そのため
  3. 起きないこと

    LLM のような「作った文章の量（トークンの数）」が、Jev では生まれない。

  4. その結果
  5. 料金への影響

この図のうち、公表された事実は「出力の料金なし」だけである。「文章を作らないので、出力の料金が生まれない」というつながりは、公表された事実から、この分析が推定したものである。

例（仮の場面）

第0章の問い合わせの振り分けでは、LLM は "billing" という答えもトークンを計算して作るので、その分の出力の料金がかかる。Jev は答えの文章を作らないので、この出力の料金がかからない。

この結論が間違いだとわかる条件

同じ判断で、Jev の正解率が LLM より大きく低いとわかった場合、この仮説は「安く速いが、正しさで劣る」という意味にしかならず、Jev は LLM の代わりにならない（第8章の検証1）。

第5章

Jev は何を置き換え、何を置き換えないのか

粒度 1（標準）

分析の該当箇所: P4 敵の定義（Enemy）

結論

TypeSafe AI が置き換えようとしているのは、LLM そのものではない。TypeSafe AI は、「文章が要らない判断にまで、文章を作る AI を使う設計」だけを置き換え、文章が必要な場所では引き続き LLM を使う立場を取った。

用語

敵

この文脈での意味
製品が、顧客と一緒に置き換えようとする「古いやり方」。競合する企業のことではない。
例
「文章が要らない判断にまで、文章を作る AI を使う設計」。
置き換えるもの（敵）

文章が要らない場所にまで、文章を作る AI を使っている、今の AI の設計。

置き換えないもの（組み合わせる相手）

Claude や GPT などの LLM そのもの。文章が必要な場所では、開発者は引き続き LLM を使う。

2枚のカードの違いは、置き換える範囲にある。TypeSafe AI は、LLM 全体ではなく、LLM の使い方の一部だけを置き換える対象にした。そのため、TypeSafe AI は、LLM を提供する企業や、LLM を使っている開発者を、敵に回さずに済む。[推定]

Jev が入る位置

Jev は、Agent の判断の流れの中で、「LLM を呼ぶ必要があるか」を先に決める段階に入る。

Jev が判断すること

Agent から判断を求められた Jev が、選択肢から答えを選ぶ。その判断の1つとして、「この場面で LLM を呼ぶ必要があるか」も Jev が決める。

文章が要らない場合

Jev の答えで判断が終わる。Agent は LLM を呼ばない。

文章が必要な場合

Agent が LLM を呼び、LLM が文章を作る（例: 顧客への返信文）。

なぜ、LLM の利用が増えると、Jev の利用も増えるのか

  1. LLM を使って Agent を作る会社が増える。

  2. その結果

  3. Agent の中で、「LLM を呼ぶか」「どの選択肢を選ぶか」を決める判断の回数が増える。

  4. その結果

  5. 増えた判断が、Jev が使われる場面になる。[推定]

この図のつながりは、Jev が LLM を置き換えずに、LLM を呼ぶ前の段階に入ったから成り立つ。もし Jev が LLM を置き換える製品なら、LLM の利用が増えることは、Jev の利用が減ることを意味する。[推定]

例（仮の場面）

問い合わせ対応の Agent は、まず Jev に「この問い合わせに、文章での返信が必要か」を判断させる。Agent は、返信が必要なときだけ、LLM に返信文を書かせる。

この結論が間違いだとわかる条件

LLM の提供企業が、同じ判断の機能を、LLM の機能として安く提供した場合、この位置の価値は小さくなる（第7章のリスク）。

次の章へ → 次の章では、この位置で戦うために、TypeSafe AI がどの市場の名前で Jev を売ることにしたかを示す。

第6章

Jev は、どの市場として戦うことにしたか

粒度 1（標準）

分析の該当箇所: P6 市場定義の判定（Category Decision。判定のみ）

結論

TypeSafe AI は、Jev を既存の「分類器」や「小型の LLM」の一種として売らず、System One Model という新しい市場の名前を作った（新カテゴリー）。既存の枠で比べられると、第1章で残った違いが見えなくなるためである。[推定]

前提

市場カテゴリーは、買い手が製品を比べるときに使う、分類の名前である。買い手は、同じカテゴリーの製品どうしを、そのカテゴリーで当たり前になっている基準で比べる。例えば、「分類器」というカテゴリーでは、買い手は正解率と料金で比べる。

3つの選び方と、Jev の判定

選び方意味Jev の判定理由
A. 新カテゴリー新しい市場の名前を作り、その名前で比べてもらう。TypeSafe AI は、この選び方を取り、System One Model という名前を作った。[事実: TypeSafe]既存の枠では、第1章で残った違いが見えないためである。[推定]
B. サブカテゴリー既存の市場の中を、「○○向けの△△」のように区切る。TypeSafe AI は、この選び方を取らなかった。「軽量の LLM」「汎用の分類器」の一種として名乗ると、比べる基準が、既存の正解率と料金に戻るためである。[推定]
C. 再ポジショニング既存の市場の名前のまま、比べる基準の重みを変える。TypeSafe AI は、この選び方を取らなかった。既存の基準で Jev が勝てるかが、まだ確かめられていないためである。[推定]

3つの選び方の違いは、買い手が Jev を何と比べるかにある。A では、買い手は Jev を LLM と比べる。B と C では、買い手は Jev を既存の分類器や軽量の LLM と、正解率と料金で比べる。TypeSafe AI は、Jev の違いが見える比べ方になる A を選んだ。[推定]

  1. 買い手が、Jev を「分類器」の一種として見る。

  2. その結果

  3. 買い手は、既存の分類器と同じ基準（正解率と料金）で Jev を比べる。

  4. そのとき

  5. 分類器も文章を作らないので、「文章を作らない」ことは、Jev の違いにならない。

  6. そのため、違いとして残るのは

  7. 長い入力について、LLM と同じくらい正しく判断できることだけである。[仮説]

  8. しかし

  9. この違いは、正解率と料金を並べた比較表では見えにくい。[推定]

  10. その結果

  11. TypeSafe AI は新しい市場の名前を作り、Jev を分類器ではなく LLM と対比させて、比べてもらう形にした。[推定]

この図の中で、確かめられていないのは「長い入力について、LLM と同じくらい正しく判断できる」という段である。この段が間違っていれば、Jev に残る違いがなくなり、新しい市場の名前を作る理由もなくなる。

リスクの深刻さ

致命的（戦略の前提が崩れる問題）

該当する問題は見つからなかった。公開情報の範囲では、Jev は技術として動いており、公開から24時間以内に Vercel の有料チームの約13%が Jev を試した。[事実: Vercel]

重大（対策が必要な問題）
  1. Jev の宣伝の言葉「Zero Hallucinations（幻覚ゼロ）」は、誤解されるおそれがある。Hallucination（幻覚）とは、AI が事実と違う答えや、ありえない答えを作ることを指す。Jev は選択肢の外の答えを返さないので、その意味では宣伝は正しい。しかし、Jev が選択肢の中で間違ったものを選ぶことは、防げない。[推定]

注意（見張る必要がある点）
  1. 使い続けている割合と、有料に切り替えた割合は、調べた公開情報（TypeSafe AI の公式ブログとサイト、Vercel、DCVC の発表）の中には見つからなかった。利用者が Jev を使い続けるかは、まだ確かめられていない。[仮説]
  2. 大手が同じ機能を出した場合、Jev を守るものは、Vercel と LangChain への組み込みと、開発者の使い慣れに頼っている。Vercel の AI Gateway は、開発者が複数の LLM を1つの窓口から呼ぶためのサービスである。LangChain は、LLM を使うアプリを作るための部品の集まりである。[推定]

3つの段のうち、対策が必要なのは「重大」の2つである。2つの問題は、どちらも Jev の答えの正しさが示されていないことから生まれている。そのため、第8章の検証1（正しさの測定）の結果が、2つの重大な問題にまとめて答えることになる。[推定]

例（仮の場面）

正解が billing の問い合わせで、Jev が technical を選ぶ。technical は選択肢の中にあるので「幻覚」ではないが、答えとしては間違いである。「Zero Hallucinations」という言葉は、この種の間違いを防ぐとは言っていない。

大手（OpenAI、Anthropic、Google など）の直近の発表に、同じ機能が含まれていないかを、この分析では調べていない（第9章）。

第8章

次に何を確かめるか

粒度 1（標準）

結論

最初に、実際の業務の判断で、Jev が LLM と同じくらい正しく答えられるかを確かめる。この結果が、第1章の「残る違い」、第3章の「本当の問題」、第4章の「反対の仮説」のすべてを左右するためである。

検証1: 実際の業務で、LLM と同じくらい正しく答えられるか（優先度: 高）

用語

ベンチマーク

この文脈での意味
同じ課題とデータを使って、複数のモデルの結果を並べて比べる測定。
例
同じ1,000件の問い合わせを、Jev と大型の LLM の両方に振り分けさせ、正解の数を比べる（件数は説明のための仮置き）。
用語

確信度の較正（calibration）

この文脈での意味
モデルが示す「この答えが正しい確率」が、実際に正しい割合と一致しているかどうか。
例
モデルが「90%の確率で正しい」と示した答えを集めたとき、実際に約90%が正しければ、較正がとれている。
確かめること

仮説: 実際の業務の判断で、Jev は LLM と同じくらい正しく答えられる。

方法: 公開されているデータと顧客の実データで、最新の大型の LLM と Jev の正解率と料金を比べるベンチマークを作り、公開する。

成功なら

TypeSafe AI は、ベンチマークの結果を公開し、「ただの分類器」という批判への答えにする。

失敗なら

TypeSafe AI は、LLM との差が大きい用途を、Jev が得意だと主張する範囲から外し、伝え方と、議論を呼ぶ主張を直す。

この検証は、第1章の「残る違い」、第3章の「本当の問題」、第4章と第6章の仮説を、まとめて確かめる。TypeSafe AI が、成功と失敗のどちらの場合に何をするかを結果が出る前に決めてあるので、結果を都合よく解釈することを防げる。

検証2: 試したチームが、使い続けるか（優先度: 高）

TypeSafe AI は、使い続けなかったチームのうち10チームに理由を聞き、最初に売り込む顧客の条件（ICP）と、利用者が最初に価値を感じる瞬間の定義を見直す。

この検証は、Jev の API の形式が、他の会社にとっても標準になるかを確かめる。形式が標準になると、開発者はその形式を前提にコードを書くので、Jev から乗り換えにくくなる。[推定] 優先度が中なのは、この検証が外れても第1章から第6章の結論は崩れず、Jev を守る手段の1つが減るだけだからである。[推定]

結論

この分析で扱った9つの段階のうち、4つはまだ確かめられていない。確かめるには、TypeSafe AI の内部の数値と、先行事例の公式の資料が必要である。

分析の段階状態理由
情報の確認（P0 Intake）確認済み分析は、公開情報だけを使うことと、内部の数値がないことを、仮定として明記した。
先行事例の確認（P0.5）未検証分析は、主に二次資料で確認した。各製品の公式の説明書での確認と、調査の記録が残っている。
市場の当たり前（P1）未検証分析は、前提を公開情報から推定した。開発者の実際の作業の流れと、判断にかかっている今の費用は、公開情報からは得られない。
本当の問題（P2）未検証原因のたどり方は推定である。問題の中心（長い入力で LLM と同じくらい正しいか）は仮説であり、検証1で確かめる。[仮説]
反対の仮説（P3）未検証料金と速さの証拠は、TypeSafe AI 自身の公表値である。正しさが LLM と同じかは仮説であり、検証1で確かめる。[仮説]
置き換えるもの（P4）確認済みTypeSafe AI が LLM そのものを置き換えず、組み合わせる相手にしていることを確認した。
戦う市場（P6 判定のみ）確認済み判定を出した。判定の理由は、公開情報からの推定である。
弱いところ（P31）確認済み分析は、結論を否定する事実を探した。大手の直近の発表は、まだ調べていない。
次に確かめること（P32）確認済み分析は、優先度の高い順に3つの検証を決めた。

4つの未検証のうち、「本当の問題」と「反対の仮説」の2つは、第8章の検証1で確かめられる。「先行事例の確認」は各製品の公式の説明書を読むことで、「市場の当たり前」は開発者の作業の流れと費用のデータを集めることで確かめる。

確かめるために必要な情報

  • TypeSafe AI の、有料に切り替えた割合、使い続けている割合、利用量の推移が必要である。
  • Jev を使っている顧客の種類（ICP）と、その内訳が必要である。
  • 開発者の今の作業の流れと、判断にかかっている今の費用が必要である。
  • TypeSafe AI が Jev を提供する費用と、売上に占める利益の割合（粗利率）が必要である。
  • 構造化出力、zero-shot 分類器、小型の LLM について、公式の説明書での確認と、調査の記録（調べた日、期間、検索語）が必要である。
  • OpenAI、Anthropic、Google などの直近の発表に、同じ機能が含まれていないかの確認が必要である。
