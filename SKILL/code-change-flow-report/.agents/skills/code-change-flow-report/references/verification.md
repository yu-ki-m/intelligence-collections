# 検証項目

## 調査担当と独立検証

- 比較計画と実行状態が調査開始前に作成され、既存状態がある場合は未完了タスクだけを再開している。
- 各タスクの開始、終了、証跡SHA-256、再試行、無効化が状態ファイルへ原子的に保存されている。
- 同じ調査バッチに属する複数タスクの最初の試行について、開始から終了までの実行区間が実際に重なっている。
- 調整担当が、対象コミットと比較元を調査開始前に固定している。
- 各コミットを異なる調査タスクが担当している。
- 対象が複数コミットの場合、少なくとも2件の調査タスクを同じバッチで並列実行している。
- 各コミットを調査担当とは異なる検証タスクが検証している。
- 各検証タスクが会話履歴を継承しない新規コンテキストで開始されている。
- 検証担当が調査担当の思考過程、期待する結論、他コミットの結果を受け取っていない。
- 検証担当が、調査JSONの形式だけでなく、差分、呼び出し元、実行フロー、コード位置、説明をGitと実コードから再調査している。
- 検証担当が調査JSONを直接修正していない。
- 修正後は、直前の検証担当とは異なる検証タスクが新規コンテキストで再検証している。
- `requestedCommitOrder`、`orchestration.commits[]`、`commits[]`の件数、コミットID、順序が一致している。
- 対象Git参照、比較元、必要なスナップショット、調査結果を含む調査単位について、調査証跡、最終検証証跡、統合後データのSHA-256が一致している。
- 調査証跡と各検証証跡がレポートJSONと同じディレクトリ以下に実在する通常JSONファイルであり、タスクID、対象Git参照、比較元、スナップショット、状態、問題件数、SHA-256が実行記録と一致している。
- 未コミット差分では、開始時と生成直前のスナップショットSHA-256が一致している。
- 失敗した検証の後に再検証した場合、修正前後の調査単位SHA-256が異なっている。
- 最後の検証が`passed`、問題件数と未解決件数が0である。
- 失敗、タイムアウト、未完了の調査または検証が1件も残っていない。
- 実行状態に未完了タスク、未解決ブロッカー、再試行上限超過が残っていない。

## Gitとコード

- 各コミットが正しい親コミットと比較されている。
- 差分の各変更ハンクが少なくとも1つのテーブルへ含まれている。
- 各コミットの`steps`とすべての`calls[].steps`を再帰的に列挙し、全テーブルをファイル位置の照合対象にしている。
- `afterCode`が空でなければ対象コミット側、純粋な削除で`afterCode`が空なら親コミット側を表示位置の基準にしている。
- 各テーブルについて、表示基準のGit参照から`filePath`の実ファイルを取得し、`startLine`から`endLine`までを両端を含めて抽出している。
- 抽出したコードと表示基準側のコード断片が、改行コードと末尾改行1つを除いて完全一致している。インデント、空白行、行内の空白を無視していない。
- `endLine - startLine + 1`が表示基準側のコード断片の行数と一致している。
- `beforeCode`が空でなければ親コミット側、`afterCode`が空でなければ対象コミット側の実ファイルに、各コード断片が連続した行として存在している。
- ファイルの移動または名称変更がある場合、親側と対象側のパスをGitの名称変更検出で対応付けている。
- 不一致があった場合、実コード上の一意な位置または所属メソッドと前後のコードで対象を確定し、パス、行範囲、必要ならコード断片も修正している。
- ファイル位置の修正後に全テーブルを先頭から再照合し、未解決が0件になっている。
- ステップID、照合したGit参照、ファイルパス、行範囲、合否の作業記録がある。
- `analysisMode`が`callers`の各変更対象について、意味解析と別系統の検索を実行し、検出した呼び出し箇所IDを`evidence`へ記録している。
- 各探索根拠の呼び出し箇所IDと`callSites`が一致している。
- 未変更ステップの`beforeCode`と`afterCode`が一致している。
- 検証処理が未変更ステップなしと通知した場合は、入口から終点までを再調査している。未変更ステップが不要と判断した場合は、その根拠を最終回答へ記載する。

## 処理フロー

- 各1段目がControllerなどの実際の入口から始まっている。
- コミット先頭と各`connectFromPrevious: false`のステップに`flowTitle`があり、それ以外のステップにはない。
- 複数の第1階層テーブルまたは入れ子を含む処理フローに`flowDescription`があり、単独テーブルにはない。
- 入口から変更箇所まで、値と制御の受け渡しを追跡できる。
- 変更箇所からレスポンス、保存結果、イベントなどの終点までを追跡できる。
- 呼び出し先が`calls`内へ入り、戻り後の処理が親階層の次ステップへ戻っている。
- 各`[後続処理確認]`について、呼び出し元メソッドを呼び出し行から終了まで実コードで確認している。
- 呼び出し後の文がある場合、親階層の次テーブルが同じファイル・同じメソッドの後続行を示し、線で接続されている。
- 接続された後続テーブルがない場合、直接`return`、メソッド末尾、例外終了、非同期境界などの根拠を実コードで確認している。
- 実行上つながらない1段目に`connectFromPrevious: false`が設定されている。
- 各`included`が、同じフロー内の入口ステップ、呼び出し元ステップ、変更ステップを参照している。
- 複数の呼び出し元がある場合、呼び出し箇所ごとに異なる変更ステップが入れ子として配置されている。
- `excluded`にはコードに基づく除外理由があり、`unresolved`が残っていない。
- 変更と関係しないコードが表を埋める目的で追加されていない。

## 説明

- コミット概要、処理フロー説明、概説、変更理由、処理仕様、備考を`explanation-writing.md`先頭の原文プロンプトへ省略・要約・言い換えせず照合している。
- 各コミットの概要が最初の1〜2文で変更全体の結果を説明している。
- 最初の1〜2文を概要全体の文数制限として扱わず、必要な前提と変更箇所間の因果関係を説明している。
- 各コミットの概要が、必要な前提をその前提を使う説明より前に示している。説明に前提が不要な場合は、架空の前提を追加していない。
- 各コミットの概要が、原因、変更内容、結果を途中で飛ばさず、各変更が次の結果を生む理由を説明している。
- 抽象的な説明を使用した場合は直後に具体例があり、具体的な説明だけで完結する場合は例を機械的に追加していない。具体例へ`例えば`という語を強制していない。
- 各コミットの概要がファイル名、クラス名、メソッド名、変更件数の列挙だけで終わっていない。
- 概説の最初の1〜2文だけで変更または未変更ステップの役割を把握できる。
- 未変更ステップの概説が変更有無を繰り返さず、処理の役割や意味だけを説明している。
- 専門用語が最初に使われる箇所で説明されている。
- 各文に主体、対象、動作が記載されている。
- 原因、処理、結果の順序が飛んでいない。
- 抽象的な説明の直後に変数名、条件値、レスポンスなどの例がある。
- 「柔軟」「高度」「効率的」「最適化」などの形容を使う場合は、その語が示す測定可能な状態または具体的な処理を同じ箇所で説明している。
- 未変更ステップの変更理由欄が`変更なし`の5文字だけになっている。
- 処理仕様の最初に、その処理が業務データ、利用者、後続処理にとって持つ意味が説明されている。
- 各テーブルの処理仕様が、1〜2文の要点、2件以上の番号付き手順、抽象的な説明を使った場合の具体例に分かれている。具体例の導入語句を固定していない。
- 番号付き手順が実コードの順序と一致し、1項目につき1つの入力、判定、状態変化、呼び出し、戻り値または外部結果を説明している。
- 各番号が、主体、扱う値、動作、直後の結果を説明している。
- コードを隠して処理仕様だけを読んでも、前提、因果関係、観測できる結果を理解できる。
- 処理仕様がクラス名、メソッド名、変数名と呼び出し順の列挙だけで終わっていない。
- 変更箇所と周辺処理について、懸念点、バグ、考慮漏れの有無を確認している。
- 備考の指摘に`[懸念点]`、`[バグ]`、`[考慮漏れ]`の分類、コード上の根拠、発生条件、影響、必要な確認または対応がある。
- 追加確認が必要な内容をバグと断定せず、根拠のない指摘を作っていない。

## 生成物

次のコマンドが成功することを確認する。

```bash
bash <skill-root>/scripts/generate-report.sh \
  <review-data.json> <review-report.html> <run-state.json>
```

コマンド出力に`Run-state self-test passed`、`Completion readiness passed`、`Repository integrity passed`、`Orchestration self-test passed`、`Orchestration verification passed`、`Root section self-test passed`、`Specification structure self-test passed`、`Explanation input self-test passed`、`Code location structure passed`、`Caller coverage self-test passed`、`Caller coverage passed`、`Continuation structure self-test passed`、`Continuation structure passed`、`HTML verification passed`が含まれることを確認する。状態検査は、実Git参照と親、証跡の現在SHA-256、タスクの重複、実際の並列実行区間、再試行と修正上限、未解決ブロッカーを確認する。オーケストレーション検査は、コミットの欠落と順序、完全なGit参照、未コミット差分の固定、担当分離、満杯の並列バッチ、新規コンテキスト、実在する証跡、最終検証、未解決件数、調査単位のSHA-256を検査する。説明入力の構造検査は、空の概要を拒否し、特定の導入語句を要求しないことを検査する。処理仕様の構造検査は、要点、2件以上の手順、HTML側の連番、任意の具体例、具体例の導入語句を検査する。ファイル位置の構造検査は、開始行と終了行の順序、および表示基準側コードの行数との一致を検査する。実ファイルとの内容照合は、状態検査が全階層のテーブルに対してGitから実行する。第1階層検査はタイトルと説明の必須条件、単独テーブルの説明禁止、表示単位の境界を検査する。呼び出し元検査は複数呼び出し元、探索結果の未登録、変更ステップの不正共有、未解決、理由のない除外、探索方法の不足、同一箇所の重複登録を検出する。後続処理の構造検査は、接続された後続テーブルのファイルと行順を検査し、実コード・HTMLと照合する対象を`[後続処理確認]`として列挙する。

生成後は最終レビュー証跡を保存し、次のコマンドを成功させる。`completed`という状態名だけで合格させず、現在のGit、証跡、JSON、HTML、最終レビューSHA-256を再検査する。

最終レビュー証跡には担当タスクID、統合JSONのSHA-256、HTMLのSHA-256、コミットタブ、差分色、接続線、独立フロー、入れ子開閉、文章折り返し、説明文再照合の合否を記載し、すべてを合格にする。

```bash
node <skill-root>/scripts/manage-run-state.mjs assert-completed <run-state.json>
```

生成したHTMLについて次を確認する。

- HTMLが外部のCSS、JavaScript、画像、Web APIを参照せず、単体ファイルとして開ける。
- HTML生成後にサーバープロセスを残さず、ポートを待ち受けない。
- `code-change-flow-template-version`が`2026.09.13.3`である。
- コミットタブがコミット数と一致する。
- 各コミットの`概要`がコミット情報の直下かつ最初の比較表より前にある。
- 第1階層の各開始テーブルの直前にタイトルがあり、処理フローだけに説明が表示される。
- 第1階層のタイトルが比較表と同じ横幅を持ち、グレー背景と左罫線で他の領域から区別できる。
- コミット概要は240pxを超えた場合に縦スクロールし、印刷時は高さ制限を解除する。
- ファイル位置が`{ファイルパス}:{開始行}-{終了行}`の形式で表示される。
- 列が`解説`、`変更前`、`変更後`、`備考`の順であり、コード列が説明列の2倍の横幅である。
- 画面背景、比較表、コード欄、列タイトルの明度差によって、コミット、ファイル、各列の境界を判別できる。
- 選択中のコミットだけが青で強調され、差分を示す薄赤色と薄緑色が操作状態へ流用されていない。
- 比較表の二層の影が表の輪郭と背景からの分離を示し、印刷時には解除される。
- 表が内容に応じて縦方向へ伸縮し、処理仕様だけが536pxを超えた場合にスクロールする。
- 各処理仕様の手順がHTMLの番号付きリストとして表示され、番号が`1.`から連続している。
- 削除行に`-`と薄赤色、追加行に`+`と薄緑色が付く。
- 未変更行に差分色が付かない。
- 入れ子の矢印がファイルパス左側にあり、配下だけを開閉する。
- 親の縦線から子テーブル左端までの横線がすべての入れ子段にあり、線の先端に矢印がない。
- 縦の接続線が点線であり、呼び出し先テーブルの直前だけは前のテーブルの下端から横線へ到達するまで連続した実線である。
- 横線を通過した後に入れ子テーブルの横へ続く縦線が点線へ戻り、子テーブルへ張り出す横線が実線である。
- 入れ子を展開すると、呼び出し後の処理が子テーブルの終了後に親階層へ戻って表示され、親階層の接続線が後続テーブルまで続く。
- 独立した1段目の直前に接続線がない。
- タブ切り替え時にページ全体の横スクロール位置が変わらず、コミットタブ欄だけがスクロールする。
- コミット概要、概説、変更理由、処理仕様、備考が句点ごとに改行される。
- 印刷時にすべてのコミットと入れ子が展開される。

`scripts/generate-report.sh`は、HTML生成前に`scripts/verify-orchestration.mjs`、`scripts/validate-review-data.mjs`、`scripts/verify-caller-coverage.mjs`、`scripts/verify-continuation-structure.mjs`を実行し、生成後に`scripts/verify-generated-report.mjs`を実行する。`Orchestration verification passed`、`Code location structure passed`、`Caller coverage passed`、`Continuation structure passed`、`HTML verification passed`のいずれかが表示されない場合は、生成物を完成扱いにしない。最終回答には、調査担当数、検証担当数、並列バッチ数、再検証回数、実コードと照合したテーブル件数、修正件数、未解決件数、および後続処理を検証した呼び出し件数、後続あり件数、後続なし件数を記載する。
