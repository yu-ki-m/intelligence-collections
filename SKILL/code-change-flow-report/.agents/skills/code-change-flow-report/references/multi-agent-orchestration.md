# 複数エージェント実行規則

この資料は、コミットごとの調査を並列化し、調査担当とは別のエージェントが結果を独立検証するための必須手順を定義する。HTMLの生成処理自体は並列化せず、全コミットの検証完了後に調整担当が1回だけ実行する。

進捗、再試行、生成、完成判定は会話内の記憶ではなく、[中断耐性と完了ゲート](resumable-execution.md)の比較計画と状態ファイルで管理する。サブエージェントを起動する前に状態を初期化し、各タスクの開始前と終了後に状態を更新する。

## 役割

- `coordinator`: 対象コミット、比較元、順序、作業場所を確定し、担当を割り当てる。調査結果の本文は書かず、検証済みデータを順番どおりに統合する。
- `investigator`: 1つのコミットだけを調査し、そのコミットのJSON断片を作る。他コミットの結果を前提にしない。
- `verifier`: 1つのコミットだけを、Gitと実コードから再調査する。調査担当の結論を根拠にせず、合否と問題点を返す。

1コミットについて、`investigator`と`verifier`を同じエージェントまたは同じタスクに割り当ててはならない。コミットが1件だけの場合も、2つの役割を分離する。

## 起動時のコンテキスト契約

新しく起動する`investigator`、`verifier`、再検証担当、停止した担当の代替担当は、すべて会話履歴を継承しない。起動機能に`fork_turns`がある場合は、既定値へ任せず明示的に`none`を指定する。これは検証担当の独立性だけでなく、長い会話履歴をAPI入力へ重ねて送信しないための必須条件である。

各タスクの依頼文は、次の情報だけで構成する。

- `investigator`または`verifier`などの役割。
- 対象リポジトリの絶対パス。
- 1件の対象コミットと比較元の完全なGit参照。
- 利用者が明示した対象範囲、除外条件、出力条件がある場合は、それだけを記録した短いタスク概要のファイルパス。
- その役割が読む資料の絶対パス。
- 読み込む入力JSONがある場合は、その固有ファイルの絶対パス。
- 証跡とコミットJSONを書き込む固有の絶対パス。
- 完了時に、状態、出力パス、SHA-256だけを返す指示。

コード全文、差分全文、JSON本文、会話の要約、他コミットの結果を依頼文へ貼り付けない。利用者固有の条件を省略せず、必要な条件だけを短いタスク概要へ転記し、会話全体の代わりにそのパスを渡す。担当は必要な部分をファイルと読み取り専用Gitコマンドから段階的に取得する。成果物は指定ファイルへ原子的に保存し、応答本文へJSON全体やコード一覧を返さない。この契約は調査対象と検査項目を削減せず、APIへ送る重複データと応答ストリームだけを削減する。

## 1. 比較計画を固定する

調整担当はサブエージェントを起動する前に、対象を表示順で列挙する。各要素へ次を設定する。

- レポートへ表示するコミットID。
- `commit`または`working-tree`の対象種別。
- 対象コードを読む完全なGit参照。
- 比較元コードを読む完全なGit参照。
- 調査結果と検証結果を書き出す、コミット固有のパス。
- 調査バッチ番号。

通常コミットは第1親と比較する。ルートコミットはGitの空ツリーと比較する。マージコミットは親を複数持つため、選ぶ親によって説明が変わる場合、調整担当は比較元を推測せずユーザーへ確認する。

コミットでは、対象Git参照と比較元を40桁または64桁の完全なオブジェクトIDで記録する。レポート表示用の短縮コミットIDだけを比較計画に使わない。

未コミット差分は1つの疑似コミットとして扱う。調整担当は開始時の差分と対象ファイルからSHA-256スナップショットを作り、HTML生成前に同じ方法で再取得する。`initialSnapshotSha256`と`finalSnapshotSha256`が異なる場合は、途中の結果を使わず処理を停止する。

## 2. 調査エージェントを並列実行する

対象が複数コミットなら、利用可能なサブエージェント枠から調整担当の1枠を除いた範囲で、2件以上の調査を同時に開始する。各バッチは利用可能な枠を満たす件数で開始し、最後のバッチだけ残件数を使用する。利用可能な枠へ収まる調査を、理由なく複数バッチへ分けない。実行可能な調査枠が1件しかなく、対象が複数コミットの場合は、逐次処理へ黙って切り替えず実行不能として停止する。

各調査タスクは`fork_turns: none`相当で起動し、渡す情報を次に限定する。

- 対象リポジトリの場所。
- 対象コミットと比較元のGit参照。
- [処理フローの追跡](flow-tracing.md)、[JSON仕様](review-data-schema.md)、[説明文規則](explanation-writing.md)の場所。
- そのコミットだけの出力先。

他コミットの調査結果、期待する結論、別担当が疑っている問題は渡さない。各調査担当は、Controllerなどの入口、変更箇所までの未変更処理、呼び出し先、同じ階層へ戻った後続処理、戻り値または副作用までを調査する。複数の呼び出し元を検出した場合は、呼び出し元ごとに独立したフローを作る。

調査担当は共有ワークツリーのGit状態を変更しない。`git checkout`、`git switch`、一時ブランチへの切り替えを使わず、`git show <ref>:<path>`、`git diff <base> <target>`など、対象を明示した読み取り専用コマンドを使う。

1コミットに独立した入口が多数ある場合、調査担当は入口単位の補助タスクへ分割できる。ファイル単位には分割しない。コミット担当は補助タスクの結果を統合し、コミット全体の変更ハンクと呼び出し元が欠けていないことを確認する。

調査担当は、コミットJSONとは別に[JSON仕様](review-data-schema.md)の調査証跡JSONを自分の`artifactPath`へ保存する。証跡はレポートJSONと同じディレクトリ以下の通常JSONファイルとし、自分のタスクID、対象種別、対象Git参照、比較元、完了状態、調査単位のSHA-256を記載する。未コミット差分では固定したスナップショットも記載する。調整担当が代理で空の証跡を作らない。

## 3. 独立検証を実行する

調査結果が完成したコミットごとに、新しい検証エージェントを起動する。検証タスクは会話履歴を継承しない新規コンテキストを使う。エージェント起動機能に`fork_turns`相当の指定がある場合は`none`を指定する。

検証タスクへ渡す情報を次に限定する。調査JSONは依頼文へ展開せず、ファイルパスだけを渡す。

- 対象リポジトリの場所。
- 対象コミットと比較元のGit参照。
- 調査担当が出力したコミットJSON。
- [検証項目](verification.md)と、この資料の場所。
- 検証結果だけを書き出す固有のパス。

調査担当の思考過程、意図した正解、既知の疑い、他の検証結果は渡さない。検証担当はJSONの形式だけを確認せず、次をGitと実コードから再実行する。

1. 変更ファイルと変更ハンクを再取得する。
2. 呼び出し元を意味解析と別系統の検索で再探索する。
3. 入口から変更箇所、後続処理、終点までを再追跡する。
4. 全テーブルのパス、開始行、終了行、コード断片を再照合する。
5. `return`、例外終了、非同期境界と同一階層の後続処理を再判定する。
6. 説明がコードの逐語訳に留まらず、前提、意味、因果関係、外部から確認できる結果を説明しているか確認する。
7. 備考の懸念点、バグ、考慮漏れについて、分類とコード上の根拠を確認する。

検証担当は調査JSONを直接修正しない。検証担当は[JSON仕様](review-data-schema.md)の検証証跡JSONを、レポートJSONと同じディレクトリ以下にある自分専用の通常ファイルへ保存する。検証結果には自分のタスクID、対象種別、対象Git参照、比較元、`passed`または`failed`、新規コンテキストの使用、問題件数、問題ごとの対象ステップ、Git上の根拠、必要な修正、検証した調査単位のSHA-256を記録する。未コミット差分では固定したスナップショットも記載する。

## 4. 修正と再検証

検証が失敗した場合、調整担当は問題一覧を元の調査担当へ返し、同じ調査担当が利用可能なら、その隔離済みタスクへ追加依頼してコミットJSONを修正させる。この追加依頼は調査担当が持つ1コミット分の履歴を継続してよい。元の担当が終了して再開できない場合だけ、同じ`investigator`役割の代替担当を`fork_turns: none`相当で起動し、調査JSONと検証問題のファイルパスを渡す。検証担当自身へ修正を依頼しない。修正試行は実行状態へ重複しない試行IDで記録する。修正後は、過去の検証担当とは異なる新しい検証エージェントを、新規コンテキストで起動する。再検証は直前の検証より後のバッチ番号へ記録する。

1コミットにつき修正は比較計画の`maxCorrectionRounds`までとし、既定値は2回、機械検査が認める上限は20回とする。修正前に失敗した検証と、修正後の検証が同じSHA-256を記録している場合は、調査結果が修正されていないため停止する。上限回の修正後も問題が残る場合は`blocked`として状態へ保存し、HTMLを生成しない。ユーザーが続行を指示した場合は、未解決ブロッカーをすべて解消できる値へ上限を増やして同じ状態から再開する。

## 5. 統合と改変検出

各調査担当は、対象種別、対象Git参照、比較元、未コミット差分のスナップショット、コミットJSONを1つの調査単位としてキー順に正規化し、SHA-256を記録する。各検証担当も、自分が検証した同じ調査単位のSHA-256を記録する。最終検証のハッシュ、調査結果の最終ハッシュ、統合後の調査単位から再計算したハッシュが一致しなければならない。この構成により、検証後に比較元だけを差し替えた場合もハッシュが変わる。

調整担当は検証済みのコミットJSONを編集せず、`requestedCommitOrder`の順で統合する。文章や行番号を統合時に変更した場合は、そのコミットを未検証へ戻し、別の検証担当による再検証を実施する。

レポートJSONには、[JSON仕様](review-data-schema.md)の`orchestration`を必須で記録する。生成前に`scripts/verify-orchestration.mjs`を実行し、次の条件を機械的に確認する。

- 対象コミットに欠落、重複、順序違いがない。
- 各コミットの調査タスクと検証タスクが異なる。
- 複数コミットの調査が利用可能な枠を満たすバッチで並列実行されている。
- 最後の検証が`passed`で、未解決件数が0件である。
- 検証したデータと統合したデータのSHA-256が一致する。
- 調査証跡と検証証跡が実在し、その内容が実行記録と一致する。

## 6. 実行不能と失敗時の扱い

次のいずれかに該当する間はHTMLを生成しない。比較元や権限など自動解決できない条件は`blocked`へ保存する。タスクの一時失敗、タイムアウト、担当コンテキストの終了は、`maxWorkerAttempts`の範囲で未完了タスクだけを再実行する。

- サブエージェント機能を利用できない。
- 複数コミットに対して2件以上の調査を同時実行できない。
- 調査担当と独立した検証担当を割り当てられない。
- 比較元を確定できない。
- 調査または検証タスクが再試行上限まで失敗、タイムアウト、未完了になった。
- `unresolved`の呼び出し元、コード位置、検証問題が残っている。
- ハッシュが一致しない。

一部コミットだけを含むHTMLを完成品として出力しない。状態が`completed`になるまでは完成を報告せず、次の呼び出し時に状態ファイルから続ける。最終的にユーザーへ渡す成果物はHTMLだけとし、調査JSON、検証JSON、実行記録は内部作業物として扱う。

### APIタイムアウト時の再試行

エージェント起動または結果取得がAPIタイムアウトになった場合、調整担当は同じタスクを直ちに重複起動しない。利用可能なエージェント状態確認機能で、元の担当が`working`、`completed`、`failed`のどれにあるか確認する。

- 元の担当が実行中なら、その担当を待ち、新しい担当を起動しない。
- 元の担当が完了し証跡が存在するなら、証跡を検査して`finish-task`へ記録する。
- 元の担当が終了し証跡がない場合は、`finish-task`または`recover-task`へ`api-timeout:`で始まる具体的理由を記録する。
- 元の担当が終了し証跡が存在しても、JSONの読込みまたは`finish-task`の証跡検査が失敗した場合は、検査エラーと証跡パスを`finish-task ... failed`の理由へ記録して実行中状態を解消する。不正な証跡を成功記録へ使用しない。
- 調整担当が制御できる再試行では、2回目の前に5秒以上、3回目の前に15秒以上の間隔を置く。待機中に完了した別タスクの結果を先に回収してよい。
- 再試行は新しいタスクIDと`fork_turns: none`相当を使用し、同じコミット固有の入力ファイルを再利用する。失敗した応答本文や会話履歴を次の依頼文へ追加しない。
- `maxWorkerAttempts`の既定値は3のまま維持し、APIタイムアウトも有界な1試行として記録する。検証NGの`maxCorrectionRounds`へは算入しない。3回失敗した場合は自動再試行せず`blocked`にする。利用者が明示的に続行を指示した場合だけ、既存の`resume`規則に従って20以下へ上限を増やせる。

初回調査は、成否にかかわらず同じバッチの別コミットと実行区間を重ねる。初回に並列起動した担当の一部だけがタイムアウトした場合は、成功済みコミットを無意味に再調査せず、失敗したコミットだけを再試行してよい。この対象限定の再試行は逐次調査への切り替えとは扱わない。コミット単位の担当分離、検証担当の独立性、全検査、HTML非公開条件は維持し、初回からの逐次調査、検証省略、対象範囲の縮小、未検証結果の統合を復旧策として使用しない。

このスキルは、ベクトルデータベース、Embedding API、RAG用データベースを要求しない。SQL、Repository、マイグレーションなどが実行フローに含まれる場合は、通常のソースファイルとして必要な範囲だけを調査する。
