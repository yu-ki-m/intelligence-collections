# Codebase Guide

## 目的

リポジトリの内容をブラウザだけで読める静的HTMLへ変換する。
さらに、依頼文に合わせて、読むべきコードを順にたどれる「ガイド」を生成する。

AIが1ファイルずつ本文を読み込んでHTMLを書かない。ファイル列挙、読み込み、HTMLエスケープ、ページ生成、リンク生成、定義リンクの解析、差分の解析、全体図の配置はスクリプトに任せる。AIは、どこを読むかを決め、解説と指摘を書くことに専念する。

## 実行モード

| スキルの引数 | モード |
|---|---|
| 依頼文が無い | 通常生成。リポジトリ全体を `.codebase-guide-out/` に変換する。 |
| 依頼文がある（例: `main...HEAD の差分をレビューしたい`、`POST /templates の処理の流れを知りたい`） | ガイド生成。`.codebase-guide-out/` が無い、または古い場合は、通常生成も自動で行う。 |

## 出力仕様

リポジトリルートに `.codebase-guide-out/` を生成する。

例:

```text
repository/
├─ src/
│  ├─ index.ts
│  └─ app/service.ts
└─ .codebase-guide-out/
   ├─ フォルダーツリー.html
   ├─ .codebase-guide.json   … 通常生成の記録（ファイル一覧と除外設定）
   ├─ .codebase-guide-xref.json … 定義リンクの記録（ガイドのページにも同じリンクを付けるために使う）
   ├─ src/
   │  ├─ index.ts.html
   │  └─ app/
   │     └─ service.ts.html
   └─ ガイド/
      └─ <ガイド名>/
         ├─ 表紙.html                  … 要約・指摘の一覧・ルート・全体図・共通のステップ・変更箇所・ステップの一覧・未確認事項
         ├─ src/app/service.ts.html    … 注釈付きのコードページ（順路に出てくるファイルと、差分の変更ファイル）
         ├─ guide.json                 … AIが書く入力
         ├─ guide.brief.md             … 下準備メモ
         └─ guide.meta.json
```

必須条件:

1. 元ファイルの相対ディレクトリ構造を `.codebase-guide-out/` 配下に保持する。
2. 元ファイル名の末尾に `.html` を追加する。`index.ts` は `index.ts.html` とする。
3. `フォルダーツリー.html` はリポジトリ全体の階層を表示し、各ファイル名を対応する変換HTMLへのリンクにする。ガイドがある場合は、ガイドの一覧も表示する。
4. 各コードページはVS Code風のダークUIとし、次を表示する。
   - ファイル名
   - リポジトリルートからの相対パス
   - 行番号
   - コード本文
   - シンタックスハイライト（キーワード、文字列、数値、コメント、関数名等）
   - 左側のExplorer風ツリー（iframeを使わず、各ページに直接埋め込む）
5. Explorerのファイルリンクから別ファイルへ移動できるようにする。
6. シンタックスハイライトは生成時にHTMLへ埋め込み、ブラウザ表示時に外部CDNやnpmパッケージを必要としない。TypeScript/JavaScript、Java/Kotlin、Python、Go、Rust、C/C++/C#、Shell、SQL、JSON、YAML/TOML/INI/Properties、HTML/XML、CSS系、Markdown、GraphQLを少なくとも識別する。
7. `.git/` と生成先 `.codebase-guide-out/` 自身は必ず変換対象から除外する。
8. Gitリポジトリでは、原則として `git ls-files -co --exclude-standard` を利用し、`.gitignore` 等でignoreされたファイルを変換しない。
9. `.gitignore` に書かれていなくても、依存ライブラリ、ビルド成果物、キャッシュ、テスト出力、ローカル状態など、一般にソースコード閲覧対象ではないものをデフォルト除外する。
10. デフォルト除外の代表例は次の通り。
   - 依存: `node_modules/`, `vendor/`, `.venv/`, `venv/`, `env/`, `__pypackages__/`
   - ビルド: `dist/`, `build/`, `out/`, `target/`, `bin/`, `obj/`, `.next/`, `.nuxt/`, `.output/`, `.svelte-kit/`, `.astro/`
   - キャッシュ: `.cache/`, `.parcel-cache/`, `.turbo/`, `.nx/`, `.vite/`, `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`, `__pycache__/`, `.gradle/`, `.m2/`
   - テスト出力: `coverage/`, `htmlcov/`, `test-results/`, `playwright-report/`, `allure-results/`, `allure-report/`
   - IaC/ローカル状態: `.terraform/`, `.serverless/`, `.aws-sam/`, `cdk.out/`, `terraform.tfstate*`
   - IDE/AIツール: `.vscode/`, `.idea/`, `.vs/`, `.cursor/`, `.continue/`, `.codex/`, `.claude/cache/`
   - その他生成物: `generated/`, `gen/`, `docs/generated/`, `storybook-static/`, `.docusaurus/`, `site/`, `.npm/`, `.pnpm-store/`, `.yarn/cache/`, `.yarn/unplugged/`, `tmp/`, `temp/`, `logs/`
   - 旧バージョン（repository-html-browser）の出力先: `html-code/`
   - ファイル: lockファイル、source map、minified JS/CSS、コンパイル済みバイナリ、アーカイブ、画像・動画・フォント等
11. デフォルト除外を意図的に含めたい場合は `--include-dir <ディレクトリ名>` または `--include-file <ファイル名または相対パス>` を利用する。これらは複数回指定できる。`.git/` と `.codebase-guide-out/` は例外指定でも含めない。
12. ignore済みファイルまで列挙する必要がある場合だけ `--include-ignored` を使う。ただし固定のデフォルト除外は引き続き適用する。
13. Gitが利用できない場合はファイルシステム走査へフォールバックする。この場合も固定のデフォルト除外を適用する。
14. デフォルト除外されていないバイナリファイルが存在した場合は、ツリーから消さず、バイナリ用HTMLページを作り「バイナリのため本文表示対象外」と表示する。
15. シンボリックリンクはリンク先を展開せず、シンボリックリンクとしてページを生成する。
16. 通常生成をやり直しても、`.codebase-guide-out/ガイド/` は消さない。
17. TypeScript / JavaScript / Java のコードページでは、識別子を定義の行へのリンクにする（定義リンク）。
   - 定義の場所は、各言語のコンパイラーに問い合わせて求める。名前の一致で推測しない。
     - TypeScript / JavaScript: 対象リポジトリにインストール済みの TypeScript のコンパイラー。`tsconfig.json`（`jsconfig.json`、`tsconfig.*.json` を含む）ごとに解析し、どの設定にも含まれないファイルは既定の設定で解析する。
     - Java: JDK（17 以降）に標準で入っているコンパイラーの API（`scripts/lib/JavaXref.java` を `java` で直接動かす。ビルドや追加のライブラリは不要）。依存ライブラリ（Maven / Gradle の依存）は読み込まない。
   - リンクするのは、クラス・インターフェース・型・列挙型（とその定数）・レコード・関数・メソッド・プロパティ（フィールド）・モジュール直下の変数と、TypeScript / JavaScript の import のパス（そのファイルの先頭へ）。引数・ローカル変数・型引数はリンクしない。
   - 定義がリポジトリ内（コードページのあるファイル）にあるものだけをリンクする。`node_modules`・標準ライブラリ（JDK を含む）・依存ライブラリ・生成物の定義や、外部の型をリポジトリ内で拡張しているだけのもの（`declare module 'fastify' { … }` など）はリンクしない。型が `any` や読み込めない型で定義を決められないものもリンクしない。
   - `declare module '*.vue'` のような型だけの宣言で解決される import は、宣言ではなく実際のファイル（`.vue` など）の先頭へリンクする。
   - Java は依存ライブラリを読み込まないので、解決先が変わりうるものはリンクしない。
     - 読み込めない import と同じ名前の型（同じパッケージの別のクラスに解決されていることがある）。
     - 親クラス・インターフェースが読み込めないクラスの中で、そのクラス自身以外に定義された名前（読み込めない親から受け継ぐ同じ名前が隠れているかもしれない）。そのクラスの型を受け手にしたメソッド呼び出しは、引数の型が引数宣言と完全に同じものだけをリンクする。
     - Lombok などが生成するメソッド（ソースに定義が無い）。
     - 引数の型が読み込めない呼び出しは、引数の数が合うオーバーロードをすべて候補にする。
     - 同じ完全修飾名のクラスが複数のモジュール（`pom.xml` / `build.gradle` のあるフォルダー）にある場合は、モジュールごとに解析する（モジュールをまたぐリンクは付けない）。
   - 別のファイルの定義は別タブで開き、同じファイル内はそのページの中で移動する。定義の候補が複数ある場合（ユニオン型のプロパティ、オーバーロードの候補など）は、押すと候補の一覧を出す。
   - 圧縮されたコード（1行が3000文字を超える、または2MBを超えるファイル）は解析しない。`.vue` / `.svelte` の中身と、その他の言語（Kotlin・Python など）には付けない。
   - TypeScript と Java の解析は、ページの書き出しと並行して別スレッド・別プロセスで行う。
   - `typescript` や JDK が見つからない場合や解析が失敗した場合は、その言語にリンクを付けずに生成を続け、理由を出力する。

## 通常生成

### 実行手順

リポジトリルートを現在ディレクトリにして次を実行する。

```bash
node .claude/skills/codebase-guide/scripts/generate-html-code.mjs
```

このスキル自体が別の場所にある場合は、スクリプトの絶対パスを使い、対象リポジトリを `--root` で渡す。

```bash
node /path/to/generate-html-code.mjs --root /path/to/repository
```

必要に応じて並列数を指定する。

```bash
node .claude/skills/codebase-guide/scripts/generate-html-code.mjs --concurrency 32
```

デフォルト除外されたものを個別に含める場合:

```bash
node .claude/skills/codebase-guide/scripts/generate-html-code.mjs \
  --include-dir .vscode \
  --include-file package-lock.json
```

`.gitignore` 等でignoreされたファイルも確認対象にする場合:

```bash
node .claude/skills/codebase-guide/scripts/generate-html-code.mjs --include-ignored
```

定義リンクは、TypeScript / JavaScript には対象リポジトリ（またはその `tsconfig.json` のあるフォルダー）の `node_modules/typescript`、無ければグローバルにインストールされた `typescript` を使う。Java には `JAVA_HOME` の `java`、無ければ PATH の `java`（JDK 17 以降）を使う。別の場所にあるものを使う場合と、定義リンクを付けない場合:

```bash
node .claude/skills/codebase-guide/scripts/generate-html-code.mjs --typescript /path/to/node_modules/typescript
node .claude/skills/codebase-guide/scripts/generate-html-code.mjs --java /path/to/jdk/bin/java
node .claude/skills/codebase-guide/scripts/generate-html-code.mjs --no-xref
```

指定した `--no-xref`・`--typescript`・`--java` は記録され、ガイド生成の前に通常生成をやり直すときにも引き継ぐ。

### Claude Codeが行うこと

1. 対象リポジトリのルートを確定する。
2. スクリプトを実行する。
3. スクリプト終了コードが0であることを確認する。
4. `.codebase-guide-out/フォルダーツリー.html` が存在することを確認する。
5. スクリプトが出力した件数サマリを確認する。
6. 列挙された対象ファイル数と生成HTML数が一致していることを確認する。
7. 代表として最低3件を検証する。
   - ルート直下のファイル
   - 2階層以上深いファイル
   - 日本語または空白などURLエンコードが必要な名前を含むファイル（存在する場合）
8. 欠落がある場合、AIが手作業でHTMLを補完せず、原因を特定してスクリプトを修正して再生成する。
9. 出力の `Definition links` を確認し、ユーザーへ定義リンクの件数を伝える。`なし` の場合は理由をそのまま伝える。`typescript` や JDK が見つからない場合も、依存パッケージや JDK のインストール（`npm install` など）はユーザーの了承なしに行わない。

## ガイド生成

依頼文に合わせて、入口から関係するコードまでの順路、各ステップの解説、全体図を作る。
レビュー依頼の場合は、指摘（バグ・懸念・改善）も加える。

入口（エンドポイント・画面の操作・初期表示など）ごとに「ルート」を作り、ルートを切り替えて読めるようにする。ルートの中身はスクリプトが steps から組み立てる（AIは入口と呼び出し元を書くだけ）。

- 表紙: ルートの一覧（通るステップを番号で並べ、途中の終わりと「ルートN へ続く」を示す）、全体図（ルートを選ぶとその流れを強調）、共通のステップ（2つ以上のルートが通るステップ）。指摘は、ルートごとに分けずガイド全体で1つの一覧にし、「通るルート」を付ける。
- コードページのサイドバー: 「ルートで読む」の枠（ルートの選択・コールスタック・順路・前へ／次へ。選んだルートだけが対象）と、「ガイド全体」の枠（指摘と差分。全件）に分ける。選んだルートは、ほかのページへ移っても引き継ぐ。
- 解説・指摘: 閉じた状態で始め、行番号の横の番号（解説）や印（指摘）を押すと開く。もう一度押すか × で閉じる。サイドバーやキー操作で移ったときは開かない（指摘へ移ったときは、その印を強調する）。「すべて開く」「すべて閉じる」も置く。

差分が対象のガイドでは、どこにどういう差があるかを、スクリプトが次のように示す（AIは書かない）。

- コードページ: 削除した行・変更前の行を赤と「−」、追加した行・変更後の行を緑と「+」で並べる。変更の行は、変更前の行と比べて変わった部分を濃い色にする。ステップや指摘を選んだときの強調は行番号の側に出し、差分の色を上書きしない。
- サイドバーの「差分」（「ガイド全体」の枠）: 変更箇所をファイルごとに並べ、どのステップ・ルートに含まれるか（含まれなければ「順路外」）を示す。`]` / `[` で次・前の変更へ移る（ファイルをまたぐ）。
- 解説: 差分を含むステップに、そのステップの変更行数と、変更箇所へのリンクを付ける。
- 表紙の「変更箇所」: 変更ファイルごとに、変更箇所の場所・種類（追加・変更・削除）・変更前後の行・含まれるステップと指摘を並べる。
- 順路に無い変更ファイルにも、差分を見るためのページを作る（200 ファイルまで）。削除されたファイル・バイナリ・圧縮されたコードは、表紙の一覧に理由と一緒に載せるだけにする。

### 役割分担

| 作業 | 担当 |
|---|---|
| 依頼文の解釈（ガイド名、差分の範囲、レビュー依頼かどうか） | AI |
| `.codebase-guide-out/` の有無と鮮度の確認、必要なら通常生成 | `prepare-guide.mjs` |
| 変更ファイル・変更行・変更を含む関数・呼び出し候補・入口の候補（変更箇所から呼び出し元をさかのぼった候補を含む）の抽出 | `prepare-guide.mjs` |
| 読むコードの選定と、呼び出し関係の確認 | AI（下準備メモの候補を起点に、必要な範囲だけ読む） |
| 順路・解説・指摘・要約を `guide.json` に書く | AI |
| guide.json の検査、アンカーから行番号への変換、差分の行の表示、全体図の配置、定義リンク、HTMLの生成、リンクの検査、フォルダーツリーの更新 | `build-guide.mjs` |

### 手順

1. 依頼文から次を決める。
   - ガイド名: 短く、内容が分かる名前（例: `POST-templates-レビュー`）。
   - 差分の範囲（`--diff`）: 依頼文にコミット・ブランチ・PRの範囲があればそれを使う（`main...HEAD`、`HEAD~1..HEAD`、`<コミット>`）。「今の変更」「未コミットの変更」なら `working`。差分が対象なのに範囲を特定できない場合だけ、ユーザーに確認する。差分が対象でなければ指定しない。PR番号だけが渡された場合は、`gh pr view` などで比較元と比較先を調べて範囲にする。
   - レビュー依頼かどうか: 「レビュー」「指摘」「問題がないか」などを含む依頼はレビュー依頼とする。
2. 下準備を実行する。

   ```bash
   node .claude/skills/codebase-guide/scripts/prepare-guide.mjs \
     --request "<依頼文>" --name "<ガイド名>" [--diff "<範囲>"]
   ```

   - 依頼文が長い場合は、ファイルに書いて `--request-file <ファイル>` で渡す。
   - スキルが別の場所にある場合は、スクリプトの絶対パスを使い、`--root` で対象リポジトリを渡す。
   - 出力（`guide.brief.md` にも保存される）に、変更行、変更を含む関数、呼び出し候補、入口の候補、`guide.json` の場所が出る。
3. 下準備メモの候補を起点に、必要な範囲だけを Read / Grep で読む。全ファイルを順に読まない。呼び出し候補は名前の一致による推定なので、呼び出し関係はコードで確かめる。
   - 順路は入口（ボタン操作・画面の初期表示・エンドポイントなど、処理のきっかけ）から始める。差分が対象なら、下準備メモの「変更箇所からさかのぼった入口の候補」を起点に、入口から変更箇所までのつながりをコードで確かめる。
   - レビュー依頼では、順路の各ステップの関数全体と、そこから呼ぶ入力の検証・共通処理の中身も読む。差分が対象なら、順路に乗らない変更箇所（下準備メモの「変更を含む関数」）もすべて読む。
4. [guide.json の書式と書き方](references/guide-format.md) を読み、`guide.json` に `title`・`summary`・`steps`・`notes` を書く。`review` は手順1の判断に合わせる。
5. ガイドを生成する。

   ```bash
   node .claude/skills/codebase-guide/scripts/build-guide.mjs --name "<ガイド名>"
   ```

   - guide.json に問題があると、項目ごとの理由を出して終了コード1で終わる（例: アンカーが複数行に一致する、レビュー依頼でないのに指摘がある、順路が入口から始まっていない、呼び出し元より先に呼び出し先が並んでいる）。guide.json を直して再実行する。
   - ガイドのコードページにも定義リンクを付ける。リンク先は、ガイドにあるファイルならガイドのページ、それ以外は通常のページになる。定義リンクは作業ツリーの内容から求めているので、差分の比較先が作業ツリーと違う内容のファイル（例: 未コミットの変更があるファイルを、コミット同士の差分で見る場合）のページには付けない（行番号がずれた誤ったリンクを出さないため）。
6. 終了コードが0で、出力の `Links checked` のリンク切れが0件であることを確認する。
7. ユーザーへ、`表紙.html` のパス、ルートの数（出力の `Routes`）、ステップ数、指摘の件数（種類別）、未確認事項の件数、定義リンクの件数（出力の `Definition links`。付けなかったファイルがあればその理由も）を伝える。差分が対象なら、変更箇所の数と、そのうち順路の外にある数（出力の `Changes`）も伝える。

### 解説と指摘の書き方

詳しくは [guide.json の書式と書き方](references/guide-format.md) に従う。要点は次の通り。

- 指摘はレビュー依頼のとき（`review: true`）だけ書く。レビュー依頼でなければ、解説だけにする。
- 指摘の種類は、指摘（バグ）・指摘（懸念）・指摘（改善）。バグは、特定の入力や状態で誤動作することをコードから示せるものに限る。
- レビューでは、読んだ範囲ごとに観点の一覧（入力、エラー処理、境界と状態、データの整合性、認証・認可、セキュリティ、性能、運用、保守性）を全部確かめる。
- 件数の目安は無い。見つけたものは全部書く。同じ種類の問題が複数の場所にあれば、場所ごとに1件ずつ書く。
- 確かめられないことは推測で埋めない。安全だとコードから確かめられない箇所は指摘（懸念）に、読解上の不明点は `unverified`（未確認事項）に書く。
- 順路は入口から始め、実行される順に並べる。差分やレビューでも、変更箇所（定数・設定値など）から始めず、入口から変更箇所までをつなぐ。
- 変更箇所や依頼の対象にたどり着く入口は、全部ステップ（`kind: "entry"`）にする。入口ごとにルートになる。画面の操作からエンドポイントへ続く場合は、両方を入口にし、API を呼ぶステップの `branches` の `to` でエンドポイントにつなぐ。
- 複数の入口から通る処理は、ステップを複製せず `parent` に呼び出し元を全部書く。同じステップから呼ばれるステップどうしは steps の並び順が呼ばれる順になるので、共通の処理は、各ルートでそれより先に呼ばれる処理の後ろに置く。呼び出し元を確かめられなかったステップは、入口にせず `callerUnknown` に理由を書く。
- エラーで途中で終わる流れは、ルートを分けず、`to` の無い `branches` で示す。ルートの名前・グループ・終わり方を指定したいときだけ `routes` を書く。
- 常体（だ・である）で、何が・どこで・どうなるかを具体的に書く。

## 禁止事項

- Claudeが各ソースファイル本文を順番に読み、HTMLを1件ずつ手書きしない。
- ガイドのHTMLを手で書いたり直したりしない。変えたい内容は guide.json を直して `build-guide.mjs` で作り直す。見た目を変える場合はスクリプトを直す。
- `find` の結果をそのまま大量にプロンプトへ読み込まない。
- `.git/` 内部オブジェクトを変換しない。
- `.codebase-guide-out/` を再帰的に変換しない。
- ソースコードとして通常確認すべきファイルを安易な拡張子判定だけで除外しない。
- デフォルト除外一覧を変更する場合は、依存物・生成物・キャッシュ等である根拠を持つ。
- デフォルト除外対象ではないバイナリファイルを「存在しなかったこと」にしない。
- レビュー依頼でないのに指摘を書かない。
- 呼び出し関係を名前の一致だけで決めない。確かめられない箇所を、もっともらしい推測でつながない。
- 順路を、変更箇所や定数から始めない。
- 変更箇所や依頼の対象にたどり着く入口を、ステップにせず要約だけで済ませない（入口ごとのルートが欠ける）。
- 呼び出し元が分からないステップを、入口（`kind: "entry"`）にしない。`callerUnknown` に理由を書く。
- レビューの指摘を、件数を減らすためにまとめたり省いたりしない。
- 定義リンクを、名前の一致や正規表現で補わない。コンパイラー（TypeScript / JDK）で決められないものは、リンクを付けないままにする。

## 完了条件

通常生成は、次のすべてを満たした場合のみ完了とする。

- `.codebase-guide-out/` がリポジトリルート直下に存在する。
- `.codebase-guide-out/フォルダーツリー.html` が存在する。
- 対象となった全ファイルに対応する `.html` が存在する。
- 出力側の相対ディレクトリ構造が元リポジトリと一致する。
- `フォルダーツリー.html` の全ファイルリンクが対応ページを指す。
- 対応言語のコードページでシンタックスハイライト用のトークンクラスが生成される。
- 生成処理がエラー0件で終了している。
- 定義リンクの件数、または付けなかった理由をユーザーへ伝えている。

ガイド生成は、次のすべてを満たした場合のみ完了とする。

- `build-guide.mjs` が終了コード0で終わり、リンク切れが0件である。
- `.codebase-guide-out/ガイド/<ガイド名>/表紙.html` が存在し、`フォルダーツリー.html` のガイド一覧に載っている。
- 順路が入口（ボタン操作・画面の初期表示・エンドポイントなど、処理のきっかけ）から始まり、実行される順に並び、依頼に答えるのに必要なステップを含む。差分・レビューでも、変更箇所は入口からの流れの中に置いている。
- 変更箇所や依頼の対象にたどり着く入口が全部ステップになっていて、入口ごとのルートで読める。
- レビュー依頼の場合は、順路の各ステップの関数全体と差分のすべての変更箇所を、観点の一覧で確かめたうえで指摘を書いている（件数の目安は無い。問題が無ければ0件でよい）。
- 確かめられなかった事項を、未確認事項として残している。
