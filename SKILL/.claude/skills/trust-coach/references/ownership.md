# 主体性・責任水準ガイド（Trust Coach）

## 信頼される人のオーナーシップ

信頼とは「気づいたことを丁寧に報告すること」ではない。役割に相応しい探索・判断案形成・利害調整・実行・結果検証まで行い、周囲が安心して任せられる状態を作ること。報告は成果そのものではなく、連携手段の一つ。

### 期待水準の目安（肩書で機械的に決めない）

| 水準 | 自ら実施すべきこと | 相談・決裁すること |
|---|---|---|
| 指示を受けた担当者 | 症状整理、再現、直接影響の確認、問題提起 | 優先度や追加調査範囲を調整 |
| 主担当エンジニア | 直接・間接影響、既存仕様とデータ、類似問題、修正選択肢、推奨方針 | スコープや優先度が権限外なら決裁依頼 |
| シニア／技術リード | システム横断リスク、顧客影響、予防策、関係者調整、実施・検証の主導 | 経営・プロダクト上のトレードオフを決裁依頼 |
| 開発リーダー | 担当の割当て、調査統括、納期と資源の再計画、横断的なリスク管理 | 予算・製品方針・重大な契約変更などを決裁依頼 |
| PO | 顧客価値と優先順位、受容リスク、対外説明の責任、成果検証 | 技術的実現方法は開発側の専門判断を尊重し、組織の権限外は調整 |

同一人物が複数水準を兼務することもある。ポジションではなく、その案件の責任分担・権限・期待を確認して評価する。

## 既存バグ発見の標準ケース

例：「本番で区分外の値がバリデーションを通るようだ」。初期状態で分からないのは、実被害、入力経路、保存可否、仕様意図、影響箇所、本人の立場・調査権限。

### 提案前に聞くべきこと
- 発見者はこのシステムのどの責任を持つか（担当開発者、技術リード、開発リーダー、PO等）。
- 症状の確認確度、外部公開の有無、緊急性、アクセス可能なコード・仕様・検証環境。
- 誰かがすでに調査・対応しているか。社内インシデント手順はあるか。

### 権限と安全が許す範囲で自ら形成する成果物
1. **再現と仕様根拠**：期待値、実際値、再現手順、従来仕様と互換性要件。
2. **侵入経路とデータ**：UI/API/バッチ/連携、永続化可否、既存データ、読み取り権限と安全確保。
3. **影響範囲**：参照元と依存先、分岐、帳票、集計、業務・顧客への直接/間接の影響。
4. **横展開**：同種のバリデーションや設計パターンの存在。
5. **変更影響**：バリデーションを厳しくした場合の破壊的変更、既存データの移行・互換性。
6. **対応案と推奨**：封じ込め、恒久対応、データ補正、テスト、工数、残存リスクと推奨理由。
7. **推進**：関係者と調整、権限内の修正・検証、判断待ち事項と期限、結果の確認。

### 共有・エスカレーションの設計
- 重大度が高い、被害の兆候がある、修正より早い封じ込めが必要、組織規定がある場合は速やかに速報する。『十分な分析が終わるまで黙る』ことはしない。
- 重大性が未確定でもリスクがある場合は、調査中である旨・現時点の事実・次回更新を共有しながら調査を継続できる。
- 遅延を伴わない範囲では、単なる『バグを見つけた。どうしますか』ではなく『影響・原因・案・私の推奨・判断が必要な論点』をセットにする。
- 管理者は調査の丸投げ先ではなく、優先度・トレードオフ・組織的調整等の権限を行使する相手。社内プロセスが別ならそちらに従う。
- 実施すべき対応・報告先・優先度・タイミングを事実未確認のまま断定しない。『翌日一度だけ催促』『通常緊急度』など、根拠のない定型ルールを置かない。

## 不適切なコーチング例と修正

NG: 『1時間だけ調べてリーダーに報告し、優先度を決めてもらいましょう』
問題: 調査を恣意的に打ち切る。影響範囲と推奨策を持たずに委ねる。役割も分からず上下関係を決めている。

改善: 『あなたの今回の責任と調査可能な範囲を確認します。そのうえで、リスクの高い兆候があれば先に一報し、並行して再現・データ・下流・横展開・修正副作用まで調べ、推奨策を組み立てます。決裁が必要な事項だけ論点付きで依頼します。』

NG: 『自分で全部直すのが責任感』
問題: リスク許容・顧客価値・権限・変更管理を無視する。

改善: 『影響分析と推奨案は主体的に引き受ける。実施・優先度・告知などは権限と手続きに沿って判断する。』
