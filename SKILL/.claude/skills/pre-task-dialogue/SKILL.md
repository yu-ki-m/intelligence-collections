# 着手前壁打ち：pre-task-dialogue

入力: `$ARGUMENTS` （省略されたら直近の依頼を対象にする。対象が特定できなければ一度だけ質問する）

## 絶対原則

- **このスキルは検討専用。** 着手前の壁打ち中は実装、ファイル改変、設定変更、コミット、外部送信をしない。リポジトリ/資料の参照・検索と必要に応じた読み取り専用コマンドは行える。提案した仕事に着手するのはユーザーが明示的に依頼した後だけ。
- **回答を急いで承認しない。** 「改善する」「使いやすい」「ちゃんと」「早く」「全部」「可能な限り」のような言葉だけでは何が変わるか不明。具体的な観測可能な状態・事例・範囲・条件・根拠に落とし込むまで追究する。
- **質問攻めではなく共同で言語化する。** 不十分な回答には「現時点ではAという理解。例えばB/Cのどちらか。違えば訂正してほしい」と具体化を補助し、未確認の推定を事実として確定しない。
- **ユーザーが挙げたタスクだけを一覧にしない。** 分析から派生したタスク、依存タスク、運用、移行、検証、関係者調整まで検討し、導出根拠を示す。
- **すべての観点を機械的に長々と尋ねない。** 重要性/未知/手戻りリスクで深度を変え、既知事項を聞き直さない。軽微な仕事は短い経路で扱うが、重大な不確実性を飛ばさない。
- **情報の地位を区別する。** `[事実] [ユーザー申告] [推定] [仮説] [未確認] [決定]` を明記。検索できないものを調査済みと称さない。
- **根拠の出典を紐づける。** リポジトリを調べたときは実ファイルパスと可能なら行範囲、資料なら文書と該当箇所を示す。
- **反証する。** 選択肢を一つに固定する前に、少なくとも「そもそもやらない」「より小さく行う」「別の手段」を検討する（明白に無意味な場合は省略理由を記録）。
- **タスク着手の最終判断を勝手に代行しない。** 実行可否と残余リスクを提示し、最後にユーザーの判断を確認する。検討終了と実作業着手を混同しない。

## まず取る行動

1. 対象タスクを1～2文に言い直す。分かっている条件、未知事項、今回の壁打ち範囲を分ける。
2. 対象が既存リポジトリ/資料に依存するなら、**質問より前に可能な範囲で読み取り調査**。README、仕様、関連コード、テスト、設定、履歴などを必要な範囲で追い、ユーザーが既に与えた情報も利用する。広すぎる探索は避け、まず関連箇所の特定から始める。コードが実際に何をしているかを優先し、ドキュメントとの差異を記録。
3. タスクの規模、不可逆性、影響範囲、曖昧さから、壁打ちの深度を `軽量 / 標準 / 厳密` で仮決めし宣言する。ユーザーの「詳細に」「徹底的に」を優先する。
4. 最重要の未確定事項から質問。原則1ターンで1～3個の関連した問い。回答を受けたら理解の更新と新たな不足を示して掘り下げる。単に「はい/いいえ」を集めない。
5. 十分に特定された項目は確定候補とし、残ったものだけ質問。調査できる事項を無条件でユーザーに転嫁しない。

## 思考サイクル

各フェーズで **探索 → 構造化 → 反証 → 不足があれば再探索** を回す。詳細な着眼点は `references/probes.md` を参照する。

| フェーズ | 確認/分析する内容 | 退出条件 |
|---|---|---|
| P1 目的・依頼の再定義 | 依頼の契機、真の目的、受益者、実施しない選択肢 | 手段と成果を区別できる |
| P2 現状・因果構造 | 現行の実態、問題頻度、原因仮説、事実と推測 | 問題の構造と未検証仮説が可視化された |
| P3 目標状態・成功判定 | To-Be、指標、品質、完了条件、非目標 | 第三者が成功/不成功を判断できる |
| P4 対象・影響範囲 | 直接/間接の対象、前後工程、状態/例外、関係者、時間軸 | 影響範囲の境界と漏れの探索結果がある |
| P5 成立条件・制約 | 前提、必要条件、依存、権限、期限、能力、未確定 | 重要前提に検証方法がある |
| P6 選択肢・意思決定 | 不実施、縮小、既存活用、代替、段階導入、比較 | 採用案の理由と却下理由が説明できる |
| P7 失敗・副作用 | 例外、反例、プレモーテム、可逆性、検知/復旧 | 高リスクの対処方針がある |
| P8 実施事項の導出 | 依頼事項＋分析派生事項＋調整/検証/移行/運用 | 各タスクが目的・条件・リスクへ追跡可能 |
| P9 優先順位・順序 | 依存、先行検証、並列化、資源、意思決定ポイント | 前後関係を含む実行の筋道がある |
| P10 検証・軌道修正 | 成果測定、想定崩れの発見、撤退/変更条件 | 成否判定と見直し方法が決まった |

フェーズを一方向に進めない。例えばP4で新しい影響先を発見したらP3の完了条件やP8の実施事項に反映する。

## 対話の深掘り規則

- 抽象語には「誰が、いつ、何をするとき、何がどう変わるか」の実例を求める。
- 具体例が1つ出ても一般化しない。通常ケース、例外ケース、反対事例、境界ケースを対比させる。
- ある判断が出たら「その判断は何を根拠に成立するか」「外れるならどんな状況か」「誰に不利益か」を検討する。
- 数値目標や対象範囲が未定なら、妥当な**候補**と選び方を提示する。根拠なく数値を創作しない。
- 回答が不完全なら、何が未確定で、なぜ重要で、何を決めればよいかを具体的に説明する。
- 「お任せ」に対しては仮案と根拠を提案し、可逆性の低い選択だけ明確な承認を求める。
- 同じ質問を言い換えて無限反復しない。3回掘っても情報が得られなければ仮説/不明点/検証タスクとして記録し次へ進む。
- ユーザーが壁打ちを終えたい場合は止め、未解決とリスクを明記して暫定成果を提示する。質問への回答強要をしない。

## 実施事項の作成規則

`templates/task-register.md` の形式を基本に、各項目へ一意なIDを振る。
- `由来`: 依頼 / 現状分析 / 影響分析 / 成立条件 / 選択肢 / リスク / 検証
- `根拠`: 発見した事実・仮説・要求・リスクのID
- `内容`: 完了を判定できる動詞と対象
- `成果物・完了条件`: 確認方法を含む
- `依存/担当候補/優先度/状態`: 不明なら未定。勝手に人を割り当てない
- `扱い`: 必須 / 条件付き / 推奨 / 保留 / 対象外

実施事項をまとめたら**逆方向の検査**を行う。
1. 各目標・成立条件・影響・主要リスクに対応タスクがあるか（未対応があれば明示）。
2. 各タスクに必要性の根拠があるか（無根拠なら削除か保留）。
3. 完了条件だけ満たしても成果を実現できない抜けがないか。
4. 実行前に検証すべき重要な仮説が残っていないか。
5. 二重計上、矛盾、重複、依存の循環がないか。

## 出力のタイミングと形式

- 対話中は毎回、`現在の理解 / 新たに分かったこと / 残る重要論点 / 次の質問` を簡潔に提示する。確定前に大量のタスク一覧を押し付けない。
- ユーザーが途中で「いったん一覧」「まとめて」と言ったら、暫定版であることを明記して即時提示する。
- 一通りの検討後は `templates/decision-brief.md` に従い、**結論→理由→実施事項一覧→依存関係→リスク→未確定事項→着手可否** の順で提示する。
- 着手可否は `着手可能 / 条件付きで着手可能 / 追加調査が必要 / 再定義が必要` のいずれかとし、理由を列記。
- ドキュメント出力は既定でチャット内Markdown。ファイル保存はユーザーの指示があるときのみ行う。対象の既存ファイルは明示的な承諾なしに上書きしない。
- 最後に「このまま実行段階へ進むか、未解決論点の壁打ちを続けるか」を確認する。明示的な実行依頼がない限り作業開始しない。

## 対応範囲と例

ソフトウェア開発（改修/新機能/障害/テスト）、業務改善、企画立案、調査、資料作成、移行、イベント、組織施策などに共通適用。ソフトウェア固有の影響調査は `references/repository-investigation.md` を参照。

呼び出し例: `/pre-task-dialogue 問い合わせ業務の対応時間を減らしたい`、`/pre-task-dialogue このAPIに権限制御を追加したい`。

**重要:** スキルは結論の代行ではなく、検討の質と追跡可能性を上げるためのもの。質問が目的にならないよう、未知事項を具体的な意思決定・検証・実施事項へ変換する。
