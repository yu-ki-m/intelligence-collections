# 既存リポジトリの読み取り調査

## 調査の原則
- ユーザーが対象コードや仕様を指定しているなら、まずその周辺を調査する。既知の場所を再質問しない。
- 読み取り専用の手段を選ぶ（例: `pwd`, `rg --files`, `rg -n`, `git status --short`, `git log`, `git show`, `sed -n`）。テストやビルドは副作用があり得るため、壁打ち段階では原則実行せず、必要性を説明してユーザーと相談する。
- 機密情報・認証情報は出力に含めず、引用に必要な最小限の情報を用いる。
- 仕様書の記述とコードの実動作は別々に扱い、矛盾があれば未解決事項にする。

## 探索軸
1. 入口: UI, API, CLI, バッチ, イベント受信, スケジューラ。
2. 主要処理: バリデーション、認可、ビジネスルール、永続化、状態遷移。
3. 波及: 呼び出し元/先、共有データ構造、キュー、キャッシュ、検索、通知、監査。
4. 非正常: 例外、リトライ、二重実行、部分成功、タイムアウト、補償処理。
5. 利用者・運用: 画面、権限、設定値、移行、監視、手順書、運用ツール。
6. 既存の検証: 単体/結合/E2E、fixtures、mock、テスト未実施の領域。
7. 仕様波及: 直接変更対象だけでなく、動作や意味が変わる既存仕様とその本来の目的を抽出する。

## 簡易調査記録
- `E-xx` 証拠: ファイル:行範囲、観察事実、確実性。
- `S-xx` 既存仕様: どの動作・目的・利用条件を守っているか。
- `I-xx` 影響: 変更内容、直接/間接、影響を受ける仕様・機能、懸念。
- `U-xx` 未確認: 検証方法と、確認できない場合の暫定仮説。

依頼内容の範囲で十分な探索を行い、全リポジトリを無条件で走査しない。影響連鎖が追えない場合はその制限を明示する。
