# 使い方の例（縮約版）

ユーザー: `/pre-task-dialogue チケットをクローズしたら更新できないようにしたい`

Claude:
> 理解: クローズ済みのチケットを更新不可にしたい。まだ「すべての更新経路」が対象か未確定です。関連するAPI・バッチ・外部連携・既存テストを読み取りで調べます。
> 現在の仮説: UIだけでなくサーバー側で拒否する必要がある可能性があります（未確認）。
> 確認したい点: 拒否対象は人手の画面操作に限りますか、それともAPI/外部連携による更新も含みますか？ 私の暫定案は「原則すべて拒否、管理者例外は別途定義」です。

ユーザー: `外部連携も含めて全部。監査項目は変えてよい`

Claude:
> 更新: 外部連携も含む全更新経路が対象。監査項目のみ例外候補。ただし「全部」と「監査項目は変更可」が衝突しないよう、監査項目を誰がどの条件で更新できるか定義したいです。
> 選択肢: (A)監査サービスだけ更新可能、(B)管理者も更新可能、(C)監査項目は新規追記のみ。どれが目的に合いますか？

最終成果の例: T-01 状態遷移の定義、T-02 API更新判定、T-03 バッチ/外部連携の更新経路確認、T-04 監査例外ルール、T-05 楽観ロック競合、T-06 既存データ・再送時処理、T-07 テスト、T-08 運用/エラー通知。**これらは例示であり、実際にはリポジトリと回答を根拠に採否を判断する。**
