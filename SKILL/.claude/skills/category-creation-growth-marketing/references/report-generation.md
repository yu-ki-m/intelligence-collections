# レポート生成（最終工程）

分析の結果を、読み手が前提と因果をたどって理解できるHTMLレポートにする手順である。

## 目的

分析の出力（`references/output-template.md` の形式）は、Phaseの番号、英語の専門用語、表の略記で書いた作業の記録である。分析者には読めるが、読み手は「なぜその結論になるのか」を追えない。このままでは、結論が正しくても、読み手は判断に使えない。

レポート生成は、分析の内容を変えずに、**読み手が前提 → 因果 → 結論の順にたどれる形** に組み直す工程である。

## いつ行うか

* どのモードでも、分析の出力（`SKILL.md` 8章）を作った後に行う。
* Completion Gate（`SKILL.md` 7章）を満たしていない場合も行う。その場合は、表紙と第0章で、分析完了ではないことと、残っている確認を示す。
* ユーザーがレポートは不要と言った場合だけ省略する。

## 入力

* 分析の出力（冒頭の5項目、各セクション、Coverage Matrix）
* 読み手の要求（`SKILL.md` 9.1。原文のまま使う）
* 説明の粒度（初回は、すべての章を粒度1にする。「分からない」と言われた箇所は6章の手順で変える）

## 1. 読み手の要求を、書き方のルールに変える

`SKILL.md` 9.1 の要求の各行を、レポートの中で次のように守る。左の列は要求の原文である。

| 読み手の要求（原文） | レポートでの守り方 | 確認のしかた |
| --- | --- | --- |
| 最初に「結論何なのか」を1〜2文で説明する。 | レポートの冒頭と、各章の冒頭に「結論」の枠（`.gist`）を置く。枠の中は1〜2文にし、その章の結論を書く。まだ説明していない専門用語は使わないか、括弧で意味を添える | 各章の最初の要素が「結論」の枠で、3文以上になっていない |
| 専門用語を使う場合、その用語がこの文脈で何を意味するのか説明する。 | 専門用語が初めて出る箇所の直後に、用語の枠（`.term`）を置き、「この文脈での意味」と「例」を書く。辞書の意味ではなく、この分析での使い方を書く（例: ICP は一般には「理想の顧客像」だが、この分析では「最初に売り込む相手として選んだ○○」を指す）。英語の略語は、正式名と日本語の意味を併記する。Phaseの番号（P7など）は読み手が知らない記号なので、本文の説明に使わず、章の補足（`.phase-tag`）にだけ書く | 本文中の英語・カタカナ語・略語を拾い、それぞれの初出の箇所に説明がある |
| 抽象語だけで説明しない。 | 「価値」「課題」「構造」「仕組み」「体験」「成長」のような抽象語を使ったら、同じ文か次の文で、それが指す具体的なもの（誰の、どの作業の、どの数値か）を書く | 抽象語を含む文の前後に、人・作業・数値のどれかがある |
| 「AによってBが可能になる」と書く場合、Aの何がBを可能にするのか説明する。 | 「Aの○○という性質（働き）が、Bに必要な□□という条件を満たすので、Bができる」の形にし、Aの性質・Bの条件・両者のつながりの3つを書く。図では、矢印に「そのため」「その結果」などのラベルを付ける | 「によって」「により」「ことで」「おかげで」を検索し、Aの性質とBの条件が書かれている |
| 主語を省略しない。「誰・何が、何を、どうする」の形を基本とする。 | すべての文に主語を書く。特に「〜できる」「〜が必要」「〜される」「〜が増える」の文で、誰・何がそうなるのかを書く。表のセルや図の中の文も同じである | 文末が「できる」「必要」「される」の文に、主語がある |
| 前提知識を暗黙に要求しない。説明に必要な前提を先に示す。 | 「結論」の直後に前提の章（第0章）を置き、読み手が知らないと本文を理解できない事柄を、本文で使う順に説明する。章ごとに追加の前提が要る場合は、その章の「結論」の直後に前提の枠（`.premise`）を置く | 各章で使っている事柄が、それより前に説明されている |
| 抽象的な説明の直後に具体例を1つ示す。 | 抽象的な説明の直後に、具体例の枠（`.example`）を1つだけ置く。例は分析の中の事実を優先する。事実がない場合は、枠の見出しを「例（仮の場面）」とし、数値を使う場合は「数値は説明のための仮置き」と書く（`SKILL.md` 3.2） | 各章に具体例の枠があり、1つの説明に複数の例を並べていない |
| 複数の概念を一度に説明せず、1つずつ説明する。 | 1つの章・1つのカード・1つの図で扱う概念を1つにする。1つの文に、まだ説明していない用語を2つ以上入れない。複数の概念が関係する場合は、1つずつ説明した後に、関係の図で結ぶ | 1つのカード・枠の中に、新しく説明する用語が2つ以上ない |
| 「柔軟」「高度」「効率的」「最適化」など、具体的な意味が不明な形容を避ける。 | 5章の語を使わない。使いたくなったら、数値・条件・比較の相手に置き換える | 5章の語を検索して0件である |
| 結論に至るまでの因果関係を飛ばさない。 | 結論までの因果を、1段ずつ因果の図（`.chain`）に並べる。分析の原因の表（P2など）の段を1つも省かない。2つの段の間を「なぜ」で説明できない場合は、その段を [仮説] と示す | 図の段の数が、分析の原因の表の段の数以上ある。各矢印にラベルがある |
| 用語の羅列で説明しない。 | 箇条書きの各項目と、表の各セルを、主語と述語のある文にする。「Distribution、Workflow、Standard」のような名詞だけの列挙をしない。点数や判定を書くセルにも、理由を1文添える | 名詞だけで終わる箇条書き・セルがない（状態のバッジと証拠ラベルは除く） |
| HTML/CSSを使い、文章を装飾するだけではなく、全体像・因果関係・順序・比較・階層が視覚的に理解できるよう、フロー図、カード、矢印、表、階層構造を使って説明すること。 | 4章の対応表に従い、各章で「伝えたい関係」を決めて、その関係を表す図を最低1つ置く。色や太字で目立たせただけのものは、図に数えない。色だけで意味を伝えず、矢印や枠には文字のラベルを付ける。図は文章の代わりにしない。図の直前か直後に、図を説明する文章を置く（3.1） | 各章に、関係を表す図が1つ以上あり、各図の前後に説明の文章がある |
| 私が「分からない」と言った場合、同じ説明を言い換えるだけではなく、説明の粒度を1段階下げる。 | 6章の手順で、分からなかった箇所の粒度を1段階細かくして書き直す | 書き直した箇所で、因果の段・前提・具体例の具体さのどれかが増えている |

## 2. レポートの構成

### 2.1 共通の骨組み

どのモードでも、以下の順に並べる。前提を本文より先に置き、全体像を見せてから、1つずつ説明する。

```text
表紙     : タイトル（読み手の問いの形） / 分析の対象 / 分析の種類（モード） / 使った情報 /
           分析の状態（分析完了か。完了でなければ、残っている確認） / 説明の粒度 / 作成日
目次
結論   : レポート全体の結論（1〜2文）
第0章    : このレポートを読むための前提
           - 本文を理解するのに必要な知識（1つずつ。各前提に具体例を1つ）
           - 根拠の強さを示すラベルの読み方（SKILL.md 3.3 の4種類）
           - この分析の限界（使った情報、置いた仮定、未実施・一部実施の確認、差し戻しの有無）
全体像   : 分析の流れの図（各段の結論を1文ずつ）と、主な結論のカード
本文の章 : モードごとに2.2の順で並べる
弱いところ       : 反証パスの結果とリスク（P31）
次に確かめること : 実験と判断ルール（P32）
まだ分かっていないこと : Coverage Matrix を、状態と理由の文にした表
付録     : 分析の出力のうち本文に入れなかった参考情報 / このレポートの章と、分析の段階（Phase）の対応表
```

分析の出力の内容は、1つも削らない。本文の筋道に入らない参考情報（例: Jevの例の「その他の強み（参考）」）は、付録に置く。

### 2.2 モードごとの本文

本文の章は、分析が結論にたどり着いた順（`SKILL.md` 2.1 の順序）に並べる。分析の出力の見出しの順が違っても、レポートはこの順にする。

| モード | 本文の章（この順） |
| --- | --- |
| Quick Diagnosis | すでに解かれている部分（P0.5）→ 市場が当たり前だと思っていること（P1）→ 本当の問題（P2）→ 反対の仮説（P3）→ 置き換えるもの（P4）→ どの市場として戦うか（P6 判定のみ） |
| White Space Discovery | 探索の条件（P0 探索版）→ 候補の一覧と判定（捨てた候補と、捨てた理由を含む）→ 選んだ候補ごとに: 顧客の今のやり方（P1）→ 残る隙間の原因（P2）→ 反対の仮説（P3）→ 市場の見込み（P6 判定のみ）→ なぜ今か（P15） |
| Full Strategy | Stage A〜F の順。Stage ごとに1つの章にし、Phase を1つずつ節にする。構成の詳細は 2.4 にある |
| Single Phase | 問いと、その問いを考える理由 → 仮置きした前提 → 対象Phaseの結論 → 前提が崩れたら結論がどう変わるか |

### 2.3 見出しの付け方

* 章の見出しは、読み手の問いの形にする（例: 「すでに解かれている部分はどこか」「本当の問題は何か」）。
* 分析の用語（Prior Art Sweep など）とPhaseの番号は、見出しに使わない。章の補足（`.phase-tag`）に「分析の該当箇所: P0.5 先行事例の確認」のように書く。

### 2.4 Full Strategy の構成

Full Strategy は、34のPhaseと38のセクションがあり、ほかのモードより長くなる。長いレポートほど、後半の説明が短くなりやすい。そのため、次の構成を使い、**34の節のすべてに、3章の説明の型を同じように使う。** 後半の節ほど「結論」だけで済ませる、ということをしない。完成の形は `examples/report-full-strategy-skeleton.html`（骨組みの例）にある。

```text
表紙 / 目次（2階層: 章 → 節。.toc.deep）
結論   : Executive Summary の結論（1〜2文）
第0章    : 前提（P0 Intake の、受け取った情報と置いた仮定を含む）
全体像   : 6つの Stage の流れ図（Stage ごとに、決まったことを1文）＋ 図の説明の文章
           ＋ 主な結論のカード（市場定義の判定、最大の勝ち筋、最大のリスク、事業性の判定）
第1章    : Stage A 問題発見     → 節 1.1 P0.5 / 1.2 P1 / 1.3 P2 / 1.4 P3 / 1.5 P4
第2章    : Stage B 市場定義     → 節 P5〜P9
第3章    : Stage C 伝達と証明   → 節 P10〜P17
第4章    : Stage D GTMと成長    → 節 P18〜P25
第5章    : Stage E 計測と事業性 → 節 P26、P27
第6章    : Stage F 防御と所有   → 節 P28〜P30
第7章    : 結論どうしが食い違っていないか（SKILL.md 4.3 の9つの組み合わせ）
第8章    : 弱いところ（P31）
第9章    : 次に確かめること（P32）
第10章   : まだ分かっていないこと（Missing Evidence と、34行の Coverage Matrix）
付録     : 分析の出力の38セクションと、レポートの章・節の対応表
```

**Stage の章の中の並び:**

```text
章の「結論」    : この Stage で何が決まったか（1〜2文）
Stage の中の流れ図: Phase ごとの結論を1文ずつ並べ、どの結論が次の Phase の前提になったかを矢印で示す
図の説明の文章    : どの Phase の結論が、この Stage の結論を決めたか
Phase の節 × n    : section.phase。見出しは h3。各節は3章の説明の型で書く
```

**分析の出力（38セクション）と、レポートの対応:**

| 出力のセクション | レポートでの置き場所 |
| --- | --- |
| 1 Executive Summary | 結論、全体像の結論のカード |
| 2 Intake & Assumptions | 第0章 |
| 3〜7（P0.5〜P4） | 第1章の節 |
| 8〜12（P5〜P9） | 第2章の節 |
| 13〜20（P10〜P17） | 第3章の節 |
| 21〜28（P18〜P25） | 第4章の節 |
| 29〜30（P26〜P27） | 第5章の節 |
| 31〜33（P28〜P30） | 第6章の節 |
| 34 Reality Check | 第8章 |
| 35 Consistency Check | 第7章 |
| 36 Missing Evidence | 第10章 |
| 37 Next Experiments | 第9章 |
| 38 Coverage Matrix | 第10章 |

## 3. 1つの章の書き方（説明の型）

各章（Full Strategy では各節）は、次の順に書く。1つの章で扱う概念は1つにする。

```text
1. 結論（1〜2文。その章の結論）
2. 前提（その章で新しく必要な知識がある場合だけ。.premise）
3. 説明の文章（結論に至る筋道を、文章で1段ずつ書く。専門用語は、初出の直後に用語の枠 .term）
4. 図（伝えたい関係を表す図。4章から選ぶ）
5. 図の説明の文章（図が何と何の関係を示すか、どの段が結論に効くか、どの段が仮説かを書く）
6. 具体例（抽象的な説明の直後に1つ。.example）
7. 根拠のラベルと、「この結論が間違いだとわかる条件」（.falsify）
8. 次の章へのつながり（1文。この章の結論を、次の章がどう使うか。.next）
```

### 3.1 図は文章の代わりではない

図は、文章で書いた筋道を見やすくするために置く。図を置いたことを理由に、説明の文章を削らない。

* **図の直前か直後に、図を説明する文章を置く。** 40字以上の段落にし、図が示す関係を文章でも言う。「下の図は○○を示す」だけの紹介文は、説明の文章に数えない。
* **図の中の文は、主語と述語のある文にし、句点（。）で終える。** 名詞だけ・体言止めにしない（例: 「判断のたびの LLM 呼び出し」ではなく、「Agent が、判断のたびに LLM を呼んでいる。」）。流れ図の見出し（h4）と、表のセルのうち名前・数値だけを書く列は除く。
* **図に入りきらない説明を削らない。** 理由、条件、例外、数値の条件のように、図の枠に入りきらない説明は、図の外の文章（5の図の説明の文章）に書く。図の枠を小さく保つために、分析の内容を落としてはいけない。

7の「この結論が間違いだとわかる条件」は、分析の反証パス（P31）、判断ルール（P32）、Depth Check の「反証」から取る。分析に書かれていない反証を、レポートで新しく作らない。分析に反証の記述がない場合は、枠の見出しを「まだ確かめていないこと」にして、未検証の内容を書く。

## 4. 図の選び方

各章で「読み手に見せたい関係」を1つ決め、その関係に合う部品を使う。部品は `assets/report-template.html` にある。

### 4.1 関係ごとの部品

| 見せたい関係 | 使う部品（テンプレートのクラス） | 向いている内容（分析の段階） |
| --- | --- | --- |
| 全体像 | 縦の流れ図（`.flow.v`）＋ 結論のカード（`.cards`） | 分析の流れと、各段の結論（全体像の章） |
| 因果関係 | 因果の図（`.chain`）。矢印に「なぜ？」「その結果」などのラベルを付ける | 症状 → 原因 → 構造原因（P2）、なぜ今か（P15）、事業性の計算（P27）、「AによってBができる」の説明 |
| 順序 | 流れ図（`.flow`）、時系列（`.timeline`）、漏斗（`.funnel`）、循環（`.loop`） | 顧客の作業の工程（P1）、ローンチの計画（P20）、最初の価値までの段階（P22）、Growth Loop（P24）、Funnel（P26） |
| 比較 | 対比（`.contrast`）、比較表（`table`。選んだ行は `tr.pick`）、カード（`.cards`） | 先行事例（P0.5）、「○○ではなく△△」（P2）、常識と反対仮説（P3）、Before / After（P4）、A/B/C の判定（P6）、比較軸（P7）、White Space Discovery の候補 |
| 階層 | 階層図（`.tree`）、Message House（`.house`）、深刻度の段（`.levels`） | 前提と設計の関係（P1）、ICPから隣接セグメントへの拡大（P5）、メッセージの構造（P10）、Moat（P29）、リスク（P31） |
| 分岐 | 分岐図（`.branch`） | 売り方の切り替え条件（P18）、実験の判断ルール（P32）、処理の振り分け |
| 条件の組み合わせ | 「かつ」でつなぐ流れ図（`.flow.and`） | 残る隙間の条件（P0.5） |
| 範囲 | 範囲の帯（`.range`） | 価格の下限・案・上限（P19） |
| 計算 | 計算の分解（`.calc`）＋ 感度分析の表（注意する行は `tr.alert`） | 現状の総コスト（P1）、LTV と回収期間（P27） |
| 数値 | 数値のカード（`.card .big`） | 主役の数値と、その条件（P11） |
| 対応 | 表（整合性チェックの結果は `.st.ok` 一致 / `.st.ng` 矛盾 / `.st.todo` 未確認） | 主張と証拠（P12）、Phase 間の整合性チェック（`SKILL.md` 4.3） |

状態を示す小さな部品として、証拠ラベル（`.badge`）、Coverage Matrix の状態（`.st`）、説明の粒度（`.grain`）を使う。これらは図に数えない。

### 4.2 Phase ごとの部品（Full Strategy）

Full Strategy では、節ごとに次の部品を使う。1つの節に図が2つ以上ある場合は、図ごとに、図の説明の文章を置く（3.1）。

| Phase | 使う部品 |
| --- | --- |
| P0.5 先行事例 | カード（先行事例ごとに、できること・できないこと）＋「かつ」の流れ図（残る隙間の条件） |
| P1 今のやり方 | 流れ図（工程。待ち・変換・確認・引き継ぎを見出しに書く）＋ 計算の分解（現状の総コスト）＋ 階層図（前提と設計） |
| P2 本当の問題 | 対比（○○ではなく△△）＋ 因果の図（症状 → 構造原因） |
| P3 反対の仮説 | 対比（常識 → 反対の仮説）＋ 表（証拠と、その強さ） |
| P4 敵 | 対比（Before → After）＋ カード（置き換えるもの / 置き換えないもの） |
| P5 ICP | 表（セグメントの評価）＋ カード（利用者・意思決定者・予算保有者）＋ 流れ図（Beachhead → 隣接セグメント） |
| P6 市場定義 | 比較表（A/B/C。選んだ行は `tr.pick`）＋ 因果の図（選んだ理由） |
| P7 比較軸 | 比較表（既存の比較軸と、新しい比較軸） |

## 5. 使わない形容と、言い換え方

以下の語は、何が・どれだけ・何と比べてそうなのかがわからないので使わない。

| 使わない言葉 | 意味がわからない理由 | 代わりに書くこと | 例 |
| --- | --- | --- | --- |
| 柔軟（な） | 何を、どこまで変えられるのかがわからない | 変えられる対象と範囲 | 「柔軟に使える」→「開発者が、選択肢を呼び出しのたびに変えられる」 |
| 高度（な） | 何と比べて、どの点で上なのかがわからない | 比較の相手と数値 | 「高度な判断」→「長い入力について、大型のLLMと同じ正解率で選ぶ（仮説）」 |
| 効率的（な）・効率化 | 何の量が、どれだけ減るのかがわからない | 減るものと、前後の数値 | 「突合を効率化する」→「経理担当2名の月末の突合が、月20時間から2時間になる（数値は例）」 |
| 最適化・最適（な） | 何を基準に、どの状態にするのかがわからない | 基準と、変わる数値 | 「コストを最適化する」→「判断1回の料金を、0.3円から0.004円にする（数値は例）」 |
| 革新的・画期的・次世代 | 既存の手段と何が違うのかがわからない | 先行事例（P0.5）との違い | 「革新的なAI」→「分類器と違い、長い入力でもLLMと同じ正解率を目指す（仮説）」 |
| シームレス（な） | どの手間がなくなるのかがわからない | なくなる操作 | 「シームレスに連携」→「開発者が、新しい契約をせずに、今使っているサービスの請求にまとめられる」 |
| 強力・大幅・飛躍的 | どれくらいなのかがわからない | 数値と比較の相手 | 「大幅に速い」→「同じ判断で、中央値70ミリ秒（比較の相手は7.2秒。数値は例）」 |
| スケーラブル | 何が増えたときに、何が保たれるのかがわからない | 増えるものと、保たれる数値 | 「スケーラブル」→「1日の判断が10倍になっても、1回の応答時間が変わらない（例）」 |
| 包括的・戦略的・効果的・高品質・高性能 | 範囲や効果がわからない | 含む範囲、効果の数値、比較の相手 | 「効果的な施策」→「無料枠の案内で、2週間に50人が最初の結果を得る（目標。例）」 |

分析の用語に同じ語が含まれる場合（例: P8 の位置の1つである Optimization）は、その語を使う代わりに、働きを具体的に書く（例: 「既存の製品の使い方のうち、料金がかかりすぎている部分を減らす役割」）。

## 6. 「分からない」と言われたとき（説明の粒度）

### 6.1 粒度の段階

「粒度を1段階下げる」とは、説明を1段階細かくすることを指す。粒度1から始め、「分からない」と言われるたびに、その箇所を次の番号に進める。

| 粒度 | 名前 | 因果の段 | 前提 | 具体例 | 1つの枠・カードに入れる量 |
| --- | --- | --- | --- | --- | --- |
| 1 | 標準（初回） | 結論までの主な段（分析の原因の表と同じ段） | その章に必要なもの | 1つ（分析の中の事実を優先） | 1つの概念 |
| 2 | 詳細 | 粒度1の各段の間に、「なぜそうなるのか」の段を1つずつ足す | 粒度1で暗黙にしていた前提を、先に足す | 足した段ごとに1つ | 1つの段 |
| 3 | 分解 | 1つの段を、「誰が、何をして、何が起きるか」の手順に分ける | 専門用語を使わずに説明し直し、用語は最後に「これを○○と呼ぶ」と名前だけ付ける | 登場する人・数値・時間の流れがある、1つの場面 | 1つの手順 |
| 4 | 最小単位 | 1つの手順を、1文に1つの事実だけを書く形に分ける | その分野の基礎知識から説明する（例: トークンとは何か） | 身近な場面へのたとえと、「たとえの何が、元の話の何に当たるか・どこが違うか」の対応表 | 1文 |

### 6.2 粒度の下げ方

1. **対象を決める。** ユーザーが示した箇所を対象にする。示されていない場合は、直前に説明した箇所を対象にする（レポートを渡した直後なら、レポート全体の「結論」と全体像）。
2. **分からなかった原因を推定する。** 前の説明の中で、次のどれが原因だったかを推定し、そこを重点的に直す。
   * 知らない用語が、説明なしに出てきた
   * 2つの段の間の「なぜ」が飛んでいた
   * 具体例が抽象的だった、または例がなかった
   * 1つの枠に、複数の概念が入っていた
3. **1段階細かい粒度で書き直す。** 6.1 の表の、次の番号の列に従う。
4. **言い換えだけになっていないか確認する。** 書き直した箇所で、次のどれか1つ以上が増えていなければならない。同じ段数・同じ例のまま、言葉だけを変えたものは不可である。
   * 因果の段の数
   * 先に示す前提の数
   * 具体例の具体さ（人、数値、場面、時間の流れ）
   * 手順に分けた数
5. **HTMLを更新する。** 同じファイルの該当する章を書き換え、章の粒度の表示（`.grain`）と表紙の「説明の粒度」を更新し、更新履歴（`.changelog`）に「どの章を、粒度いくつから、いくつにしたか」を書く。前の版を残したい場合は、別のファイル名で保存する。
6. **チャットで伝える。** 書き直した箇所の要点を、読み手の要求（`SKILL.md` 9.1）に従って説明する。最後に、特に分からなかった文があれば教えてほしいと1文添える。
7. **すでに粒度4の場合** は、これ以上細かく分けられないので、どの文から分からなくなったかを質問する。

### 6.3 例: 同じ説明を、粒度1から3まで下げる

| 粒度 | 説明 |
| --- | --- |
| 1 | Agent は判断のたびに LLM を呼ぶので、判断の回数が増えるほど、時間と料金が増える。 |
| 2 | ① Agent は、1つの作業の中で何度も判断する。→ なぜ呼ぶのか: ② Agent は、判断のたびに LLM を呼ぶ（長い入力を正しく判断できる手段が、LLM しかないため）。→ 呼ぶと何が起きるか: ③ LLM は、答えを作るたびに、トークンを1つずつ計算する。→ その結果: ④ 計算した回数に応じて、時間と料金がかかる。→ そのため: ⑤ 判断の回数が増えるほど、時間と料金が増える。（各段に具体例を1つずつ付ける） |
| 3 | 例の場面: 問い合わせ対応の Agent が、1件の問い合わせを受け取る。手順1: Agent は「どの担当に回すか」を決めるために、LLM を1回呼ぶ。手順2: LLM は "billing" という答えを、トークンを計算して作る。手順3: Agent は「返信が必要か」を決めるために、もう1回 LLM を呼ぶ。…手順5: 1件で3回呼んだので、料金も3回分かかる。1日に1,000件なら、3,000回分かかる（数値は説明のための仮置き）。 |

## 7. 分析の内容を変えない

レポートは、分析の結論を読みやすくするだけであり、新しい分析ではない。

* 分析の結論、数値、証拠ラベル、未検証の扱いを変えない。
* わかりやすくするために、[仮説] を断定の文にしない（例: 「LLMと同じ精度が出る」ではなく、「LLMと同じ精度が出るかは、まだ確かめていない [仮説]」と書く）。
* 分析にない数値・事例・顧客の発言を、具体例として作らない。説明のために仮の場面や数値を使う場合は、「例（仮の場面）」「数値は説明のための仮置き」と明記する（`SKILL.md` 3.2）。
* 背景の知識（例: LLMの一般的な仕組み）を前提として説明する場合は、分析の主張と区別し、「この節の説明は一般的な仕組みであり、分析の主張ではない」と書く。
* 分析の出力の「未検証」「一部実施」「分析完了ではない」を、レポートでも同じ強さで示す。

### 7.1 取りこぼしの確認

「削らない」と決めていても、長いレポートでは、削ったことに書き手が気付かないことがある。そのため、レポートを書き終えたら、確認用のスクリプトで、分析の出力とレポートを比べる。

```text
python scripts/check_report.py <分析の出力.md> <レポート.html>
```

スクリプトは、次の項目を確認する。**「要修正」が1件でもあれば直し、もう一度実行する。「要確認」は1件ずつ見て、問題がないかを判断する。**

| 確認すること | 基準 | 区分 |
| --- | --- | --- |
| 証拠ラベルの数 | [事実]・[推定]・[仮説]・[不在確認] のそれぞれで、レポートの数が分析の出力の数以上ある（凡例の `.cards.legend` は数えない） | 要修正 |
| 実行したPhase | 分析の出力の Coverage Matrix にあるPhaseが、すべてレポートに出てくる | 要修正 |
| 数値 | 分析の出力にある2桁以上の数値が、レポートにある。表記を変えた場合（例: $40M → 4,000万ドル）は見つからないと表示されるので、1つずつ確かめる | 要確認 |
| 本文の長さ | レポートの本文（付録を除く）が、分析の出力より長い。前提・用語・具体例を足すので、短いのは省略の兆候である | 要確認 |
| 結論 | 各章・各節の最初に「結論」があり、2文以内である | 要修正 |
| 図 | 各章・各節に、関係を表す図が1つ以上ある | 要修正 |
| 図の説明の文章 | 各図の直前か直後に、40字以上の段落がある（3.1） | 要修正 |
| 図の中の文 | 図の中の文と、箇条書きの各項目が、句点で終わる文になっている（3.1） | 要修正 |
| 使わない形容 | 5章の語がない | 要修正 |
| ローカルの情報 | ファイルパスや作業フォルダの名前がない（9章） | 要修正 |
| テンプレートの残り | 【】、部品の見本の節、骨組みの枠（`.box.skeleton`）が残っていない | 要修正 |
| 説明の粒度 | 各章・各節に粒度の表示がある | 要確認 |

Python が使えない環境では、同じ項目を手で確認する。少なくとも、証拠ラベルの数を種類ごとに数えて比べることと、各図の前後に説明の文章があることは、必ず確認する。

スクリプトが見るのは、数と形である。スクリプトの確認をすべて通っても、説明の筋道が正しいとは限らない。10章の完成条件は、スクリプトの結果とは別に確認する。

## 8. HTMLの作り方

### 8.1 章ごとに書き足す

レポートを1回の出力で書き切ろうとしない。1回で書ける量には上限があるので、1回で全体を書こうとすると、後半の章ほど説明が短くなる。

1. テンプレートをコピーし、表紙・目次・結論・第0章・全体像までを書いて、ファイルに保存する。
2. 本文の章を、1回に1章ずつ書き足す（Full Strategy では、1回に1〜3節）。書き足すたびに、分析の出力の対応するセクションにある主張・数値・証拠ラベル・表の行が、すべて入っているかを確かめてから、次の章に進む。
3. 書く量が上限に近づいたら、章や節の途中で区切り、次の書き足しで続きを書く。残りの量が多いことを理由に、後半の章を短くしない。
4. 最後に、弱いところ・次に確かめること・まだ分かっていないこと・付録を書き足す。
5. 7.1 の取りこぼしの確認を行う。

### 8.2 HTMLのきまり

* `assets/report-template.html` をコピーして使う。`<style>` はそのまま使い、本文はテンプレートの部品を組み合わせて作る。【】の文はすべて置き換え、使わない部品は削除する。
* 1ファイルで完結させる。JavaScript は使わない（テンプレートの部品だけで図を描ける）。外部のフォントや画像も読み込まない。外部のフォントを読み込むと、ネットワークにつながらない環境では、読み込みが終わるまで本文が表示されないことがあるためである。フォントは、利用者の環境にあるもの（テンプレートの CSS 変数で指定済み）を使う。
* 見出し（h1〜h4）の階層を、内容の階層と一致させる。
* 色だけで意味を伝えない。証拠ラベルは文字でも示し、矢印と枠には文字のラベルを付ける。
* スマートフォンの幅（360px程度）でも、横スクロールなしで読めるようにする。表だけは `.scroll` の枠に入れて、横スクロールを許す。
* 図を `<svg>` で描いてもよい。その場合も、文字のラベルを図の中に入れ、色はCSS変数を使って、ダークモードでも読めるようにする。

## 9. 保存と提示

* **ファイル名:** レポートは `report-<対象の名前>-<YYYYMMDD>.html`、分析の出力は `analysis-<対象の名前>-<YYYYMMDD>.md` とする。
* **保存先:** ユーザーの指定があればそこにする。なければ、作業中のフォルダ（分析の対象資料があるフォルダ）にする。
* **公開しない:** ローカルのファイルとして保存する。ユーザーが明示的に求めない限り、外部のサービスに公開しない。
* **本文にローカルの情報を書かない:** レポートの本文に、ローカルのファイルパスや作業フォルダの名前を書かない。対象は、製品名や事業名など、内容上の名前で示す。
* **チャットでの提示:** 次の順に示す。チャットの説明にも、読み手の要求（`SKILL.md` 9.1）を適用する。
  1. 結論（1〜2文）
  2. ファイルの場所（レポートと、分析の出力）
  3. 章の構成（1章を1行にし、各行に章の結論を1文で書く）
  4. 分析完了かどうかと、残っている確認

## 10. 完成条件

以下をすべて満たしたら、レポートを完成とする。

* [ ] 表紙に、分析の状態（分析完了か。完了でなければ残っている確認）と、説明の粒度がある
* [ ] レポートの冒頭と各章の最初に、「結論」が1〜2文である
* [ ] 第0章（前提）が本文より前にあり、必要な知識、証拠ラベルの読み方、分析の限界を含む
* [ ] 専門用語は、初出の箇所で「この文脈での意味」と例が示されている
* [ ] 抽象的な説明の直後に、具体例が1つある
* [ ] 「AによってBが可能になる」の形の文で、Aの何がBを可能にするかが書かれている
* [ ] すべての文に主語がある
* [ ] 1つの章・カード・枠で扱う概念が1つである
* [ ] 5章の語を使っていない（検索して0件）
* [ ] 結論までの因果の段が、分析の原因の表の段の数以上ある
* [ ] 名詞だけの箇条書き・表のセルがない
* [ ] 各章に、関係（全体像・因果・順序・比較・階層）を表す図が1つ以上ある
* [ ] 分析の結論・数値・証拠ラベル・未検証の扱いが、分析の出力と一致している。分析の出力の内容を削っていない
* [ ] 本文に、ローカルのファイルパスや作業フォルダの名前がない
* [ ] 各章に、説明の粒度が表示されている
* [ ] 各図の直前か直後に、図を説明する文章（40字以上の段落）がある。図の中の文は、句点で終わる文になっている
* [ ] 章ごと（Full Strategy では1〜3節ごと）に書き足し、後半の章・節の説明を、前半より短くしていない
* [ ] `scripts/check_report.py` を実行し、「要修正」が0件で、「要確認」をすべて見て判断した（Python が使えない場合は、7.1 の項目を手で確認した）
* [ ] （Full Strategy）34の節のすべてに、3章の説明の型を使っている。第7章に、`SKILL.md` 4.3 の9つの組み合わせの結果がある。付録に、38セクションとの対応表がある

| 「Moat は Distribution、Workflow、Standard」（用語の羅列） | 階層図の各枝に文を置く: 「開発者が使っている Agent の部品に、自社の判断機能が標準で入っている（Distribution）」→「開発者が、判断の形式を前提にコードを書くので、乗り換えると書き直しが要る（Workflow）」…… |
| 「分からない」と言われて、「結論、判断の回数が多いと費用がかさむということです」と言い換える | 6.3 の粒度2のように、段を足し、各段に具体例を付けて書き直す |

## よくある失敗

* 分析の出力の見出しを、そのままHTMLの見出しにする。Phaseの名前や英語の用語が並び、読み手が意味を追えない。
* 図が文章の飾りになっていて、関係（因果・順序・比較・階層）を表していない。
* 図を置いたことで説明した気になり、図の外の文章を書かない。図の枠に収めるために、理由や条件を削り、枠の中を名詞だけにする。
* 1回の出力で全章を書こうとして、後半の章ほど説明が短くなる。
* 「削らない」と書いてあるので確認を省き、証拠ラベルや数値が減ったことに気付かない。
* わかりやすくするために、[仮説] を断定の文にする。
* 具体例として、分析にない数値や事例を作る。
* 「結論」に、まだ説明していない専門用語を詰め込む。
* 「分からない」と言われて、同じ段数・同じ例のまま、言葉だけを変える。
