# Stage C: 伝達と証明（P10〜P17）

Stage C では、Stage A・B で決めた問題と市場の定義を、**相手に伝わる言葉と、疑われても崩れない証拠** に変える。言葉だけが強く、証拠が弱いと、話題にはなっても信頼を失う。

---

## P10: Messaging Architecture

### 目的

相手と使える時間に合わせて、段階的なメッセージを作る。どの段階でも同じことを言っていて、深く知るほど納得が深まる構造にする。

### 入力

P2の再定義された問題、P3の反対仮説、P4の敵、P5のICP（利用者・意思決定者・予算保有者）、P6のカテゴリー名と Point of View、P7の比較軸、P8の自社の位置、P9のPrimitive。

Level 2 の数値（P11）と、各主張を支える Proof（P12）は、このPhaseの後で作る。ここでは仮置きで書き、P11・P12 を終えた後に見直す。

### 手順

**Step 1. Message House を作る**

```text
【屋根】傘となるメッセージ（1文）
【柱1】価値の柱   【柱2】価値の柱   【柱3】価値の柱
【土台】各柱を支える Proof（P12）
```

柱は3つまでにする。4つ以上あると、どれも覚えてもらえない。各柱は、P7の比較軸やP3の反対仮説に対応させる。

**Step 2. 5つのレベルを書く**

| Level | 相手・時間 | 型 |
| --- | --- | --- |
| 1 | 5秒 | 「【敵】ではなく【新しい方法】で、【成果】」 または 「【カテゴリー名】: 【一文定義の要約】」 |
| 2 | 30秒 | 問題（P2）→ 原因 → 解決原理（P3）→ 結果（数値1つ、P11） |
| 3 | 3分 | 2に加えて、仕組み（P9のPrimitive）、既存の方法との違い（P7）、組み合わせ方（P8） |
| 4 | 技術者 | アーキテクチャ、統合方法、API、制約、性能が出る条件 |
| 5 | 専門家 | 設計思想、前提条件、性能が出ない条件、既知の限界、評価方法 |

Level 5 では、**性能が出ない条件と既知の限界** を必ず書く。専門家は限界を書かない説明を信用しない。

**Step 3. 役割ごとに言い換える**

P5の役割ごとに、Level 2 を言い換える。

| 役割 | 関心 | 強調すること |
| --- | --- | --- |
| 利用者 | 自分の作業が楽になるか、すぐ使えるか | 作業時間、導入の簡単さ |
| 意思決定者 | チームの成果が上がるか、リスクはないか | 成果の指標、信頼性、移行のしやすさ |
| 予算保有者 | 費用に見合うか | 現状コストとの比較（P1）、回収期間 |

**Step 4. メッセージをテストする**

| テスト | 方法 | 不合格の場合 |
| --- | --- | --- |
| 5秒テスト | Level 1 だけを見せて、何の製品か説明してもらう | 言葉を具体的にする |
| So What テスト | 各文に「だから何？」と3回問う。機能 → 利点 → 顧客にとっての価値 までたどり着くか | 価値の段まで書き足す |
| 競合入れ替えテスト | 製品名を競合の名前に入れ替えても、文が成り立つか | 成り立つなら差別化になっていない。P7の比較軸を入れる |
| 証拠テスト | 各文に、対応するProof（P12）があるか | ないなら [仮説] とするか、文を弱める |

**Step 5. 使わない言葉を決める**

以下の言葉は、証拠がない限り使わない。

* 「世界初」「最高」「革命的」「次世代」などの根拠のない最上級
* 「AI活用」「DX」「効率化」など、どの製品にも当てはまる言葉
* 顧客が使わない社内用語、技術用語

### 深掘りの問い

* Level 1 を聞いた顧客は、次に何を質問するか。その質問への答えは Level 2 にあるか。
* 競合がこのメッセージを見たとき、反論できる点はどこか（P17へ）。
* このメッセージを、顧客が同僚に説明するときに、そのまま使えるか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| Level 1: 「AIで業務を効率化する次世代プラットフォーム」 | Level 1: 「Decisions, not strings. 文章を生成せずに、判断だけを返すAI」 |
| Level 2: 「高速で安価、使いやすいAPIです」 | Level 2: 「Agentは1タスクで何十回も判断するが、判断のたびに文章を生成するLLMを呼んでいる。判断に文章は要らない。○○は選択肢と確率だけを直接返すので、同じ判断が1/100以下の時間で終わる（条件は○○）」 |

### よくある失敗

* レベルごとに違うことを言っている。
* Level 1 に機能名を並べる。
* 全ての役割に同じメッセージを使う。

### 出力

```text
■ Message House
■ Level 1〜5
■ 役割ごとの Level 2
■ テストの結果
■ 使わない言葉
```

### 次への受け渡し

* Level 1〜3 → P13（デモの台本）、P20（ローンチ記事）
* 各主張 → P12（Proofとの対応）
* 役割ごとのメッセージ → P18（営業資料）

## P11: Quantitative Hook & Number Framing

### 目的

製品の価値を、一目でわかる数値で示す。数値は、言葉よりも速く伝わり、SNSでそのまま引用される。ただし、条件のない数値や誇張した数値は、発覚したときに信頼を大きく損なう。

### 入力

P1の現状のコスト、P7の比較軸と測り方。

### 手順

**Step 1. 比較対象を正直に選ぶ**

比較対象は、**ICPが今実際に使っている代替手段** にする。最も遅い・最も高い代替手段と比べて大きな倍率を出すのは誤認を招く。

**Step 2. 数値の候補を出す**

以下の型から、P7の比較軸に合うものを選ぶ。

X倍高速 / X分の1コスト / X倍の処理量 / X分短縮 / X人分の工数削減 / X%の精度向上 / X%のエラー削減 / X秒で導入 / X行で利用可能

**Step 3. 主役の数値を1つ決める**

数値を並べすぎると、どれも覚えてもらえない。**主役の数値を1つ** 決め、他は補助にする。主役は、P7の比較軸を表す数値にする。

**Step 4. 条件を書く**

数値ごとに、以下を必ず書く。

```text
数値:
比較対象:
測定条件（データ、タスク、環境）:
代表値か最大値か（平均・中央値・最大値のどれか）:
再現方法（公開しているか）:
```

最大値を使う場合は、「最大」と明記し、代表的な値も併記する。

**Step 5. 見せ方（Number Framing）を選ぶ**

同じ数値を、複数の表現で書いてみる。

| 見せ方 | 例 |
| --- | --- |
| 単位を変える | $0.042 / million tokens ↔ $42 / billion tokens |
| 時間に換算 | 70ms ↔ 1秒間に14回判断できる |
| 顧客の業務に換算 | 判断1回0.004円 ↔ 月100万回の判断で4,000円 |
| 相対 ↔ 絶対 | 99%削減 ↔ 月300万円 → 3万円 |

最も理解しやすく、かつ誤解を招かない表現を選ぶ。

**誤認を招く表現の例（禁止）**

* 条件の違う数値を並べて比較する
* 最大値を平均値のように見せる
* 小さい絶対値を、大きな割合で見せる（2件 → 4件を「100%増加」と書く）
* グラフの縦軸を0から始めずに、差を大きく見せる

### 深掘りの問い

* この数値を見た競合は、どの条件を突いて反論してくるか。
* 顧客が自分の環境で試したとき、同じ数値が出るか。出ないなら、どれくらいの値になるか。
* この数値は、1年後も意味を持つか（競合が追いついたら意味がなくなるか）。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「100倍速い！」 | 「判断1回の完了時間: 中央値70ms（大型LLMでの同じ判断は中央値7.2秒）。条件: 社内ベンチマーク（5択の分類タスク1,000件）、比較対象は○○。最大値は193倍だが、代表的な業務では数十倍程度（数値は例）」 |

### よくある失敗

* 最も遅い・最も高い代替手段と比べて、大きな倍率を作る。
* 数値を5つも6つも並べ、どれも覚えてもらえない。
* 最大値だけを載せ、顧客が試したときに再現できず、信頼を失う。

### 出力

| 数値 | 主役／補助 | 比較対象 | 条件 | 代表値／最大値 | 見せ方 | 証拠ラベル |
| --- | --- | --- | --- | --- | --- | --- |

### 次への受け渡し

* 主役の数値 → P10（Level 2）、P13（デモ）、P20（ローンチ）
* 条件 → P12（Proof）、P17（批判への回答）

## P12: Proof Architecture

### 目的

すべての主張に、それを支える証拠を対応させる。証拠のない主張は、話題になるほど疑われ、批判されたときに崩れる。ローンチ前でも作れる証拠はある。

### 入力

P3の反対仮説の証拠、P7の比較軸の測り方、P10の主張、P11の数値。

### 手順

**Step 1. 主張と証拠の対応表を作る**

| 主張 | 証拠の種類 | 現状（あり／なし） | 信頼度 | 証拠ラベル |
| --- | --- | --- | --- | --- |
| 高速 | ベンチマーク | | | |
| 安価 | コスト比較 | | | |
| 正確 | 評価結果 | | | |
| 採用されている | 利用データ | | | |
| 実用できる | 顧客事例 | | | |
| 信頼できる | 第三者の検証 | | | |

**Step 2. 証拠の信頼度を評価する**

信頼度は、以下の順に高い。

1. 第三者による独立した検証（研究者、アナリスト、競合の比較記事）
2. 顧客が自分の言葉で語った成果（名前付きの事例）
3. 誰でも再現できる形で公開したベンチマーク
4. 自社が測定した結果（手法を公開）
5. 自社が測定した結果（手法を非公開）

自社の測定しかない主張は、信頼度が低いことを前提に扱う。

**Step 3. ベンチマークを設計する（必要な場合）**

ベンチマークを作るときは、以下を守る。

* **代表的なタスク**: ICPの実際の業務に近いタスクを使う。自社が得意なタスクだけを選ばない。
* **公正な比較対象**: 比較対象の設定を最適化する（競合の製品を不利な設定で動かさない）。
* **負けも載せる**: 自社が負けるタスクがあれば、それも載せる。負けを隠したベンチマークは、第三者に検証されたときに信頼を失う。
* **再現手順を公開**: データ、コード、設定を公開する。

**Step 4. ローンチ前に証拠を作る方法**

| 方法 | 得られる証拠 |
| --- | --- |
| デザインパートナー（開発段階から協力してくれる顧客） | 名前付きの事例、顧客の発言 |
| 限定的な試験導入 | 実際の業務での数値 |
| 公開ベンチマーク | 再現できる性能比較 |
| 早期アクセスの提供（研究者・開発者） | 第三者による検証、SNSでの評価 |

**Step 5. 証拠がない主張の扱いを決める**

証拠がない主張は、次のいずれかにする。

* 証拠ができるまで、メッセージから外す
* [仮説] として扱い、P32で証拠を作る実験を計画する
* 主張を弱めて、今ある証拠で支えられる範囲にする

### 深掘りの問い

* 最も懐疑的な技術者がこの証拠を見たら、どこを疑うか。
* この証拠は、ICPの意思決定者が稟議書に添付できる形になっているか。
* 競合が同じベンチマークを実行したら、結果はどうなるか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「多くの企業で効果が実証されています」 | 「主張『判断コストが1/100』: 証拠は公開ベンチマーク（データとコードをGitHubで公開、信頼度3）。主張『実業務で使える』: 証拠なし [仮説]。デザインパートナー3社で8週間の試験導入を行い、名前付き事例を作る（P32 #1）」 |

### よくある失敗

* 自社に有利なタスクだけでベンチマークを作り、第三者に再検証されて崩れる。
* 「多くの企業で実証済み」のように、証拠の中身を示さない。
* 証拠がない主張を、メッセージの中心に置いたままにする。

### 出力

```text
■ 主張と証拠の対応表（信頼度つき）
■ ベンチマークの設計（必要な場合）
■ 証拠がない主張の扱い
```

### 次への受け渡し

* 証拠 → P13（デモ）、P17（批判への回答）、P20（ローンチ材料）
* 証拠がない主張 → P32

## P13: Demo Strategy

### 目的

言葉と数値では伝わらない価値を、見せて伝える。デモには2種類ある。**購買理由を作る Business Demo** と、**拡散理由を作る Viral Demo** である。この2つを混ぜると、どちらの目的も果たせない。

### 入力

P1のワークフロー（Business Demo の題材）、P4の Before / After、P5のICP、P9のPrimitive、P10の Level 1〜3（デモの台本）、P11の主役の数値、P12の証拠。

### 手順

**Step 1. Business Demo を設計する**

| 要素 | 内容 |
| --- | --- |
| 題材 | ICPの実際の業務（P1のワークフロー） |
| 構成 | Before（今のやり方）→ After（製品を使ったやり方）→ 数値の比較 |
| 見せる数値 | P11の主役の数値。ICPの環境に近い条件で |
| 長さ | 3〜10分 |
| 最後に示すもの | 導入の手順と、自社の環境で試す方法 |

最初の30秒で、Before と After の違いが見えるようにする。

**Step 2. Viral Demo を設計する**

Viral Demo は、実務でなくてよい。以下の条件を満たすものを考える。

| 条件 | 問い |
| --- | --- |
| 一目でわかる | 音声や説明がなくても、何がすごいかわかるか |
| 意外性 | 「それにも使えるのか」と驚かせる題材か（ゲーム、ロボット、意外な分野など） |
| 短さ | 60秒以内に収まるか |
| 能力の正しさ | 製品の実際の能力を正しく表しているか。演出で誇張していないか |
| 真似しやすさ | 見た人が「自分も試したい」と思い、実際に試せるか |

例: 判断の速さを見せるために、AIにゲームをリアルタイムで操作させる。業務の題材よりも、「高速な判断を大量に回せる」ことが一目で伝わる。

**Step 3. 見た人を試用につなげる**

どちらのデモにも、見た人がすぐに試せる導線を付ける（P22）。デモを見て興味を持った人が、登録や設定で止まると、デモの効果が消える。

**Step 4. 失敗する条件も見せる（Business Demo）**

製品が苦手な入力や条件を、あえて見せる。限界を示すことで、残りの主張の信頼度が上がる。

### 深掘りの問い

* Viral Demo を見た人は、SNSにどんな一言を添えて共有するか。
* Business Demo を見た意思決定者は、社内で何と説明するか。
* デモで使った条件と、顧客の本番環境の条件は、どれくらい違うか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「製品の機能を紹介するデモ動画を作る」 | 「Business Demo: 問い合わせ振り分けの業務で、現在のLLM方式と並べて1,000件を処理し、時間とコストを比較する。Viral Demo: AIがレトロゲームをリアルタイムで操作する60秒動画。判断の速さが一目で伝わる。どちらも、概要欄から3分で試せるPlaygroundにつなぐ」 |

### よくある失敗

* Business Demo と Viral Demo を1本にまとめ、業務の説明が長すぎて拡散されず、演出が強すぎて購買の根拠にもならない。
* 演出や編集で、製品の実際の能力を誇張する。
* デモを見た人が試す導線がなく、関心がそこで止まる。

### 出力

```text
■ Business Demo（題材、構成、見せる数値、長さ、試用への導線）
■ Viral Demo（題材、満たす条件、試用への導線）
```

### 次への受け渡し

* デモ → P20（ローンチ材料）、P23（UGC のきっかけ）

## P14: Founder Story

### 目的

「なぜこのチームが、この問題を解けるのか」を、経歴と経験から説明する。新カテゴリーの主張は、誰が言うかで信頼度が大きく変わる。

### 入力

P2の再定義された問題と「なぜ今まで解かれなかったか」。

### 手順

**Step 1. 4つの問いに答える**

```text
なぜこの問題に気付いたか（どんな経験から）
→ なぜ既存の方法では解けないと思ったか（何を見たから）
→ なぜ自分たちが解けるのか（どんな知識・技術・立場があるから）
→ なぜ今なのか（P15）
```

**Step 2. 「獲得した秘密」を特定する**

創業者が、特定の経験を通じて知った、他の人がまだ知らないこと（Earned Secret）を1つ書く。例: 「既存のLLMを作る側にいたので、Chat形式がソフトウェアへの組み込みに向かない理由を内側から知っている」。

**Step 3. 物語の型を選ぶ**

| 型 | 内容 |
| --- | --- |
| 内部からの転換 | 既存のパラダイムを作る側にいた人が、その限界に気付いて逆方向のものを作る |
| 現場の当事者 | 自分自身がその問題に苦しんでいた |
| 異分野からの持ち込み | 別の分野で当たり前の方法を、この分野に持ち込んだ |

**Step 4. 経歴と問題に関連がない場合**

無理に物語を作らない。代わりに、以下で信頼を補う。

* チームの技術的な実績（論文、OSS、過去の製品）
* 顧客との共同開発の経緯（デザインパートナーの存在）
* 実測データと公開ベンチマーク

Coverage Matrix には「対象外」と理由を書く。

**経歴や経験を誇張・捏造してはいけない。**

### 深掘りの問い

* この物語を聞いた人は、「この人たちなら解けそうだ」と思うか、「よくある起業ストーリーだ」と思うか。
* Earned Secret は、競合の創業者も持っているものではないか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「創業者は長年この業界で活躍してきました」 | 「創業者は、LLMを人間との会話に適応させる手法を作る側にいた。その経験から、Chat形式がソフトウェアへの組み込みに向かない理由を内側から知っている（Earned Secret）。型は『内部からの転換』」 |

### よくある失敗

* 経歴を並べるだけで、それが問題を解ける理由につながっていない。
* 問題と関係のない経歴を、無理に物語にする。
* 経歴や経験を誇張する。

### 出力

```text
■ 4つの問いへの答え
■ Earned Secret
■ 物語の型
■ （関連がない場合）代わりの信頼の源
```

### 次への受け渡し

* Founder Story → P20（ローンチ材料）、P25（メディア・投資家への説明）

## P15: Timing Analysis

### 目的

「なぜ3年前ではなく今なのか」に答える。答えられない場合、その機会は3年前から存在していたことになり、すでに誰かが解いているか、解けない理由があるかのどちらかである。

### 入力

P1の「崩れつつある兆候」、P2の構造原因。

### 手順

**Step 1. 変化を洗い出す**

以下の観点で、最近（目安として1〜3年以内）起きた変化を探す。

技術の変化 / 法規制 / コストの低下 / 顧客の行動の変化 / APIの普及 / インフラの普及 / 競合の変化 / 開発者の行動の変化 / 経済環境 / 社会の変化

**Step 2. 変化を3つの条件で評価する**

| 条件 | 問い |
| --- | --- |
| 最近性 | その変化は最近起きたか |
| 実現性 | その変化によって、以前は作れなかった製品が作れるようになったか、以前は成立しなかった事業が成立するようになったか |
| 未開拓性 | 既存の大手は、まだその変化を活かしていないか。活かしていないなら、その理由は何か |

**Step 3. 「早すぎる」リスクを確認する**

変化が始まったばかりだと、顧客がまだ準備できていない場合がある。以下の兆候で、市場の準備度を確認する。

* ICPの顧客が、すでにその変化に関わる予算やチームを持っているか
* 関連する検索、求人、カンファレンスの話題が増えているか
* 顧客が、変化に関わる問題を自分から話し始めているか

**Step 4. 1文で答える**

> 今なのは、【変化】によって【以前は成り立たなかったこと】が成り立つようになり、かつ【既存の提供者】は【理由】でまだそれを活かしていないからである。

答えられない場合は、「タイミングの優位はない」と明記する。

### 深掘りの問い

* その変化は、競合にも同じように見えているか。見えているなら、なぜまだ動いていないのか。
* その変化が逆戻りする可能性はあるか（規制の強化、コストの再上昇など）。
* 3年後に同じ問いをしたら、答えはどう変わっているか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「AIが注目されているから今」 | 「今なのは、AIシステムが単発の応答から Agent Loop に移り、1タスクあたりの判断回数が数十倍に増えたからである。判断のコストが、以前は無視できる大きさだったが、今は費用の大部分を占めるようになった。既存のLLM提供企業は、トークン量で課金しているため、判断を安くする動機が弱い」 |

### よくある失敗

* 「AIブームだから」「DXが進んでいるから」のように、どの製品にも当てはまる変化を理由にする。
* 変化が本当に製品を可能にしたのかを説明しない。
* 市場がまだ準備できていない「早すぎる」リスクを見ない。

### 出力

```text
■ 変化の一覧と評価
■ 市場の準備度
■ 「なぜ今か」の1文
```

### 次への受け渡し

* なぜ今か → P6の Point of View（仮置きした1段目を更新する）、P10、P14、P20

## P16: Controversy Strategy

### 目的

議論を呼ぶ主張を、意図的に設計する。議論は、市場に「このカテゴリーとは何か」を学ばせる。ただし、検証できない主張や、パートナーを攻撃する主張は、信頼と関係を壊す。

### 入力

P3の反対仮説、P4の敵、P8のパートナー候補、P12の証拠。

### 手順

**Step 1. 主張を作る**

P3の反対仮説から、以下の条件を満たす主張を作る。

* 反論できる（議論の余地がある）
* 検証できる（証拠で白黒がつく）
* 既存の常識とぶつかる
* 製品の能力で証明できる
* 誤解を招かない

**Step 2. 範囲を限定する**

```text
× 「○○は不要である」
○ 「△△の場合、○○を使う必要はない」
```

**Step 3. 反論と回答を準備する**

| 主張 | 予想される反論 | 反論のうち正しい部分 | 回答 | 使う証拠 |
| --- | --- | --- | --- | --- |

**Step 4. リスクを評価する**

| 確認すること | 問い |
| --- | --- |
| パートナーへの影響 | P8のパートナー候補を攻撃していないか |
| 顧客への影響 | 今の方法を使っている顧客を、愚かに見せていないか |
| 炎上のリスク | 主張が切り取られたときに、誤解される表現になっていないか |
| 撤回のコスト | 主張が間違っていた場合、どう訂正するか |

### 深掘りの問い

* この主張が切り取られてSNSで広まったとき、どう読まれるか。
* この主張に最も強く反発するのは誰か。その人は、自社の顧客やパートナーか。
* 主張が間違っていたと判明したとき、どう訂正するか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「LLMはもう古い」（範囲なし、パートナーを攻撃、検証できない） | 「出力が決められた選択肢である判断に、文章生成は要らない。予想される反論『Structured Outputs で十分』には、同じ判断タスクでの遅延とコストの比較で答える。LLM自体は否定しない（生成が必要な場所では引き続き使う）」 |

### よくある失敗

* 注目を集めることが目的になり、検証できない主張をする。
* パートナーや顧客を攻撃する主張をする。
* 反論への回答を準備せずに主張し、最初の反論が定着する。

### 出力

```text
■ 主張（範囲つき）
■ 反論と回答の表
■ リスク評価
```

### 次への受け渡し

* 主張 → P20（ローンチ時の話題）、P25（第三者の議論のきっかけ）

## P17: Criticism Pre-Mortem

### 目的

ローンチ後に来る批判を、事前に予想して準備する。批判への回答を準備していないと、最初の批判が定着し、製品の評価として固まってしまう。

### 入力

P6〜P12の結論。P0.5の先行事例の表と調査の記録。

### 手順

**Step 1. 批判する人を想定する**

以下の立場から、それぞれ最も厳しい批判を考える。

| 立場 | 批判の方向 |
| --- | --- |
| 懐疑的な技術者 | 「技術的に新しくない」「ベンチマークが偏っている」 |
| 競合のプロダクトマネージャー | 「うちの製品でもできる」「すぐに追いつける」 |
| アナリスト・投資家 | 「市場が小さい」「Moatがない」 |
| ICPの予算保有者 | 「乗り換えるほどの差がない」「リスクが大きい」 |
| 既存の顧客（代替手段の利用者） | 「今のやり方で困っていない」 |

**Step 2. 典型的な批判を確認する**

以下の批判は必ず検討する。製品に固有の批判があれば追加する。

```text
昔から存在する / ○○で代用できる / ただの○○ / 大手が作れば終わる
技術的Moatがない / 特定のBenchmarkだけ / 実際の精度が低い
用途が限定的 / 市場が小さい / 価格競争になる
```

**Step 3. 外部で事実を確認する**

以下の4つの批判は、**外部で調べた結果を「事実確認」の欄に書くことを必須とする。** 自分の知識や、製品側の説明だけで回答を書いてはいけない。

| 批判 | 調べること |
| --- | --- |
| 昔から存在する | 同じ機能・手法が、以前から公開・販売されていないか（P0.5の表を出発点にし、批判の言い方で追加検索する） |
| ○○で代用できる | ○○の一次資料（公式ドキュメント、仕様）で、実際にできることとできないこと |
| ただの○○ | ○○の定義と、○○との違いが、一次資料で説明できる違いか |
| 大手が作れば終わる | 大手の既存製品と、直近の新機能の発表・ロードマップ |

事実確認の欄には、証拠ラベル（[事実: 出典] / [不在確認: 調査範囲]）を付ける。外部で調べられなかった場合は「未確認」と書き、その批判への回答は [仮説] として扱う。

**Step 4. 批判を最も強い形にしてから答える**

批判を弱い形で紹介して反論するのではなく、最も説得力のある形（Steelman）に書き直してから答える。

| 批判（最も強い形） | 事実確認（出典・調査範囲） | 正しい部分 | 誤っている部分 | 回答 | 必要なProof |
| --- | --- | --- | --- | --- | --- |

**正しい部分は認める。** 全否定する回答は信頼を失う。

**Step 5. 批判を4種類に分けて対応する**

| 種類 | 対応 |
| --- | --- |
| 誤解による批判 | メッセージ（P10）を直す |
| 正当な批判（一部が正しい） | 製品を直すか、主張の範囲を狭める |
| **前提を覆す批判**（調べた結果、批判のほうが正しかった。例: 同じものがすでに存在した） | 戦略の調整やメッセージの修正で済ませず、`SKILL.md` 4.4 の差し戻しのルールに従って、P0.5・P2・P3・P6 などの上流に戻って見直す |
| まだ判断できない批判 | 検証する（P32） |

### 深掘りの問い

* 最も広まりやすい批判はどれか（短く、覚えやすく、一部が正しいもの）。
* その批判に、1文で答えられるか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「批判: ただの分類器 → 回答: 違います。当社独自の技術です」（外部で調べていない） | 「批判（最も強い形）: 汎用の zero-shot 分類器は以前から存在し、機能的に同じである。事実確認: 公開されている zero-shot 分類の手法とライブラリは、分類のラベルを実行時に自然言語で指定できる [事実: 各ライブラリの公式ドキュメント]。正しい部分: 分類という機能も、ラベルを実行時に定義できることも新しくない。『実行時に定義できる』を新しさとして主張していた場合は、その主張を取り下げる。誤っている部分: 未確定。残る差の候補は、長い非構造の状態を入力にした判断の精度と、確率の較正 [仮説]。対応: 前提を覆す批判として P0.5 の判定を『部分的に解決済み』に直し、残る隙間を P2・P6 で再定義する。必要なProof: 既存の zero-shot 分類器との比較ベンチマーク」（例） |

### よくある失敗

* 批判を弱い形で紹介し、簡単に反論できるように見せる。
* 正しい部分を認めず、全面的に否定する。
* 批判への回答を用意しただけで、メッセージや製品を直さない。
* 外部で調べずに、「既存の○○にはできない」と回答する。調べると、既存の○○にできることが多い。
* 批判のほうが正しいとわかったのに、メッセージの言い回しの修正だけで済ませる。

### 出力

```text
■ 想定した批判者と批判
■ 批判と回答の表（事実確認の欄に出典・調査範囲）
■ 対応の分類（メッセージ修正／製品修正／上流への差し戻し／検証）
```

### 次への受け渡し

* 誤解による批判 → P10を修正
* 前提を覆す批判 → P0.5・P2・P3・P6 へ差し戻し
* 必要なProof → P12、P32
* 「大手が作れば終わる」 → P28
