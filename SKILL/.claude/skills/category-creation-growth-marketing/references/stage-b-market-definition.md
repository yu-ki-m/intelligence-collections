# Stage B: 市場定義（P5〜P9）

Stage B では、Stage A で見つけた問題を、**誰に対して、どの土俵で、どんな役割として** 提供するかを決める。ここで決めた市場の定義によって、顧客が自社を何と比べるかが決まる。

---

## P5: ICP & Beachhead

### 目的

最初に確実に勝つ顧客セグメント（Beachhead）を決める。カテゴリーは「誰にとっての新しい分類か」が決まらないと定義できない。また、全員を狙うと、メッセージもチャネルも薄まり、どのセグメントでも「2番目に良い選択肢」になってしまう。

### 入力

P1のワークフローと担当者、P2の再定義された問題と問題の強さ。

### 手順

**Step 1. セグメントの候補を出す**

業種、企業規模、技術スタック、役割、利用シーンなどで区切り、候補を3〜5個出す。区切り方は「問題の強さが違う」単位にする。業種で区切っても問題の強さが変わらないなら、業種ではなく利用シーンで区切る。

**Step 2. 候補を評価する**

| 評価軸 | 問い | 点数（1〜5） |
| --- | --- | --- |
| 課題の強さ | P2の問題を最も強く感じているか。回避策やお金を使っているか | |
| 到達しやすさ | 安く届くチャネル（P21）があるか。コミュニティとしてまとまっているか | |
| 導入のしやすさ | 意思決定が速いか。購買・セキュリティ審査が軽いか | |
| 支払い能力 | 予算があるか | |
| 波及力 | そこで勝つと、隣のセグメントに広がるか | |
| 競合の薄さ | 既存製品が十分にカバーしていないか | |

合計点だけで決めない。**課題の強さが低いセグメントは、他の点数が高くても選ばない。** 課題が弱い顧客は、試しても使い続けない。

**Step 3. Beachhead の大きさを確認する**

Beachhead は、以下の両方を満たす大きさにする。

* **小さすぎない**: そこだけで、次の資金調達や事業継続に必要な実績（顧客数、売上、事例）が作れる。
* **大きすぎない**: 限られたリソースで、そのセグメントの中で明らかな1番手になれる（目安として、18か月程度で対象顧客の相当な割合に使われている状態を目指せる）。

**Step 4. ICPを記述する**

```text
業種・規模・技術スタック:
利用者（毎日使う人）:
意思決定者（導入を決める人）:
予算保有者（お金を払う部門・人）:
導入を検討し始めるきっかけ（トリガー）:
現在の代替手段:
成功の定義（導入後に何が変われば「成功」か。数値で）:
```

利用者・意思決定者・予算保有者が同じ人かどうかは、P18 GTM Motion の選択に直結する。

**Step 5. 対象外の顧客（Anti-ICP）を書く**

「この条件に当てはまる顧客は、今は追わない」という条件を書く。例: 「オンプレミス環境でしか動かせない企業」「判断の種類が月に数件しかない企業」。Anti-ICP を書くことで、営業やサポートのリソースが分散するのを防ぐ。

**Step 6. 広げる順序を決める**

```text
Beachhead → 隣接セグメント1 → 隣接セグメント2 → …
```

それぞれの矢印について、なぜ広がるのかを書く。広がる理由は、主に以下のいずれかである。

* 同じ技術やデータを使っている（製品をそのまま使える）
* 同じチャネルで届く（追加の営業コストが小さい）
* Beachhead の顧客事例が、そのまま信頼の根拠になる
* Beachhead の顧客が、隣接セグメントの顧客と取引している

### 深掘りの問い

* このセグメントの顧客は、今週この問題のために何をしているか。
* 製品が明日なくなったら、このセグメントの顧客は困るか（「とても困る」と答える顧客が4割を超えるかが、一般的な目安とされる）。
* このセグメントで勝ったとき、隣のセグメントの顧客は、その事実を知る経路を持っているか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「AIを活用したい企業」 | 「Agentを本番環境で運用している、従業員50〜500人のSaaS企業のプラットフォームチーム。月のLLM費用が数百万円を超え、Agentの判断ステップの遅延が問題になっている。利用者はエンジニア、意思決定者はエンジニアリングマネージャー、予算はインフラ費用から出る。トリガーは、LLMの請求額が予算を超えたとき」（例） |

### よくある失敗

* 「中小企業全般」「開発者全般」のように広すぎる。
* 支払い能力や市場規模で選び、課題の強さを軽視する。
* 利用者と予算保有者を区別しない。

### 出力

```text
■ セグメント候補と評価表
■ 選んだBeachheadと、その大きさの確認
■ ICPの記述
■ Anti-ICP
■ 広げる順序と、その理由
```

### 次への受け渡し

* ICP → P6（誰にとってのカテゴリーか）、P10（誰向けの言葉か）、P13（Business Demoの題材）
* 利用者・意思決定者・予算保有者 → P18 GTM Motion
* 到達チャネル → P21 Distribution
* 成功の定義 → P22（最初の価値。P26 の Activation の定義にもなる）

## P6: Category Decision

### 目的

自社が戦う市場の定義を選ぶ。新カテゴリーを作るか、既存カテゴリーの中のサブカテゴリーにするか、既存カテゴリーの中で位置取りを変えるか。**新カテゴリーは強力だが、最もコストが高い選択肢** である。その判断を、勢いではなく根拠で行う。

### 入力

P0.5の判定と残る隙間、P2の再定義された問題と顕在度、P3の反対仮説、P4の敵、P5のICP。

### 手順

**Step 1. 既存カテゴリーで比較された場合を想定する**

P0.5 の先行事例が、どの既存カテゴリーに属するかを出発点にする。P0.5 が「部分的に解決済み」の場合、自社の違いとして使えるのは残る隙間だけである。

```text
顧客が今の製品を見たとき、頭に浮かぶ既存カテゴリー:
そのカテゴリーで比較される相手:
そのカテゴリーの標準的な比較軸:
その比較軸での自社の勝ち負け:
```

**Step 2. 3つの選択肢を評価する**

| 選択肢 | 選ぶ条件 | コスト | リスク |
| --- | --- | --- | --- |
| **A. 新カテゴリー** | 既存カテゴリーで比較されると、自社の価値が構造的に伝わらない／不利になる。問題が潜在的で（P2）、名前を付けること自体に価値がある | 最大。市場教育が必要で、立ち上がりが遅い | 市場が立ち上がる前に資金が尽きる。顧客側に予算の枠がない |
| **B. サブカテゴリー** | 既存カテゴリーの枠組みは使えるが、「○○向けの△△」「△△の新しい型」として区別すると優位が明確になる | 中 | 既存カテゴリーの大手が、同じサブカテゴリーを名乗る |
| **C. 再ポジショニング** | 既存カテゴリーの比較軸でも勝てる、または比較軸の重み付けを変えるだけで勝てる | 最小。検索需要と予算枠がすでにある | 差別化が小さく、価格競争になりやすい |

以下の判定表を埋める。

| 判定の問い | A | B | C |
| --- | --- | --- | --- |
| 既存カテゴリーの比較軸で、自社は勝てるか | 勝てない | 一部で勝てる | 勝てる |
| 問題は顧客に認識されているか（P2） | 潜在 | どちらでも | 顕在 |
| 市場教育に使える資金・時間・話題性があるか | ある | ある程度 | 不要 |
| 顧客は既存カテゴリーの名前で予算を取っているか | 取っていない、または新しい予算を作れる | 取っている | 取っている |
| 第三者が新しい名前を使い始める見込みはあるか（P25） | ある | ある程度 | 不要 |

**判定と、他の2つを選ばなかった理由の両方を書く。**

**Step 3. 予算の出どころを確認する（A・Bの場合）**

新カテゴリーには、顧客側に予算の枠がない。以下のどれで予算を確保するかを書く。

* 既存の予算を置き換える（例: LLMの利用料の一部を、判断専用モデルの利用料に置き換える）
* 人件費を置き換える（例: 目視確認の工数を削減した分を充てる）
* 新しい予算を作る（最も難しい。経営層への提案が必要になる）

**Step 4. 名前を作る（A・Bの場合）**

候補を5個程度出す。名前の作り方には、主に以下の型がある。

| 型 | 例 | 長所 | 短所 |
| --- | --- | --- | --- |
| 修飾語＋既存の名詞 | Decision Model、Revenue Intelligence | 意味が推測しやすい | 既存カテゴリーとの違いが弱くなりやすい |
| 既存の概念の借用 | System One Model（認知科学の System 1 から） | 既存のメンタルモデルに乗れる。話題になりやすい | 元の概念を知らない人には伝わらない |
| 新しい造語 | （独自の単語） | 独占しやすい | 意味が伝わるまで時間がかかる |
| 対比による命名 | 「Chat AI」に対する「System AI」 | 敵（P4）との違いがすぐにわかる | 対比相手が変わると意味が弱くなる |

各候補を以下の要件で評価する。

| 要件 | 確認方法 |
| --- | --- |
| 短い・発音できる | 声に出して言ってみる |
| 検索できる | 検索して、既存の別の意味と衝突しないか確認する |
| 意味を推測できる | 知らない人に聞かせて、何のカテゴリーか推測してもらう |
| 製品名と独立している | 他社が名乗っても不自然でないか |
| 会話で使える | 「うちも○○を入れようか」と自然に言えるか |
| 既存カテゴリーとの違いが伝わる | 既存カテゴリー名と並べて、違いがわかるか |
| 機能名に限定されない | 機能が増えても、名前が狭すぎないか |
| 複数企業が参加できる | 「○○の市場」「○○ベンダー」と言えるか |

**Step 5. 一文定義を書く**

A・Bの場合:

> ○○とは、【入力】を受け取り、【従来とは異なる原理】によって、【成果】を提供する製品カテゴリーである。

Cの場合（ポジショニングステートメント）:

> 【ICP】にとって、【製品】は【既存カテゴリー】の中で唯一【差別化要素】を持つ製品である。なぜなら【理由】だからだ。

**Step 6. カテゴリーの視点（Point of View）を書く（A・Bの場合）**

カテゴリー名だけでは市場は動かない。以下の4段で、カテゴリーの主張を短い文章にまとめる。これが、後のメッセージ（P10）、ローンチ記事（P20）、第三者への説明（P25）の元になる。

```text
1. 世界はこう変わった（P1の「崩れつつある兆候」から仮置きし、P15を終えた後に更新する）
2. そのため、古い方法（P4の敵）では○○という問題が起きている（P2）
3. 新しい方法（カテゴリー）は、△△という原理でそれを解く（P3）
4. その結果、顧客は□□ができるようになる
```

### 深掘りの問い

* このカテゴリー名を、競合他社が名乗り始めたら、自社は嬉しいか困るか。嬉しいと思えないなら、カテゴリーではなく製品の機能名になっている可能性がある。
* 顧客の社内で、このカテゴリー名を使って稟議や予算申請が書けるか。
* 3年後に、このカテゴリーに何社くらい参加していそうか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「新カテゴリー『次世代AI判断プラットフォーム』を作る」（理由なし、長い、何でも当てはまる） | 「判定はA（新カテゴリー）。既存の『分類器』カテゴリーではBERTなどの分類器や小型LLMと、既存の精度・価格の軸で比較され、P0.5 で残った隙間（長い非構造の状態を入力にした判断を、LLM並みの精度で、生成のコストなしに返すこと）での違いが伝わらないため。『文章を生成しない』ことは、LLMと比べたときの違いにはなるが、分類器と比べたときの違いにはならない。Bは、『軽量LLM』『汎用分類器』のサブカテゴリーとして名乗ると、比較軸が既存の精度・価格に戻るため選ばない。Cは、既存の比較軸で勝てないため選ばない。予算はLLM利用料の置き換えで確保する。名前は System One Model（認知科学の System 1 を借用し、LLM = System 2 との対比を作る）」 |

### よくある失敗

* 新カテゴリーを作ること自体が目的になる。
* カテゴリー名が、自社の製品名や機能名になっている。
* カテゴリー名を決めたが、その主張（Point of View）がない。

### 出力

```text
■ 既存カテゴリーで比較された場合の想定
■ 判定表と判定（A/B/C）、選ばなかった理由
■ 予算の出どころ（A・B）
■ 名前の候補と評価、推奨（A・B）
■ 一文定義 または ポジショニングステートメント
■ カテゴリーの Point of View（A・B）
```

### 次への受け渡し

* 判定 → 以降のすべてのPhaseの前提
* カテゴリー名と一文定義 → P10、P20、P25、P30
* Point of View → P10、P20のローンチ記事

## P7: Competitive Axis Redesign

### 目的

顧客が製品を比べるときの「ものさし」を変える。既存の比較軸で戦うと、先行する大手が有利になる。**自社が10倍の差を出せて、かつ顧客にとって本当に重要なものさし** を見つけ、それを顧客の比較の中心に置く。

### 入力

P5のICPと成功の定義、P6の判定と既存カテゴリーの比較軸。

### 手順

**Step 1. 既存の比較軸と、その重みを書く**

ICPが製品を選ぶときに見ている軸と、それぞれの重み（どれを重視しているか）を書く。

| 既存の比較軸 | ICPにとっての重み | 自社の位置 | 主な競合の位置 |
| --- | --- | --- | --- |
| 精度 | 高 | 同等 | 高い |
| 機能数 | 中 | 少ない | 多い |
| ... | | | |

**Step 2. 新しい比較軸の候補を出す**

以下の変換を試す。

| 変換 | 例 |
| --- | --- |
| 絶対値 → 単位あたり | 最高性能 → 1ドルあたりの処理量 |
| 能力 → 時間 | 機能数 → 導入までの時間 |
| 平均 → ばらつき | 平均精度 → 予測可能性（結果のばらつきの小ささ） |
| 1回 → 累積 | 1回の応答速度 → 1タスク全体の完了時間 |
| 製品単体 → 顧客の業務全体 | モデルの精度 → 業務全体の自動化率 |

候補を3〜5個出す。

**Step 3. 候補を4つの条件で評価する**

| 条件 | 問い |
| --- | --- |
| 顧客価値 | ICPの成功の定義（P5）に直結しているか。P1・P2の根拠があるか |
| 差の大きさ | 自社は、その軸で10%ではなく、数倍〜10倍の差を出せるか |
| 追随の難しさ | 既存の大手がその軸で追いつこうとすると、自社のビジネスモデルと衝突するか（例: 利用量で課金している大手は、利用量を減らす軸では戦いにくい） |
| 測定可能性 | その軸の測り方を定義して、第三者が再現できる形で公開できるか |

上位を1〜2個選ぶ。

**Step 4. 測り方を定義する**

選んだ比較軸について、測り方を書く。測り方が曖昧な比較軸は、競合に都合よく解釈される。

```text
比較軸の名前:
定義（何を何で割るか）:
測定条件（データ、環境、比較対象）:
自社の値 / 主な代替手段の値:
```

**Step 5. 比較表を設計する**

顧客が見る比較表（Webサイト、営業資料）では、新しい比較軸を一番上に置く。既存の比較軸で負けている項目も、隠さずに載せる。隠すと、顧客や第三者が自分で比較したときに信頼を失う。

### 深掘りの問い

* この比較軸は、ICPの予算保有者が稟議書に書く言葉になるか。
* 既存の大手が、この比較軸で追いつくには何を捨てる必要があるか。
* この比較軸が重要でなくなる状況（顧客の業務の変化、技術の変化）はあるか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「新しい比較軸: 使いやすさ」（測れない、誰でも言える） | 「新しい比較軸: 判断1回あたりのコスト（円／判断）。定義は、1か月の判断関連の費用 ÷ 判断回数。自社は0.004円、代替の大型LLMは0.3円（条件は○○、数値は例）。大型LLMの提供企業はトークン量で課金しているため、判断あたりのコストを下げることは自社の売上減につながり、追随しにくい」 |

### よくある失敗

* 自社だけが重要だと思っている比較軸を選ぶ。
* 差が小さい（10〜20%）軸を選ぶ。小さな差は、競合が数か月で追いつく。
* 測り方を定義せず、主張だけする。

### 出力

```text
■ 既存の比較軸と重み
■ 新しい比較軸の候補と、4条件での評価
■ 選んだ比較軸と、その測り方
■ 比較表の案
```

### 次への受け渡し

* 選んだ比較軸 → P10（Level 1メッセージ）、P11（数値）、P19（課金単位）
* 測り方 → P12 Proof
* 追随の難しさ → P28

## P8: Complementary Positioning

### 目的

既存の巨大な市場を置き換えるのではなく、**既存の市場が伸びるほど自社も伸びる位置** を探す。置き換えを狙うと、既存の大手と正面から戦うことになる。組み合わせを狙えば、既存の大手がパートナーやチャネルになりうる。

### 入力

P4の敵と「敵にしないもの」、P6の判定。

### 手順

**Step 1. バリューチェーンを描く**

顧客が目的を達成するまでに使っている製品・サービスを、流れの順に並べる。

```text
データ入力 → 前処理 → 判断 → 実行 → 検証 → 記録
（各工程で使われている製品名）
```

**Step 2. 自社の位置を選ぶ**

以下の位置から、自社が入れる場所を選ぶ。

| 位置 | 役割 | 向いている条件 |
| --- | --- | --- |
| 前段 | 既存製品に渡す前に、入力を整える・振り分ける | 既存製品の利用コストが高く、呼ぶ回数を減らしたい |
| 後段 | 既存製品の出力を検証・加工する | 既存製品の出力に誤りがあり、確認が必要 |
| 制御層 | 複数の既存製品の使い分けを決める | 顧客が複数の製品を併用している |
| Routing | 処理をどこに送るかを決める | 送り先によってコストや品質が大きく変わる |
| Validation / Evaluation | 品質を確認・評価する | 品質の基準があいまいで、測られていない |
| Monitoring | 稼働状況を監視する | 障害やコストの急増が見えていない |
| Security / Governance | 安全性・規制への対応を保証する | 規制や社内ルールが厳しい |
| Optimization | コストや性能を最適化する | 既存製品の使い方に無駄がある |
| Coordination / Orchestration | 複数の処理をつなぐ | 工程間の引き継ぎに手間がかかっている |

**Step 3. 成長の連動を確認する**

```text
既存市場の成長 → （何が増えるか） → 自社市場の成長
```

例: LLMの利用が増える → 振り分け・安全判定・検証の判断回数が増える → 判断専用モデルの利用が増える。

この連動が説明できないなら、自社は既存市場に依存しているだけで、成長は連動しない。

**Step 4. 既存製品の提供企業にとってのメリットを書く**

| 既存製品の提供企業 | 自社と組むメリット | 自社と組むデメリット | パートナーになる可能性 |
| --- | --- | --- | --- |

メリットの例: 顧客の利用コストが下がり、解約が減る / 自社で作る必要のない機能を補完できる / 顧客の利用が安定する。

**Step 5. 依存のリスクを確認する**

既存製品の上に乗るほど、その提供企業に依存する。以下を確認する。

* その提供企業が、同じ機能を自分で作る可能性はどれくらいか（P28で詳しく検討する）
* その提供企業の仕様変更や価格変更で、自社の製品が成り立たなくなる可能性はあるか
* 1社に依存しないように、複数の既存製品と組み合わせられるか

置き換えを選ぶ場合は、共存より置き換えのほうが有利な理由（既存製品が衰退している、既存製品の提供企業が敵対的である、など）を書く。

### 深掘りの問い

* 既存製品の提供企業の営業担当者が、自社製品を顧客に紹介したくなる理由はあるか。
* 顧客が既存製品の利用を増やしたとき、自社の利用も自動的に増えるか。
* 既存製品の提供企業が、自社を買収したくなるか、潰したくなるか。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「既存のLLMと共存できる」 | 「位置はLLMの前段（Routing）。ユーザーの要求を受けて、どのLLMを呼ぶか、そもそも呼ぶ必要があるかを判断する。LLMの利用が増えるほど判断回数が増え、自社の利用も増える。LLM提供企業にとっては、顧客のコスト負担が下がって利用が続くメリットがある。ただし、LLM提供企業が同等のRouting機能を自社で提供するリスクがある（P28で検討）」 |

### よくある失敗

* 「共存できる」と書くだけで、既存市場の成長と自社の成長がどうつながるかを説明しない。
* パートナーにしたい相手の利益を考えず、自社の都合だけで組み合わせを描く。
* 1社のプラットフォームに全面的に依存し、その会社が同じ機能を作るリスクを見ない。

### 出力

```text
■ バリューチェーン図
■ 自社の位置と、その理由
■ 成長の連動
■ 既存製品の提供企業との関係の表
■ 依存のリスク
```

### 次への受け渡し

* 自社の位置 → P9（Primitiveの形）、P10（Level 3の説明）
* パートナー候補 → P21 Distribution、P25 Third-Party Amplification
* 依存のリスク → P28

## P9: Product Primitive

### 目的

製品を、最も単純な基本操作として表す。Primitive が単純であるほど、顧客は製品をすぐ理解でき、自分の用途に当てはめて使い方を発明できる（P23 UGC）。逆に、説明に何ページも必要な製品は、口コミで広がらない。

### 入力

P6の一文定義、P8の自社の位置。

### 手順

**Step 1. 製品の入出力を書く**

```text
Input + Instruction → Output
```

または、

```text
State → Decision
```

の形で書く。

**Step 2. 抽象度を上げる**

最初に書いたPrimitiveに、特定の用途や業界の言葉が入っていたら、それを外す。

```text
「問い合わせメール → 担当チーム」
  ↓ 抽象化
「テキスト＋選択肢 → 選ばれた選択肢＋確信度」
```

抽象化しすぎて、何の製品かわからなくなったら、1段戻す。

**Step 3. Primitiveを動詞で名付ける**

開発者や利用者が、同僚に一言で説明できる動詞にする（例: 「判断させる」「振り分ける」「照合する」）。

**Step 4. 組み合わせの例を書く**

Primitiveを組み合わせると、何ができるかを3つ以上書く。

```text
Primitive × 1 → 問い合わせの振り分け
Primitive × 3（並列）→ インシデントの重要度・担当・影響範囲を同時に判定
Primitive を Loop の中で → Agent の次の行動の選択
```

### 深掘りの問い

* 製品を知らない開発者に、1行で説明できるか。
* このPrimitiveで、自社が想定していない用途を3つ思いつけるか。
* 入力と出力の形式は、他の製品とつなぎやすいか（JSON、標準的なAPI形式など）。

### 合格ライン

| 浅い | 深い |
| --- | --- |
| 「AIがビジネスの意思決定を支援します」 | 「State ＋ Question ＋ Allowed Answers → Answer ＋ Probability。動詞は『判断させる』。1回の呼び出しで複数の質問を並列に判断できる」 |

### よくある失敗

* 機能の一覧を Primitive と呼んでしまう。
* 特定の用途に寄せすぎて、他の用途を想像できない。

### 出力

```text
■ Primitive（入出力の形）
■ 動詞
■ 組み合わせの例（3つ以上）
```

### 次への受け渡し

* Primitive → P10（Level 2・3の説明）、P13（Viral Demo の題材）、P22（最初の価値体験）、P23（UGC）
