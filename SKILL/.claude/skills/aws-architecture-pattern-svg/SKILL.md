# AWS Architecture Pattern SVG Generator

AWSサービスの羅列や一般的な3層構成の量産を避け、**実装可能な経路・境界と、少なくとも1つの技術的発見を備えたパターン**を選定し、参考画像のように明快なAWSアーキテクチャ図をSVGで作る。

## 既定の入力

利用者から指定がなければ以下とする。指定された条件は必ず優先する。

| 設定 | 既定値 |
|---|---|
| 件数 | 5パターン |
| 難易度 | 中級4件・上級1件程度（全体では中級70～80%、上級20～30%を目安） |
| 新機能 | 直近18か月程度にGAされた新サービス・新統合・重要な機能拡張を、可能なら全体の20～30%程度に採用。5件なら通常1件。無理に充足しない |
| 領域 | AWS全般。ネットワーク・イベント・API・セキュリティ・データ・運用等を分散 |
| 出力 | 各パターンの独立した `.svg` と、その解説。ファイル操作が可能なら実ファイルに保存 |
| 読者 | AWS基本機能を理解し、開発・運用・設計経験のあるエンジニア |
| 言語 | 日本語。AWSサービス名・プロトコルは正式英語名 |

「最新」を明示された場合は公開情報を都度確認し、現在日付から対象期間を計算する。参照できない場合、知識だけで「最近追加」と断定しない。

## 実行手順

### 1. 候補を多めに選定する

`references/pattern-selection.md` に従い、希望件数の少なくとも2倍の候補を考える。各候補を「解決課題」「中心となる経路」「意外な学び」「導入条件」「代替案」「難易度」で1行ずつ整理する。

候補は網羅を装うために無駄なサービスを増やさない。珍しいサービスを使うこと自体は加点せず、**実務上の設計判断が変わるような発見**を優先する。定番構成だけ、同型パターンだけを選ばない。

### 2. 構成と新機能を技術検証する

- 実際にサポートされるサービス間統合、API種別、リージョン、GA/プレビュー、設定前提を確認する。
- 利用可能ならAWS公式サービスドキュメント、AWS What's New、AWS Architecture Blog等の一次情報を使う。公式のリリース情報は新機能の年月と共に記録する。
- **実在しない直接連携を線で表現しない**。経由するVPC Link、Interface Endpoint、NLB、EventBridge Pipes、IAM権限、ターゲット設定など、主題の成立に必須の要素を落とさない。
- CloudFront、Route 53などグローバルサービスの配置、VPC/サブネット/AZ/アカウント境界、ALBの内部/外部、RDS配置を確認する。
- DNS解決、HTTPの実通信、認証・認可、コントロールプレーン、非同期イベントを明確に分ける。とくにRoute 53 → CloudFrontをHTTP転送として扱わない。
- 必要な事実を検証できなければ、慎重な注記を付けるか別の候補に交換する。日付・対応リージョン・料金は推測しない。

### 3. 経路モデルを先に作る

SVGを書き始める前に、対象を次の内部モデルとして定義する。`assets/layout-reference.png` は利用者が提示した図の**レイアウト・配色・粒度の参考**であり、そこにある実際のAWS構成や矢印が正しいことを保証しない。図の中身は独立に技術検証する。

- **ノード**: ID、AWS正式名称、実際の役割、AWS Account/Region/VPC/AZ/Subnet等の包含先、グローバルかリージョナルか。
- **エッジ**: 開始・終点、方向、通信種別（data / event / DNS / control / auth）、プロトコルまたは操作名、前提条件、成功/失敗の区別。
- **境界**: AWS Cloud、Region、Account、VPC、AZ、Subnet、Cluster/Service/Task等。必要な境界のみ示す。
- **主経路**: ユーザーに最も学んでほしい経路を1本定め、太さ・線色・順序で強調する。

経路の種類ごとの視覚ルールは `references/diagram-contract.md` を参照。**図中の線を読み上げたとき、AWS仕様と矛盾していない**ことを確認する。

### 4. SVGを構成する

- SVGの基準幅は例として1400×800程度。`xmlns` と `viewBox` を必須とする。
- 白～ごく薄いグレーの背景、淡いグリッド（任意）、整った直交コネクタ、適度な余白を使う。
- サービスは主経路を原則として左→右、分岐・DLQ・戻りは上下に分離する。
- 主要サービスは通常4～10種類程度。主題に不要な監視・設定サービスを詰め込まない。
- 公式AWS Architecture Iconsが正規の利用可能な素材として手元にある場合は利用してよい。なければ**公式素材を装わない汎用のベクター記号**と正式名称を用いる。著作権上不明なアイコンの無断抽出・非公式の模倣はしない。
- テキストは日本語で可読性を保ち、矢印・箱・注釈・ラベルと重ねない。SVG内に制御用JavaScriptや外部Webアセットを含めない。
- 必要なら図右下などに線種凡例を配置する。図そのものには新しい学びと関係する統合方式を必ずラベルで示す。
- 外部CSS、`foreignObject`、Webフォント依存を避け、後からSVGを人が編集できる `<g>`, `<rect>`, `<path>`, `<text>` 等を使用する。

### 5. 1パターンごとに解説を添える

次の順序で簡潔ながら検証可能な文章を用意する。

1. **パターン名 / 難易度**: 目的がわかる具体名。
2. **解決課題**: 実務上どういう制約・問題があるか。
3. **構成概要**: サービスの担当範囲と接続方法。
4. **経路の説明**: 図のラベルに一致する番号付きの順序。DNS/制御と実通信は分ける。
5. **今回の学び**: 驚きや価値のある仕様・機能を具体的に1つ以上。
6. **採用条件 / トレードオフ**: なぜこの構成か、代替案との差、注意点。
7. **運用・セキュリティ上の注意**: 認証、冗長性、権限、課金、監視など必要なもの。
8. **一次情報**: 確認できたAWS公式情報のリンクと確認時点。確認不能ならその旨。

新機能を採用したパターンでは追加して、**一般提供開始日（確認できた場合）／従来の実現方法／追加後にできること／設計上の改善点／公式リリース情報**を解説する。GA前ならプレビューと明記し、採用の前提や制限を説明する。

### 6. 実ファイルを検証して納品する

- ファイル作成可能なら `pattern-01-...svg` のようにパターンごとに出力し、学習解説を `README.md` か各パターン個別のMarkdownで保存する。
- `python scripts/validate_svg.py <SVGファイル...>` でXML構造・外部依存の基本検証を行う。これだけでAWS仕様や配置の正しさが証明されるわけではない。
- 可能ならレンダリングして、重なり、欠け、極端に細い矢印、認識できないアイコンや文字などを目視確認する。
- 技術検証と見た目の検査が終わったものだけ納品する。実ファイルを作れない場合は完全なSVGソースコードを出す。

## 優先順位・禁止事項

**技術的な正確性 > 発見性 > 実用性 > 視覚的な華やかさ > 新しさ**。技術的に実現しないパターンは採用禁止。新機能枠を満たすための水増しは禁止。

- 線の意味を省略し、サービス名を並べるだけの図にしない。
- 構成の成立条件となる中継コンポーネントを省略しない。
- 全AWSリソースがVPCに所属するような配置図にしない。
- 接続のためだけのAWS Lambdaを機械的に挟まない。ただし変換・認証・コード処理が必要な場合は使う。
- 「公式検証済み」「新規リリース」「GA」等の表現は実際に確認した場合だけ使う。
- 1つの図で複数の設計課題を無理に解決しようとしない。

## 呼び出し例

- 「AWSの中級者向けデザインパターンを5つSVGで生成して」
- 「ネットワーク系だけ3件。PrivateLinkなど意外な接続を中心に」
- 「直近1年にGAされたAWS機能を活用した構成を2件追加して」
- 「このパターンの経路をSVGで図解。DNS経路と通信経路を分離して」
