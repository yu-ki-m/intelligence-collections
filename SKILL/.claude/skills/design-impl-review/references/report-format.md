# 最終アウトプットの書き方（要件一覧と要件ごとの指摘）

最終アウトプットは、`build_report.py` が作る HTML の2つの表だけである。

1. **要件一覧**：No／前提となる文脈／要件。`03_requirements.jsonl` の全件（指摘の有無によらない）。書き方は `workspace-files.md` の6節。
2. **要件ごとの指摘**：指摘のある要件だけを、要件一覧の No の順に、要件を見出し（名前だけの行）にして並べる。列は 指摘／事象／原因（原因箇所）／修正案／再現手順／根拠。`08_findings/*.json` のうち、判定が設計欠陥・実装の誤り・設計未定義・判断保留のもの。同じ要件の中では、この判定の順、同じ判定ならファイル名の順に並ぶ。

視点・ケース記録・横断確認・共通視点・確認の範囲は、HTML に載せず、ワークスペースのファイルに残す。判定と重大度の列も設けない。

## 読み手

読み手はレポートを鵜呑みにせず、自分で確かめる。だから、確かめるための情報（場所、原文の引用、確かめていない前提）を、その指摘の行の中に書く。別の表・付録・ほかの指摘を見ないと分からない書き方にしない。同じ内容を複数の場所に書かない。

## ガイドの7.3節との対応

ガイドの7.3節（論点ごとの結果）の項目は、次の列に入れる。

| ガイドの項目 | この表の列 |
|-|-|
| 見出し（状況と影響、または確認したいこと） | 指摘（`name`） |
| 判定 | 列にしない。名前と書き方で区別する（下の「判断保留・設計未定義の書き方」） |
| 状況と影響 | 事象（`event`） |
| 判断の根拠 | 原因（`cause`・`cause_at`）と根拠（`basis`） |
| 重要度と対応順 | 列にしない。`severity`・`priority` に記録し、`09_closing.md` で使う |
| 対応案・確認したいこと | 修正案（`fix`） |
| 確認方法 | 再現手順（`repro`）と、修正案の補足 |
| 照合用の記録（ケースID・視点名） | 表示しない。`cases`・`viewpoints` に記録する |

### 記録用の項目（表示しない）

| 項目 | 書くこと |
|-|-|
| `id` | `F-001` からの連番。ファイル名と同じにする |
| `req` | 違反している（または判定できない）要件の id。1つだけ。ほかの要件にも関わるときは、文中で `[[REQ-xxx]]` と書く |
| `judgment` | 設計欠陥／実装の誤り／設計未定義／判断保留（HTML に載る）。改善提案／取り下げ／問題なし／対象外（載らない。記録として残す） |
| `severity` | 重大度と、その根拠となる影響。基準が示されていなければ「（暫定）」を付ける。影響を評価できなければ「未評価」。AI の確信度で代用しない |

| `viewpoints`・`questions` | 関係する視点と確認待ちのID |

### 表示する項目

#### `name`（指摘）

問題そのものを、状況と影響が分かる1文で書く。「V10／整合性の問題」のような分類名にしない。

- 設計欠陥・実装の誤り：起きることを書く（「保存ボタンを2回押すと、2回処理されることがある」）。
- 判断保留：「…が分からない」（「閲覧権限のない人に通知が届くかが分からない」）。
- 設計未定義：「…が決まっていない」「…が食い違っている」（「失敗したら止めるか続けるかが、設計書とコードで食い違っている」）。

#### `event`（事象）

誰が、どの状態・操作・順序で、何が起き、誰の何に影響するか。具体的な値・件数・役割で書く（「検索結果が120件（1ページ50件）のとき、1ページ目で『全件選択』して一括更新すると、2・3ページ目の70件も更新される。」）。
確かめていない影響は「（未確認）」を付けるか、「可能性がある」と書く。コードを実行して確かめていないことを、本番で起きた障害のように書かない。

#### `cause` と `cause_at`（原因・原因箇所）

`cause`：設計書とコードのどこがどう期待と違うのかを、短く書く。コードの誤りなら、末尾に「（実装の誤り）」と書いてよい。
`cause_at`：原因の場所のリスト。`{"where": "パス:行", "note": "その場所の名前（見出し・関数名）"}`。場所のないもの（入手していない資料、要件がないこと）は文字列で書く（`"通知サービスの仕様とコード（別のリポジトリ。入手していない）"`）。

#### `fix`（修正案）

- 設計欠陥・実装の誤り：`label` は「直した後の動き」、`text` に要件を満たす振る舞いを書く。特定の方式を唯一の解として断定しない。
- 判断保留・設計未定義：`label` は「確認したいこと」、`text` に回答が必要な具体的な質問・資料・判断を書く。誰に決めてほしいかが分かるように。
- `diffs`：修正例。`{"where": "パス:開始行-終了行", "note": "場所の名前", "code": "差分"}`。`code` の各行の先頭は、空白（変えない行）・`-`（消す行）・`+`（加える行）のどれか。変えない行と消す行は、開いたファイルの行をそのまま写す（`build_report.py` が照合する）。途中を省くときは、変えない行として `…` だけの行を置く。設計書を直す修正例も書いてよい。新しい節を足すときは、足す位置の行番号を書き、全行を `+` にする。新しいファイルなら `"new_file": true` を付ける。
- `diff_label`：修正例の見出しを変えるとき（「通知サービスが絞り込まない場合の修正例：」）。既定は「修正例：」。
- `note`（補足）：修正だけでは防げない場合、ほかの要件の修正との関係（`[[REQ-xxx]]`）、直した後に正当な操作がまだ成立することの確かめ方。

修正版を受け取っていないので、「修正済み」「再確認済み」と書かない。

#### `repro`（再現手順）

読み手が自分で確かめるための、番号付きの手順。具体的な値・役割・APIを書き、最後の手順に「結果：…。期待：…。」を書く。判断保留なら「期待：要件の判断による。」と書いてよい。
並行・タイミングの問題は、止める場所（`パス:行`）と止め方（デバッガ、テスト用の待ち）を書く。
AI はコードを実行していない。手順は「確かめ方」であり、再現した記録ではない（実行して確かめたときだけ、そう書く）。

#### `basis`（根拠）

`{"label": "…", "where": ["パス:行"], "text": "…"}` のリスト。要求 → 設計書 → コード → 共通仕様 → 前提 の順に、判断に必要なものだけを書く。

- `label`：要求／設計書／コード／共通仕様／前提（未確認）／分からないこと／起きる条件 など。要求・設計書・コード・共通仕様には `where` が必要。
- `where`：`パス:行`、`パス:開始行-終了行`。「記載がない」の根拠は、確かめた範囲をパスだけで示し、`text` に確かめた範囲を書く（「同時更新の扱いの記載がない（1〜8章を確かめた）。」）。
- `text`：原文を引くときは「」で囲み、原文のまま写す（`build_report.py` が、その場所の近くにあるかを照合する。Markdown の `**` や表の `|` は省いてよい）。要約するときは「」を使わない。元資料の項目番号（要求の番号など）を示すなら、ここに書く。
- 指摘が頼っているが確かめていないことは、必ず「前提（未確認）」として書く。それが違えば結論がどう変わるかも書く。

## 文の書き方（すべての表示する項目）

- 平易な日本語で、1文を短くする。読み手が一度読んで分かる言葉を使う（「トランザクション」より「確定の範囲」など。コードの名前はそのまま `` ` `` で囲む）。
- 1文ずつ「。」で終える。`build_report.py` が、括弧の外の「。」ごとに改行する。
- レビュー内のID（REQ-001、V10、F-001、Q-003、C-V10-001、BASE-001、SRC-001、視点の丸数字）を書かない。内容と名前で書く。要件を指すときは `[[REQ-020]]`（HTML では「要件20」へのリンクになる）。`build_report.py` が検査する。
- 場所は、リポジトリのルートからの相対パスで `パス:行` と書く（VS Code で開ける）。
- 同じものは、同じ名前で呼ぶ（「一括更新」と「バルク更新」を混ぜない）。
- 説明例や過去の検証の数値を、実案件の要求・指摘として書かない。

## HTML を作る前の確認

1. `python <SKILL_DIR>/scripts/build_report.py <レビューのフォルダ> --check-only` の誤りがない。
2. 注意（引用・修正例の元の行が見つからない）は、場所を開いて確かめ、直した。
3. 1件の指摘だけを読んで、状況・影響・根拠・対応案・確かめ方が分かる。
4. 判断保留・設計未定義を、欠陥が確定したように書いていない。
5. 実施していないこと（修正・再確認・性能の測定・承認・コードの実行）を、実施したように書いていない。
