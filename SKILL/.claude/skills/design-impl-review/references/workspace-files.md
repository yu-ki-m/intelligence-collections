# ワークスペースのファイルの書き方

レビューのフォルダ（`<リポジトリのルート>/.ai_review_workspace/<日時>_<対象>/`）に置くファイルの形。
`workspace.py status` は、ここに書いた形（探索範囲表の列、`実施状況：` `判定：` の行、ケースの見出し、`V10へ：` の行）を読んで進み具合を判断する。形を崩さない。

ガイドの3.2節（共通記録）、7章（開始記録・7.1探索記録・7.2ケース記録）、8章（再開用記録）を、ファイルに分けたものである。

1. 書き込みの道具

12. 09_closing.md（終了時の記録）

## 1. 書き込みの道具

- 新しいファイル：Write。
- 追記（参照資料の行、要件の行、確認待ち、ケース、視点のまとめ）：Bash のヒアドキュメント。区切りを `'EOF'` と引用符で囲むと、`$` や `` ` `` を展開しない。

  ```bash
  cat >> "<レビューのフォルダ>/07_explorations/V10_競合・並行.md" <<'EOF'

  ### C-V10-002 一括更新の途中で単票の保存が確定する
  - …
  EOF
  ```

- 一部の書き換え（`review.json` の status など）：Edit。`00_progress.md` は小さいので、`cat > 00_progress.md <<'EOF'` で丸ごと書き直してよい。

追記は、ファイルの最後に足すだけなので、途中で止まっても前に書いた内容は壊れない。大きなファイルを Write で丸ごと書き直さない。

## 2. review.json

`workspace.py init` が作る。HTML の見出し（対象・資料・版・作成日）と、状態の表示に使う。

```json
{
  "target": "会議室予約",
  "mode": "標準",
  "focus": [],
  "previous": "",
  "created": "2026-10-11",
  "version": "コミット 1a2b3c4",
  "materials": "設計書・要求・共通仕様（Markdown）とコード",
  "status": "進行中",
  "banner": ""
}
```

- `materials`：Phase 0 で書く。読んだ資料の種類を短く。
- `status`：進行中 → 最後に 記録完了・途中・入力待ち のどれか。
- `banner`：HTML の上部に出す1〜2文。status が記録完了でないときに、確認していない範囲を書く（空なら既定の文が出る）。記録完了なら空にする。

## 5. 02_sources.md（参照資料）

資料を1つ読むたびに、行を追記する。抜粋だけ読んだ、取得に失敗した、も、そのまま書く。

```markdown
# 参照資料

| ID | 場所 | 版 | 読んだ範囲 | 取得状態 | 要件の抽出 |
|-|-|-|-|-|-|
| SRC-001 | docs/requirements/reservation.md | コミット 1a2b3c4 | 全体（1-142行） | 取得済み | 済み（REQ-001〜REQ-048） |
| SRC-002 | docs/design/reservation.md | 同上 | 全体（1-188行） | 取得済み | 未 |
| SRC-010 | src/reservation/ReservationService.ts | 同上 | 1-240行 | 取得済み | 対象外 |
| SRC-020 | 通知サービスの仕様 | — | — | 未入手（別リポジトリ。設計書 6章が参照） | 対象外 |
```

- 要件の抽出：要求・設計書・共通仕様は、読んだ時点で「未」と書き、要件を追記し終えたら「済み（REQ-…〜REQ-…）」に書き換える（Edit）。コード・未入手の資料は「対象外」。`workspace.py status` は「未」の資料を、要件を抜き出していない資料として表示する。

## 6. 03_requirements.jsonl（要件）

1行に1件の JSON。最終の「要件一覧」になる。資料1つ（または章1つ）を読み終えるたびに、まとめて追記する。

```json
{"id":"REQ-012","group":"予約の登録","context":"会議室は先着で使う","requirement":"同じ会議室・時間帯の予約が既にある場合、後から確定しようとした予約を拒否する。","source":["docs/requirements/reservation.md:24"],"kind":"明示","status":"合意済み"}
{"id":"REQ-013","group":"予約の登録","context":"通信が切れると、画面が再送する","requirement":"同じ要求IDの要求には、24時間、最初の応答を返す。","source":["docs/common/api-common.md:52-55"],"kind":"暗黙","status":"合意済み"}
{"id":"REQ-087","group":"定期予約","context":"定期予約は月末にまとめて作られる","requirement":"定期予約の一括作成は、決められた件数のもとで、決められた時間内に終わる（件数・時間は未定）。","source":[],"kind":"暗黙","status":"未合意"}
```

| 項目 | 書くこと |
|-|-|
| `id` | `REQ-001` からの連番。後から足すものも続きの番号にする。表示しない |
| `group` | 話題のまとまり（例：予約の登録、定期予約、通知、非機能）。要件一覧はグループが最初に出た順に並び、後から足した要件も同じグループの所に入る。表示しない |
| `context` | 前提となる文脈。その要件が必要になる業務上の前提・理由を短い句で（例：「チケットの件名は必須項目である」「誤った連携が大量の要求を送ることがある」） |
| `requirement` | テストできる1〜2文（「〜の場合、〜する。」）。誰が・何に・どの条件で・どうなるかが分かるように |
| `source` | 根拠の場所（`パス:行` か `パス:開始行-終了行`）のリスト。暗黙の要件は、読み取った設計書・共通仕様の場所。根拠のない要件は空にする |
| `kind` | 明示（要求の資料に書かれている）／暗黙（設計書・共通仕様の約束から読み取った） |
| `status` | 合意済み／未合意（資料にない、値が決まっていない、要求どうしが矛盾する） |
| `note` | 任意。読み取った理由など |

- 直すときは、同じ `id` の行を新しく追記する（後の行で置き換わる）。消すときは `{"id":"REQ-005","deleted":true}` を追記する。前の行を書き換えない。
- 表示する文（context・requirement）に、レビュー内のIDを書かない。
- 設計書から読み取った暗黙の要件は、コードが設計どおりかを判定するのには使える。しかし、設計そのものが業務の目的に合っているかの根拠にはならない（ガイド3.2）。
- 要件どうしが矛盾するときは、両方を書き、status を未合意にして確認待ちに書く。どちらを優先するかを AI が決めない。

### 処理の順序と確定の範囲

- 重なりの判定の条件は設計書にない。コードでは開始・終了の両端を含めて比べる（`src/reservation/overlap.ts:5-12`）

- 主体／入口／対象：一般の利用者／予約画面／会議室A
- 初期状態／入力：空いている枠／10:00〜11:00
- 処理／結果：重なりを確かめて確定し、参加者に通知する

- 設計：`docs/design/reservation.md:20-45`、コード：`src/reservation/ReservationService.ts:40-92`

## 期待結果
### 不変条件

### 到達条件

### 観測・対処
- 利用者は、仮予約と確定を画面で区別できる（REQ-020）

## 未合意の期待結果と必要な判断
- 通知の遅れの許容時間（Q-001）

## 10. 07_explorations/（視点ごとの探索記録とケース）

ファイル名：`V01_主要シナリオ.md` のように、視点のIDと名前。横断確認は `X_横断確認.md`、再レビューの前回の指摘の再確認は `R_前回の指摘の再確認.md`。

### 探索を始めるとき（Write で作る）

- 実施状況：途中
- 深さと選択理由：重点。定期予約の作成と、画面からの予約が同じ枠を取り合う

### ケースを1件判定するたび（追記する）

```markdown

### C-V10-001 同じ枠を2人がほぼ同時に予約する
- 主視点／関連視点：V10／V08
- 状況：利用者Aと利用者Bが、会議室Aの10:00〜11:00を同時に開く。Aの重なりの確認が通った後、Bが確定し、その後にAが保存する
- 成立の条件と根拠：資料上成立する。確認と保存の間を直列にする共通の仕組みはない（`docs/common/api-common.md:60-72`）
- 期待結果と根拠：Aの予約を拒否し、Bの予約を残す（REQ-012、`docs/requirements/reservation.md:24`）
- 設計の記述：重なりを確認してから保存する、とだけある（`docs/design/reservation.md:40-42`）
- コードの動き：重なりを SELECT で確かめ（`src/reservation/ReservationService.ts:55-60`）、別の文で INSERT する（同 :71-74）。一意制約もない（`db/schema.sql:30-41`）
- V17・V18：前提「同時に予約しない」を支える仕組みがない。データベース：分離レベルは未確認（既定の READ COMMITTED と仮定）
- 照合結果：期待と違う。両方の予約が確定する
- 判定：設計欠陥
- 影響：同じ枠に2つの確定済み予約ができ、当日に会議室が重なる
- 対応案のメモ：保存の時点で重なりを拒否する（排他制約、または行のロック）
- 関連：Q-004（分離レベル）
```

- 問題なしのケースも、少なくとも 状況・期待結果と根拠・設計の記述／コードの動き・判定 を書く。何を照らし合わせたかが分かるようにする。
- `判定：` の行は、問題なし・設計欠陥・実装の誤り・設計未定義・判断保留・対象外・未判定 のどれかで始める。照合を終えていなければ「未判定」と書く。
- 場所は Read や grep で開いた行番号を書く。推測した行番号を書かない。
- 全欄を埋めるために、資料にないことを補わない。分からない欄は「未確認」と書く。

### 視点を閉じるとき（追記する）

```markdown

## 視点のまとめ
- 実施状況：記録完了
- 見た範囲：選んだ3つの範囲（C-V10-001〜004）
- 未確認範囲と理由：管理画面からの一括取消は、コードが別リポジトリで未入手（Q-005）
- V17の前提確認：「同時に予約しない」は支える仕組みがない（C-V10-001）
- V18の適用領域と結果：データベース（排他・一意制約）。分離レベルの設定は未確認

## 他視点への引継ぎ
- V11へ：予約の保存後に通知が失敗した場合の状態
- V13へ：取消が利用実績の集計に反映されるか
```

- 範囲の一部が残ったまま閉じるときは「実施状況：途中」と書き、残りを未確認範囲に書く。計画を後から全件完了に書き換えない。
- 引継ぎは `- V11へ：…` の形で書く（status が受け取り先の視点を示す）。

### 横断確認（X_横断確認.md）

視点ファイルと同じ形。冒頭に選んだ組み合わせと選んだ理由、ケースは `### C-X-001 …` とし、関連する元のケースのIDを書く。行わない場合も、理由を書いて `- 実施状況：記録完了` にする。

### 前回の指摘の再確認（R_前回の指摘の再確認.md。再レビューだけ）

冒頭に前回のフォルダ・前回の版・今回の版・差分の範囲を書く。前回の指摘ごとに `### C-R-001 <前回の指摘の名前>` とし、元のケースを新しい版に当てはめた結果を書く。`判定：` の行には、新しい版での判定（問題なし・設計欠陥など）を書き、別の行に `再確認の結果：解消を確認／未解消／別問題へ変化／確認不能` を書く。修正で正当な操作まで拒否していないか、同じ不変条件・資源・影響先を使うほかの視点に波及していないかも書く。
