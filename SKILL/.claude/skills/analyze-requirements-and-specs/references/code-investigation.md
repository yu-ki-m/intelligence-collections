# 既存コード精査と調査完了条件

## 調査台帳

入口・関連動作ごとに調査ID、対象、変更との関係、経路、状態・条件、現行結果、副作用、コード位置、関連テスト、履歴、目的、調査状態、未解決、対応する既存仕様IDを記録する。状態は未調査／調査中／確認済み／対象外（理由付き）とする。

1. 対象版を固定し、ルーティング・画面操作・ジョブ登録・イベント購読から入口を列挙する。
2. 入口→入力検証→権限→業務判定→保存→戻り値→後続処理を読む。例外経路、早期return、トランザクション境界も追う。
3. 呼び出し元、同じ共通処理の利用先、同じデータの参照・更新先を逆引きする。直接参照だけでなくDI登録、設定、動的呼び出し、イベントの対応も調べる。追跡できないものは不明として残す。
4. 判定を状態・権限・設定・入力・データ世代に分解し、正常・拒否・失敗・競合時の結果を列挙する。
5. テスト・設計書・git logやblame等を必要に応じて照合する。履歴のコメントだけで意図を断定しない。動作の確認と目的の確認を別に記録する。
6. 影響が伝わる先を繰り返し追い、各境界に停止理由を残す。「検索でヒットしない」だけで影響なしとはしない。生成物、外部サービス、履歴不足は調査の限界として記す。
7. 発見した仕様を「変更対象・関連機能の現行仕様と目的」に掲載し、影響→要件一覧→仕様一覧へ展開する。

## 完了判定

重要な入口・分岐・依存先に未調査がある場合、分析完了にしない。暫定成果物にはどの結果が確定できないかを示す。コードアクセスがない場合も同様。
調査済み件数だけで完了判定しない。経路・業務条件の網羅根拠、証拠、矛盾解消、影響への対応結果を確認する。静的調査・机上実行・実テストの別を明記する。
