# 成果物とデータ形式

## 人が読む成果物

1. 対象・調査範囲・版・要約・完了状態
2. 要求一覧：要求ID、原文、目的、対象、成功条件、出典
3. 変更対象・関連機能の現行仕様と目的：既存仕様ID、対象機能、変更対象との関係（直接／呼び出し元／呼び出し先／後続／共有／間接）、影響の伝播経路、影響が生じる条件、調査状態、現行動作、入口・条件、証拠ID、当初目的、目的の確度、現在の必要性、矛盾、処遇、判断根拠、関連要件ID
4. 要件一覧：要件ID、導出元、前提となる文脈、適用条件、要件、受入条件、追加／変更／維持／移行／撤去、採否、確認状態、関連仕様ID
5. 仕様一覧：仕様ID、親要件ID（一つ）、入口、入力、状態・条件、判定順、処理、データ変化、結果、副作用、失敗・競合、依存仕様ID、既存との差、証拠、受入ケースID
6. 影響一覧：対象、対応する既存仕様ID、関係、条件、影響分類、必要対応、根拠、対応要件・仕様
7. 判断・未決一覧：論点、仮案、選択肢、影響、判断者、期限、状態、決定根拠
8. 受入ケース：ID、対象仕様ID、前提、入力、期待結果、副作用、根拠
9. 検証結果：構造検証、意味の紐づけ、既存理解、シナリオ検証、残課題

多すぎる列は詳細台帳へ分離し、要件一覧・仕様一覧を見通せるようにする。各仕様の必要性が親要件のどの意味に対応するかを詳細に記録する。

既存仕様の掲載範囲は直接の変更対象に限定しない。影響一覧の各項目から上記台帳の既存仕様IDを参照し、現在の動作・目的・保証が確認できるようにする。未調査の場合も台帳に未調査と記載し、確認済みの仕様を創作しない。新機能など既存仕様が存在しない場合は非該当の理由を記す。MarkdownとHTMLの見出しは「変更対象・関連機能の現行仕様と目的」で統一する。

## 要件一覧で結果を完結させる

要件一覧には明示要求、暗黙的要求、影響派生、維持、移行、置換、撤去と条件付き候補を集約する。各行に前提となる文脈、必要な条件、適用条件、導出元、採否、確認状態、未決の理由を記載する。未決の重要事項を他の台帳にだけ隠さない。
影響一覧には影響ID、要件への処理区分（既存要件で対応／要件を追加／対応不要／未調査・判断待ち）、対応要件ID、理由を追加する。要件が不要なら理由を残し、架空の要件を数合わせで作らない。仕様がまだない候補は1:Nが完成していないことを明示する。
analysis.jsonのrequirementsにはproposed/deferredも含める。まだ要件文が作れない論点はrequirementsではなくdecisionsに保持し、表示上は要件一覧末尾の「要件化に関わる未決事項」に併記する。機械検証合格だけで分析完了としない。
調査台帳をinvestigationsとして保持し、人向け成果物の根拠資料に掲載する。

## Markdown・HTMLの同時出力

- 標準では `requirements-specifications.md` と `requirements-specifications.html` を必ず両方作成する。JSONは検証用の補助成果物であり、人が読む二形式の代わりにしない。
- 共通の分析データから両形式を生成し、上記9区分、各ID、親子関係、根拠、状態、未決事項を一致させる。HTMLのために内容を要約・脱落させない。更新時も両形式を同時に更新する。
- HTMLは日本語（`lang="ja"`）、UTF-8、viewport指定付きの単独で開けるファイルとする。CSSを内包し、外部CDN・フォント・通信を必須としない。JavaScriptなしでも本文・表・リンクを読めるようにする。
- 冒頭に対象・版・分析状態と未決事項の件数を表示し、区分別目次を付ける。要件一覧・仕様一覧を主な閲覧対象とする。
- 要件・仕様・既存仕様・未決事項に一意なアンカーを付ける。要件から子仕様へ、仕様から一つの親要件へ移動できるリンクを設け、依存仕様や根拠への参照も可能な範囲でリンク化する。親要件と依存参照を明確に区別する。
- 表には見出しセルを設定し、長文を折り返す。横長の表は横スクロール可能な領域に収め、ページ全体のはみ出しを防ぐ。列が多い詳細は別の詳細表へ分離し、IDで往復できるようにする。
- 未確定・推定・確認済み・廃止候補などを文字ラベルで表示し、色だけで区別しない。廃止候補を決定済みのように見せない。
- 印刷用CSSを用意し、本文を欠落させない。折りたたみを使う場合は印刷時にも全内容が出るようにし、実現できない場合は折りたたみを使わない。
- コード・資料・ユーザー入力をHTML本文へ埋め込む際はエスケープする。未検証の内容をスクリプトや生HTMLとして実行しない。
- 提出前に両形式のID集合・親子関係・項目件数・未決状態を照合する。HTMLのアンカー重複・リンク切れを確認する。利用可能なローカル描画手段で広い画面と狭い画面を確認し、文字切れ、重なり、表の欠落を修正する。描画手段がなければ構造確認まで実施し、表示確認は未実施と記録する。

## analysis.json

必須のトップレベルは requirements と specifications。補助台帳は requests, existing_specs, evidence, impacts, decisions, acceptance_cases, review に保持する。

```json
{
  "requirements": [
    {"id":"R-001","status":"accepted","context":"完了後の内容を保持する必要がある","statement":"完了済みの外部連携更新を拒否すること","sources":["D-001"],"acceptance":"完了済み対象の業務データが更新されない"}
  ],
  "specifications": [
    {"id":"S-001","requirement_id":"R-001","statement":"完了が先に確定した対象への外部更新を拒否する","rationale":"完了済みへの変更禁止を競合時も成立させるため","depends_on":[]}
  ]
}
```

status は accepted / proposed / deferred / rejected。採用済みでも業務合意状況は別フィールドに記録し、acceptedをユーザー承認済みの意味に偽装しない。
採用要件の子仕様は最低一つ。提案・保留要件は子仕様ゼロを許すが、完成した要件一覧と呼ばない。rejected/deferredに確定仕様を帰属させない。候補仕様は仕様一覧と分けて判断台帳に置く。
requirement_id に配列、カンマ区切り、複数IDを許さない。親と子の紐づけはこのフィールドを正とし、表示用の関連仕様IDは逆引きする。
機械検証はID、参照、最低限の記述、1:N、依存循環を検査するだけで、仕様の意味の漏れや証拠の妥当性を保証しない。
