# 調査と判断の観点

## 証拠と目的

証拠にはID、種類、対象版、場所、確認内容、限界を記す。コードは現行実装の根拠、履歴・課題は導入背景の根拠、テストは期待の一例、運用資料は利用実態の手掛かりであり、それだけで正しい将来要件を保証しない。
資料間の矛盾は、各主張と出典、適用時期、環境差、利用条件を並べる。新しい資料という理由だけで採用せず、業務目的・現在の制約・決定権者の判断に基づく採用理由を残す。

既存仕様ごとに次を問う。
- 誰の、どの業務成果や不変条件を守るのか。
- 導入時の障害、外部制約、暫定対応、互換性対応は何か。
- その目的は明記された事実か、複数証拠に基づく推定か、不明か。
- 現在その利用者・依存先・前提・制約は残るか。
- 目的は有効でも実現手段だけが古くなっていないか。
- 他の仕様が代わりに保証しているか。重複の除去で保証が欠けないか。
- 存続・変更・廃止した場合、それぞれどんな損失と移行負担があるか。

## 影響・暗黙的要求チェック

| 領域 | 調査すること |
|---|---|
| 業務 | 前後工程、取消、訂正、承認、手動介入、例外、責任分界 |
| 経路 | 画面、API、一括、バッチ、管理、連携、イベント、再実行 |
| 条件 | 状態、権限、所属、契約、設定、データ有無、世代、境界値 |
| データ | 意味、必須、既定値、整合性、制約、履歴、削除、保持期間 |
| 共有 | 呼び出し元・先、共通部品、共有テーブル、集計、キャッシュ、検索索引 |
| 時間 | 判定時点、同時更新、排他の外部保証、順序、重複、冪等性 |
| 失敗 | 成功単位、部分更新、タイムアウト、再送、補償、復旧 |
| 接点 | 入出力契約、通知、エラーの意味、互換性、利用者の次の行動 |
| 品質 | 性能と負荷条件、容量、可用性、認証認可、分離、秘密情報、監査 |
| 導入 | 既存データ移行、新旧混在、適用順序、処理中データ、切り戻し |
| 運用 | 監視、問い合わせ、手動復旧、教育、コスト、担当者 |

適用しない観点にも理由を付ける。すべてに新機能を追加しない。現在満たしている保証を維持する要件も含める。

## 廃止の判断記録

1. 廃止対象を限定し、機能全体と内部の古い手段を区別する。
2. 過去の目的と現在の必要性を別々に示す。
3. 実利用・依存の調査範囲と見えない範囲を明記する。静的参照なしだけで利用なしとしない。
4. 維持／修正／置換／廃止を、品質・業務損失・費用・移行で比較する。
5. 失われる保証と代替、データ・外部利用者の移行、監視、復旧手段を示す。
6. 決定者・決定根拠を記録する。未決なら廃止候補のままにする。技術的美しさだけで決めない。
7. 採用された廃止でも、撤去・移行・維持保証に必要な要件と仕様を作る。

## 意味の1:Nレビュー例

要求「完了済みの外部連携更新を止めたい」から、以下を分析する。
- 更新禁止要件 → 状態による拒否仕様、競合時の確定順仕様。
- 誤った成功通知を防ぐ要件 → 拒否時の成功イベント抑止仕様。
- 連携先が対処を選べる要件 → 拒否理由の識別仕様。
- 未完了の既存更新を維持する要件 → 許可条件の維持仕様。
エラーコードの値そのものを独立要件にはしないが、識別・再試行判断という保証を仕様だけに埋め込まない。
監査仕様が複数機能で共有されるなら監査要件の子仕様として一度定義し、各機能の仕様はそのIDを参照する。

## 完了ゲート

- 調査対象と対象外の理由を説明でき、未探索の依存先を隠していない。
- 関連する現行仕様の目的、証拠、現在の処遇を追跡できる。
- 重要な矛盾・不明点・廃止判断を未解決のまま確定していない。
- 独立した要求事項が仕様だけに隠れていない。
- 採用要件は一つ以上の仕様を持ち、各仕様は一つの親を持つ。
- 受入ケースから最終結果と副作用を判断できる。
- 構造検証と意味レビューの結果を分けて報告している。
