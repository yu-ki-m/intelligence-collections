# 要件・仕様分析（Claude Code版）

## 守る原則

- 要求（望み・課題）、要件（満たすべき条件と理由）、仕様（具体的な外部観測可能な振る舞い）、実装設計（実現手段）を分ける。
- 要件→仕様を必ず1:Nにする。採用した要件は一つ以上の仕様を持ち、各仕様は必ず一つだけの親要件を持つ。Nは1以上であり、数合わせの仕様分割はしない。
- これは単なる紐づけ検査ではない。仕様に独立した目的・義務・制約・保証が初めて現れたら、その意味を表す要件を追加し、仕様を適切な単位に分割して帰属させる。既存要件を無制限に広げる、汎用の「適切に処理する」要件に押し込む、同一仕様に複数の親を付けることを禁止する。
- エラーコードや表示文言など既存要件の具体化まで機械的に要件化しない。「なぜ必要か」が既存要件で説明できるかを判定する。再試行可否の識別など新たな保証なら要件を追加する。
- 横断的保証は専用要件と仕様を持たせ、他の仕様は依存仕様IDで参照する。参照は第二の親ではない。同じ仕様をコピーして1:Nを装わない。
- 現行実装・設計書・テスト・担当者の説明のどれも無条件に正解としない。「観測した動作」「過去の目的」「現在必要な目的」「採用する将来仕様」を分離する。
- 目的不明・未調査を「影響なし」「不要」と扱わない。根拠がない歴史を作らない。推定には根拠・反証・確認先を記載する。
- 実装変更や既存機能廃止を分析の依頼だけで実行しない。成果物は分析・判断案とし、すでに明示された決定は再承認を求めず根拠として扱う。

## Claude Codeでの実行

- このSKILL.mdのあるディレクトリをスキルルートとして、参照資料・検証スクリプトのパスを解決する。対象プロジェクトのルートと混同しない。
- ユーザーの依頼・引数から分析対象と要求を読み取り、プロジェクトのCLAUDE.md等の適用指示に従う。
- 調査にはRead、Grep、Globや許可されたBashを使う。`rg` があれば検索に利用し、なければ利用可能な検索機能に切り替える。特定のMCP・外部サービス・サブエージェントを必須にしない。
- Gitの状態・対象コミット・未コミット変更の有無を記録する。未コミット変更がある場合はコミット内容と混同せず、作業ツリーを調査した旨と差分を記録する。既存作業を戻さない。
- 実装コードの変更、依存追加、デプロイ、外部送信はこの分析の範囲に含めない。既存テストは実行環境と副作用を確認して必要な範囲で実施し、読んだだけの場合と実行した場合を区別する。
- 出力先は指定を優先し、未指定ならプロジェクト内 `docs/requirements-analysis/<案件名>/` とする。既存の別案件成果物を上書きしない。
- Python 3を検証スクリプトに使用する。`python3`、`python`、Windowsの`py -3`から実在するものを確認する。追加パッケージは不要。Pythonが使えない場合は手動検証結果を残し、機械検証済みとは書かない。
- ChatGPT Library、sandboxリンク、Codex固有のAPIは必要ない。成果物をプロジェクト内に保存し、最終応答に実際のファイルパスを示す。

## 開始時

1. スキルルートの `references/analysis-guide.md`、`references/output-contract.md`、`references/code-investigation.md` を読む。
2. 要求、対象業務、対象版、利用可能な設計資料・コード・テスト・履歴・問い合わせを確認する。提供済み情報を再質問しない。
3. アクセスできる資料を先に調査し、判断が変わる不足情報を絞って質問する。コードや資料が得られなければ仮説ベースの暫定一覧を作り、既存仕様を確認済みとしない。
4. 調査対象と除外範囲、完了条件を宣言する。調査は関係のある範囲から始め、依存・矛盾が見つかれば拡張する。無関係なシステム全体を調査しない。

## 手順

### 1. 要求と業務目的を整理する

発言を要求IDに分解し、原文・課題・主体・場面・支障・期待結果・対象範囲・例外・成功条件を整理する。「ボタンを無効化したい」など解決案から、守りたい業務目的を確認する。曖昧な回答は具体例と反例に変換し、「この状態でも同じ扱いか」と判断を助ける。未決事項には仮案、選択肢、差分、判断者、期限、未決の影響を記録する。

### 2. 既存コードを精査し、現行を再構成する

`references/code-investigation.md` の調査台帳を作り、入口・分岐・依存先・調査境界を追跡する。

入口から呼び出し先・保存・戻り値・後続処理まで追い、呼び出し元と共有データの読書き箇所も逆方向に調査する。画面だけでなくAPI、一括、バッチ、管理、外部連携、非同期イベントを列挙する。状態、権限、設定、データ世代による分岐を確認する。
「変更対象・関連機能の現行仕様と目的」台帳に動作と証拠を記録する。直接変更する仕様に加え、呼び出し元・呼び出し先・後続処理・共有データや共通処理の利用先・間接的な影響先の現行仕様も掲載する。各項目に変更対象との関係、影響の伝播経路、影響が生じる条件、調査状態を記録する。影響先の名前だけを挙げて仕様を理解済みとしない。未調査・不明はそのまま明記し、影響が伝わらないと判断した境界には根拠を残す。検索結果の断片だけで理解済みにせず、周辺の条件、例外、トランザクション、利用側の前提を読む。参照資料の版・コードのコミット・該当箇所を残す。

### 3. 既存仕様の目的と現在の妥当性を分析する

各関連仕様について「誰の何を守るためか」「導入時に何が問題だったか」「その前提は現在もあるか」「取り除くと誰に何が起きるか」を調べる。利用可能な変更履歴・課題・障害記録・テスト・運用を突き合わせる。
過去の意図が特定できない場合、現在の必要性は別途判断可能だが、過去の目的が判明したとは書かない。
維持／明文化／修正／置換／例外的な廃止候補／保留に分類する。廃止候補は目的失効、代替保証、実利用、互換性、移行、復旧、判断権限を分析して提案する。負債・複雑・検索で見つからないという理由だけでは廃止しない。

### 4. シナリオと影響を展開する

主体→前提状態→入力・契機→条件→処理→状態変化→外部影響→失敗・復旧を記述する。
正常、拒否、境界、欠損、既存データ、競合、重複、順序逆転、途中失敗、新旧混在を検討する。全組合せを無条件に量産せず、結果が変わる組合せと高リスクな組合せを選び、その根拠を残す。
各影響先を「修正必要」「仕様維持・回帰確認」「影響なし（根拠付き）」「未解決」に分類する。異なる入口が同じデータを操作する場合、業務ルールの適用範囲を揃える必要があるか確認する。

### 5. 暗黙的要求を要件化する

明示要求、現行目的、維持すべき保証、シナリオ、影響分析、品質基準から要件候補を作る。候補を必須と断定せず根拠・適用条件・採否を判断する。具体的な数値基準は根拠なく捏造しない。
要件一覧には前提となる文脈、満たすべき条件、適用範囲、受入条件、導出元を必ず持たせる。変更だけでなく維持・移行・撤去に必要な要件も記載する。独立して採否や充足を判断する事項は分ける。

要件一覧だけで要件分析の結果全体を把握できる状態にする。明示要求だけでなく、暗黙的要求、影響から生じた保証、既存動作の維持、移行・置換・廃止に必要な要件、未確定候補を同じ一覧に集約する。根拠資料の参照だけで済ませず、必要な内容・理由・適用条件・採否・確認状態を各行に記載する。採用済みと候補を明確に区別する。
影響ごとに「既存要件で対応」「要件を追加」「対応不要（根拠付き）」「未調査・判断待ち」を記録する。未調査でも導出できる要件候補は条件付きで一覧に載せる。まだ内容を定義できない場合は要件分析上の未決行として記録し、確定要件と偽装しない。仕様一覧・影響一覧・判断台帳にだけ要求事項を残さない。

### 6. 仕様へ展開し、要件へ戻す

要件ごとに具体的な入力、条件、判定順、処理、更新範囲、結果、副作用、失敗・競合時動作を記載する。判定表や状態遷移表を必要に応じて使う。共通仕様はID参照で一元化する。
仕様の各記述について「この振る舞いが必要な理由は親要件のどの条件か」を説明する。説明できない独立した要求事項を発見したら要件を追加し、仕様の分割・再帰属と影響分析を行う。親IDを付けるだけで済ませない。
クラスやDBロック方式などは実装案として分離する。ただし外部制約として特定技術が必要なら理由と出典を要件に残す。

### 7. 双方向検証する

要求→要件→仕様→受入ケースと、仕様→要件→目的・根拠を照合する。既存仕様台帳の各項目の処遇が、要件・仕様または理由付き対象外判断へつながるか確認する。
境界・拒否・競合・失敗ケースを机上実行し、最終データ、戻り値、通知、後続処理まで一意に決まるか確認する。仕様同士の矛盾、参照循環、孤立要件、多親仕様、受入条件の欠落を確認する。
`analysis.json` を作成し `python3 <スキルルート>/scripts/validate_traceability.py <出力先>/analysis.json` を実行する。これは構造検証に限られる。意味の整合・調査十分性・根拠の真偽は別途レビューし、その結果を残す。

### 8. 成果物を提出する

要件一覧と仕様一覧を中心に、「変更対象・関連機能の現行仕様と目的」台帳、影響整理、判断・未決事項、受入ケース、検証結果を提出する。標準成果物として日本語の `requirements-specifications.md` と `requirements-specifications.html` の両方、および機械検証用の `analysis.json` を作成する。HTMLは省略版ではなくMarkdownと同じ分析内容を収録する。明示的に単一形式を指定された場合のみその指定を優先する。HTMLの表示・検証条件は `references/output-contract.md` に従い、指定した出力先に保存して両形式の実ファイルパスを提示する。
採用要件に仕様がない、多親仕様がある、重要な目的・挙動・判断が未解決の場合、分析完了としない。暫定成果物を渡し、未決によって何が確定できないか明示する。未決項目に完了扱いの仕様を作らない。
更新時は既存IDを維持し、変更理由と関連IDへの再分析結果を残す。
