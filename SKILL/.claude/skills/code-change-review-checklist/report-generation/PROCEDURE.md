# レポート生成手順(同梱)

これは `code-change-review-checklist` に同梱した、コード変更フローのレポート(`review-data.json` とHTML)を生成する手順である。チェックリストの入力が存在しない場合に、`code-change-review-checklist/SKILL.md` の指示で読む。独立したスキルとしては登録しない。

- この資料と `references/` にある `<skill-root>` は、このファイルがあるフォルダ(`code-change-review-checklist/report-generation/`)を指す。
- 元は `code-change-flow-report`(テンプレート版 `2026.09.13.3`)である。本文は元の手順と同じで、変更していない。更新する場合は、`../scripts/verify-templates.mjs` が同梱版とチェックリストの対応版が一致していることを検査する。

# コード変更フロー表

コミットごとに変更前後を比較し、変更行だけでは分からない実行経路を単体のHTMLファイルで示す。対象リポジトリは読み取り専用で調査し、ユーザーが明示的に依頼しない限りソースコード、Git履歴、リモートリポジトリを変更しない。

最終成果物は自己完結したHTMLファイルだけにする。JSONはHTMLを生成するための内部入力として扱い、ユーザーが明示的に求めない限り納品しない。Webサーバー、開発サーバー、HTTPサーバーを起動せず、ポートを待ち受けない。Node.jsはHTMLを生成して終了する単発処理にだけ使用する。

## 必ず読む資料

1. 担当を割り当てる前に [複数エージェント実行規則](references/multi-agent-orchestration.md) を読む。
2. 調査前に [処理フローの追跡](references/flow-tracing.md) を読む。
3. JSONを書く前に [JSON仕様](references/review-data-schema.md) と [説明文規則](references/explanation-writing.md) を読む。
4. HTMLを生成する前に [HTMLテンプレート要件](references/report-template-requirements.md) を読む。
5. 独立検証前とHTML生成後に [検証項目](references/verification.md) を読む。

## 実行手順

1. 調整担当が対象リポジトリ、コミットまたはコミット範囲、出力先を確定する。対象が指定されていない場合は、結果が変わる推測をせずユーザーへ確認する。通常コミット、ルートコミット、マージコミット、未コミット差分の比較元は`multi-agent-orchestration.md`に従って固定する。
2. 調整担当がコミットごとに1つの調査タスクを作る。複数コミットは2件以上を同じバッチで並列実行し、枠を超える場合だけ複数バッチへ分ける。コミットが1件でも調査はサブエージェントへ委譲する。サブエージェントを利用できない場合、複数コミットを並列実行できない場合、または独立した検証担当を確保できない場合は処理を停止する。
3. 各調査担当が、担当コミットと比較元を明示した読み取り専用Gitコマンドで調査する。調査担当は変更ファイル、メソッド、条件分岐、データ項目を特定し、変更箇所の呼び出し元を意味解析と別系統の検索で逆方向にたどる。次にControllerなどの入口から、必要な未変更処理、変更箇所、呼び出し先、同じ階層へ戻った後続処理、戻り値または副作用までを実行順にたどる。複数の呼び出し元は個別のフローとして残し、コード上の根拠がある懸念点、バグ、考慮漏れも抽出する。
4. 各調査担当が、自分のコミットだけを表すJSONを作る。すべてのステップへ重複しない`id`を設定し、各呼び出し箇所を`included`、`excluded`、`unresolved`のいずれかに分類する。`included`は入口、呼び出し元、専用の変更ステップへ関連付け、`excluded`はコードに基づく理由を記録する。`unresolved`を残したまま調査完了にしない。
5. 各調査担当が、コミット概要、処理フロー説明、概説、変更理由、処理仕様、備考へ`explanation-writing.md`先頭の原文プロンプトを省略、要約、言い換えせず適用する。`specification`は意味を示す`summary`、実行順に1項目1動作で分けた`steps`、抽象的な説明を使った場合だけ追加する`example`で作る。未変更ステップも処理フローに必要なら含め、`reason`は`変更なし`だけにする。
6. 各調査担当が、全階層の`filePath`、`startLine`、`endLine`、`beforeCode`、`afterCode`を親側または対象コミット側の実コードと照合する。名称変更は`git diff --name-status -M <親> <対象>`で対応付ける。不一致を修正した場合は全テーブルを先頭から再照合する。調査担当は、対象種別、対象Git参照、比較元、未コミット差分のスナップショット、コミットJSONを一体として正規化したSHA-256と、`review-data-schema.md`で定める調査証跡JSONを調整担当へ返す。
7. 調整担当がコミットごとに、調査担当とは別の検証エージェントを新規コンテキストで起動する。検証担当は調査担当の思考過程や想定する正解を受け取らず、`verification.md`に従って変更ハンク、呼び出し元、フロー、後続処理、コード位置、説明、備考をGitと実コードから再調査する。検証担当は調査JSONを直接編集しない。
8. 検証が失敗した場合、元の調査担当が問題一覧に基づいて修正する。修正後は前回とは異なる検証エージェントが新規コンテキストで再検証する。修正は1コミットにつき最大2回とし、問題が残る場合はHTMLを生成せず停止する。
9. 調整担当が検証済みコミットを指定順に統合し、`review-data-schema.md`の`orchestration`へ担当、バッチ、対象Git参照、比較元、状態、検証履歴、証跡ファイル、SHA-256を記録する。調整担当は検証済みコミット本文を編集しない。最終検証のハッシュと統合後の調査単位から再計算したハッシュが異なる場合は、そのコミットを再検証する。
10. 次のコマンドでオーケストレーション、JSON、呼び出し元網羅性、後続処理構造を検証し、HTMLを生成する。HTMLを直接組み立てず、過去に生成したHTMLや別テンプレートを流用しない。

```bash
bash <skill-root>/scripts/generate-report.sh <review-data.json> <review-report.html>
```

11. 検証処理が「未変更コードのステップがない」と通知した場合は、入口から終点までを再調査する。未変更ステップが本当に不要な場合だけ、その理由を最終回答へ記載する。
12. コマンド出力の`Orchestration self-test passed`、`Orchestration verification passed`、`Root section self-test passed`、`Specification structure self-test passed`、`Explanation input self-test passed`、`Code location structure passed`、`Caller coverage passed`、`Continuation structure passed`、`HTML verification passed`を確認する。いずれか1つでも表示されないHTMLを完成扱いにしない。
13. コマンドが出力する各`[後続処理確認]`について、検証担当の記録、実コード、展開したHTMLを照合する。呼び出し後の文がある場合は、同じ親階層の次テーブルが呼び出し元と同じファイル・同じメソッドの後続行を示し、線で接続されていることを確認する。呼び出し後の文がない場合は、直接`return`、メソッド末尾、`throw`、非同期境界など、後続テーブルを置かない根拠を実コードで確認する。
14. 出力したHTMLファイルを直接開き、コミットタブ、差分色、接続線、独立フロー、入れ子の開閉、文章の折り返しを確認する。生成後HTMLのコミット概要と全テーブルの説明を、同じ原文プロンプトへ再度照合する。確認のためにサーバーを起動しない。最終回答には、調査担当数、検証担当数、並列バッチ数、再検証回数に加え、`コード位置検証: N件、修正M件、未解決0件`と`後続処理検証: 呼び出しN件、後続ありM件、後続なしK件`を記載する。コード位置を修正した場合は対象ステップIDと修正後の位置を記載する。後続なしが1件以上ある場合は対象ステップIDと理由も記載する。

## 完了条件

- 各コミットを別の調査タスクが担当し、複数コミットでは2件以上の調査を同じバッチで並列実行している。
- 各コミットを調査担当とは別の検証タスクが新規コンテキストで再調査し、最後の検証が成功している。
- 対象コミット、`requestedCommitOrder`、実行記録のコミットが同じ順序で一致し、欠落と重複がない。
- 対象Git参照、比較元、調査結果、最終検証対象を含む調査単位のSHA-256が一致し、未解決問題が0件である。
- 調査、検証、再検証のいずれかが失敗または未完了の場合、部分的なHTMLを生成していない。
- 各コミットが独立したタブになっている。
- 各コミットの先頭に`概要`があり、変更全体の意味、必要な前提、因果関係を説明している。抽象的な説明がある場合だけ、その直後に具体例がある。
- 第1階層の各開始テーブルの直前にタイトルがある。複数テーブルまたは入れ子を含む処理フローには説明があり、単独テーブルには説明がない。
- 各処理フローがControllerなどの実際の入口から始まっている。HTTP処理でない場合は、Listener、Consumer、Job、Commandなど実際の入口を使い、その理由を備考へ書く。
- `analysisMode`が`callers`の各変更対象について、種類の異なる2つ以上の探索方法で呼び出し元を確認している。直接呼び出されない設定値などは、その根拠を`not-applicable`へ記録している。
- 探索で検出した呼び出し箇所がすべて`callerCoverage`へ登録され、掲載対象は入口、呼び出し元、変更ステップへ関連付けられている。
- 同じ変更対象を呼び出す箇所が複数ある場合は、呼び出し箇所ごとに専用の変更ステップを配置している。
- 除外した呼び出し箇所には具体的な理由があり、未解決の呼び出し候補が残っていない。
- 変更へ到達する経路と変更結果が戻る経路に必要な未変更ステップが含まれている。
- 未変更ステップでは`beforeCode`と`afterCode`が同一である。
- 未変更ステップでは`reason`が`変更なし`の5文字だけである。
- 未変更ステップの`overview`では変更有無を繰り返さず、処理の役割だけを説明している。
- すべての階層の全テーブルについて、表示するファイルパスと行範囲を対象コミットまたは親コミットの実コードと照合し、コード断片が一致している。
- `endLine - startLine + 1`が、表示位置の基準にするコード断片の行数と一致している。
- ファイル位置の不一致を修正した後に全テーブルを再照合し、未解決が0件になっている。
- 同じメソッド内の呼び出し前と戻り後を別ステップに分け、上段へ実行後の`return`を書かない。
- 呼び出し後の処理がある場合、次の接続テーブルが呼び出し元と同じファイル・同じメソッドの後続行を示している。呼び出し後の処理がない場合、その根拠を実コードで確認している。
- すべての説明へ`explanation-writing.md`先頭の原文プロンプトを省略、要約、言い換えせず適用し、JSON作成後とHTML生成後の2回照合している。
- 処理仕様が、先に示す処理の意味、2件以上の番号付き手順、抽象的な説明を使った場合の具体例に分かれている。
- 処理仕様の各番号が1つの入力、判定、状態変化、呼び出し、戻り値または外部結果だけを扱い、実コードの順序と因果関係を説明している。
- 処理仕様がコードの逐語訳ではなく、各手順で扱う値、その値を使う理由、直後に生じる結果を説明している。
- 備考が、コード上の根拠を確認できた懸念点、バグ、考慮漏れを分類して示している。不確かな推測をバグと断定していない。
- 納品物が外部ファイルやサーバーを必要としない単体HTMLになっている。
- サーバープロセスが起動しておらず、ポートを待ち受けていない。
- オーケストレーション検査、JSON検証、呼び出し元網羅性検査、呼び出し後の構造検査、10,000段の深度検査、HTML生成、生成後HTML検査が成功している。
- 生成後HTMLが`2026.09.13.3`のテンプレート要件を満たしている。

ユーザーが説明を「分からない」と指摘した場合は、既存文の言い換えだけで済ませない。入力、判定、中間値、呼び出し、戻り値を分割し、説明の粒度を1段階下げてJSONとHTMLを再生成する。
