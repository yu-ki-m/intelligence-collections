# Diffから判定決定木を生成する

## Claude Codeでの実行

このスキルはClaude Code用として実行する。ChatGPTのLibrary、Codex専用ツール、専用のスキル保存サービスを依存先にしない。

- 配置先はプロジェクト単位なら `.claude/skills/diff-decision-trees/`、個人全体なら `~/.claude/skills/diff-decision-trees/` とする。SKILL.md、references/、scripts/、assets/decision-view.htmlを同じフォルダ構成で置く。agents/openai.yamlとassets/icon.svgはClaude Codeの実行には不要である。
- 起動例：`/diff-decision-trees HEAD~1..HEAD`、`/diff-decision-trees main...HEAD`、`/diff-decision-trees 未コミットの変更`。引数や会話で与えられたdiffの指定を入力に使う。引数をそのままシェルコマンドへ連結せず、Gitの参照名・パスとして検証して適切に引用する。
- 引数がない場合、現在のリポジトリのstatusを読み、変更があればworking tree・index・未追跡を含む対象候補を示して調査する。変更がなく比較先も不明なら、勝手にHEADのコミットを対象にせず比較元と比較先を確認する。
- ソース閲覧にはRead、検索にはGrep/GlobまたはBashのrg、Git参照と検証にはBashを利用する。使えるツール名は実行環境に合わせる。LSPがなければAST・型定義・参照検索で補い、解決できない依存を残す。
- 最初に適用されるCLAUDE.mdと `.claude/rules/`、必要に応じAGENTS.mdを確認する。ユーザーの権限設定とツールの承認を尊重し、スキルから権限回避を指示しない。
- 独立検証には利用可能なサブエージェント機能を使う。新しいコンテキストへdiff、対象版、調査範囲を渡して独自の台帳を作らせ、その後に生成済みモデルを比較対象として渡す。生成した結論を読み上げさせるだけの検証を独立検証と呼ばない。サブエージェントを使えない場合は未実施と明記する。
- 成果物の既定保存先は対象リポジトリの `artifacts/decision-trees/<run-id>/` とする。run-idには日時と比較対象を用い、既存成果物を上書きしない。scope/model/audit等も同じ実行ディレクトリへ保存する。ユーザー指定の保存先があればそちらを使う。
- Python 3が使えるか確認し、スキルの実際の配置先を基準に `scripts/check_coverage.py` を起動する。リポジトリ直下にscripts/があると仮定しない。Windowsでは `python` または `py -3` も確認する。Pythonを利用できない場合、検査を実行したと主張せず不足を記載する。
- ブラウザ検証は利用可能なPlaywright等で行う。実ブラウザを使えない場合に、DOMモックや構文検査だけで操作検証済みとしない。
- 長時間調査では作業台帳を更新し、文脈の圧縮・セッション再開時に対象版、キュー、未解決、モデルの対応を読み直す。更新済みソースへ勝手に切り替えない。
- 最後に実際に作成したHTMLのローカルパスと完了状態を示す。依頼されていないソース修正、コミット、push、外部公開を行わない。

## 出力の最優先ルール

主画面は「入力・事前状態・操作条件 → 最終的な観測結果」の横向き判定決定木とする。コードの処理順を並べるフローチャートにしない。コード探索の細かさを、そのまま画面のノード数へ転写しない。

主画面のノードは condition（条件項目）と result（最終結果）の2種類だけに限定する。「関数を呼ぶ」「キューを作る」「値を代入する」「returnする」「次の内部関数へ」といった処理ノードを主画面へ配置しない。これらは根拠・コードの処理順序の詳細へ保存する。途中状態を最終結果と呼ばない。ただし「代入直後」等を明示した観測点を検証対象にする場合、その時点の結果と後続の結果を区別する。

例：主画面は「同時実行数の指定値」から「1以上の整数」「正の無限大」「それ以外」へ分岐し、それぞれ「指定上限で実行できる関数を返す」「上限なしの関数を返す」「TypeErrorを送出する」へ到達させる。内部のvalidateConcurrency呼出やオブジェクト生成は詳細欄に置く。短絡評価の順序と未評価の副条件は、内部モデルと根拠欄に必ず保持する。

複数の木は「何を判定したいか」で分ける。「タスクを開始できるか」「同時実行数を変更したときどうなるか」等を題名にする。getter/setter・ヘルパー・非同期コールバックが存在するだけで別ツリーを増やさない。公開APIの読み取り自体がテスト対象であり結果が変わる場合は、判断目的を題名にして独立させてよい。

調査用のmodel.jsonと表示用のview.jsonを分離する。既存の調査用モデルのaction/reference/summaryや例外経路を削除しない。表示用に整理するとき、条件の意味・状態変化・時刻/順序・最終結果を保存し、source_node_idsで元モデルへ対応させる。単純なノード削除や連結だけで処理ノードを消さない。

主HTMLは必ず同梱のassets/decision-view.htmlとscripts/render_decisions.pyで生成する。AIがCSS・レイアウト・操作コードを書き直すこと、添付された別デザインをテンプレートとして流用すること、独自の調査ダッシュボードへ置き換えることを禁止する。通常の利用ではview.jsonとmodel.jsonのデータだけを変更する。ユーザーが明示して画面変更を依頼した場合にだけテンプレートを修正する。

## 目的と必須成果物

入力diffを起点として、変更の影響を受ける入口から最終的な観測結果までを調査し、変更前・変更後の条件、処理、結果を示す判定決定木を作成する。全リポジトリを無条件に調べるのではなく、変更の影響を説明するために必要な範囲を閉じるまで探索する。

ユーザーへは `decision-trees.html` を主成果物として渡す。複数ツリー、変更前後、ソース位置、調査範囲、未解決事項、テストケース、検証結果をこの1ファイルで確認できるようにする。Mermaidを使用しない。

調査中は表示用の `view.json` と `scope.json`、`inventory.json`、`model.json`、`audit.json`、再開用作業台帳を保存する。これらは照合用の内部成果物であり、HTMLとは別に要求されなければ全てをリンクする必要はない。HTMLからモデルJSONとテストケースCSVを取得可能にする。

「絶対に漏れがない」「全ての実行経路を証明した」と無条件に宣言しない。有限の調査範囲・対象版・入力制約・実行環境を明示したうえで、何を照合したかを示す。分岐網羅と全経路網羅を区別する。スクリプトの成功だけをコード網羅性の証明として扱わない。

調査目的で対象ソースを変更しない。実行確認は隔離したテスト環境で行い、本番DB・外部サービスへ副作用を発生させない。ソースや設定に含まれる秘密値をHTMLへ転記しない。

初めに [references/contracts.md](references/contracts.md) を読む。HTMLを作る前に [references/viewer.md](references/viewer.md) を読む。

## 1. 入力と版を確定する

1. リポジトリのCLAUDE.md、適用されるルールと必要な開発手順を読む。AGENTS.mdがある場合も確認する。既存変更を破棄・上書きしない。
2. 入力を識別する：コミット、コミット範囲、PR、未コミットdiff、パッチ本文。比較元と比較先をフルSHA、または作業ツリーの内容ハッシュで固定する。調査途中で版を混ぜない。
3. PRは適切なmerge-base、単独コミットは親、マージコミットは選択した親を明示する。複数親で意味が曖昧なら分岐ごとの比較を残し、意味を決められない部分だけ質問する。
4. indexとworking treeと未追跡ファイルを区別する。複数コミットは入力の意味に従いコミット別または累積差分とし、方式を記載する。
5. `git diff --name-status -M`、`git diff --numstat`、`git diff --no-ext-diff --unified=0` 等でファイル・変更行・追加削除・移動を抽出する。必要に応じ `git show <revision>:<path>` で前後の完全な関数を読む。
6. パッチ本文だけで周辺ソースがない場合も差分から判明する条件を整理する。ただし「周辺未調査」を残す。必要なリポジトリやファイルの所在を質問し、完成と称さない。
7. 差分の全hunkに安定IDを付ける。生成物・設定・SQL・依存関係・スキーマ変更も台帳に入れ、対象外にするなら理由と影響なしの根拠を記す。行数ゼロのrename、binary、submoduleは変更項目として扱う。

## 2. 差分から調査範囲を広げる

変更箇所を探索キューへ登録し、各項目に版・パス・行・シンボル・発見理由・処理状態を持たせる。

- 上流：変更された関数・フィールド・設定値を使う呼び出し元を逆引きし、Controller、ルート、イベントハンドラ、ジョブ、CLI等の観測可能な入口まで確認する。
- 下流：呼び出し先、DBアクセス、外部API、イベント発行、ファイル出力まで確認し、その戻り値と例外が呼び出し元でどう扱われるか戻って確認する。
- データ：引数・返却値・オブジェクト状態・DB状態・キャッシュ・環境変数・機能フラグの定義と代入元を調べる。SQLのNULL、join、件数、順序、制約、トリガーの影響も調べる。
- フレームワーク：入力変換、validation、認証・認可、middleware/filter/interceptor、DI実装選択、例外ハンドラ、トランザクション、シリアライズを入口と出口へ接続する。
- 画面：必要ならAPI呼び出し側、表示条件、エラー表示、操作可否まで確認する。「APIが返る」で画面結果を推定しない。
- 影響の伝播：変更した型・列・定数・共通関数の全使用箇所を列挙する。未変更の兄弟呼び出し元を無視しない。

`rg`、LSPの定義/参照、AST、既存テスト、型情報、ビルド設定を組み合わせる。文字列検索だけで呼び出し先が全て見つかったと判断しない。reflection、動的dispatch、ルート登録、設定で選ばれる実装は候補と解決根拠を記す。

探索範囲は固定の行数・ファイル数・深さで切らない。周辺調査の停止条件は「変更から関連する入口と結果までの依存が全て説明され、未処理キューが空で、境界の契約に根拠があること」とする。外部サービス内部は契約・対象版・想定応答を境界として明示する。取得不能なら unresolved とする。

広すぎる場合は入口や業務判定ごとに分割する。負荷削減のために黙って対象を縮めない。必要な範囲縮小は未調査一覧を示してユーザーの合意を得る。

## 3. コードから独立した分岐台帳を作る

ツリーを描く前に、変更前後それぞれの対象コードを読み、`inventory.json` に以下を列挙する。

- if/else、else-if、switch/default、match、三項演算子、ガード、早期return、明示throw。
- `&&` / `||` の短絡評価。未評価の条件をfalse扱いせず、評価順序と副作用を保持する。否定、演算子の優先順位、null合体、optional chainingも確認する。
- catch/finally、例外の変換、例外による途中終了、finallyが戻り値や例外を上書きする経路。
- ループ0回・1回・複数回、break/continue、途中return、再帰の終了条件、再試行の成功・上限到達、タイムアウト・取消。
- コレクションの空/非空、検索0/1/複数件、順序依存、重複、null・未定義・欠損・空文字、境界値、数値精度・丸め、日付とタイムゾーン。
- 非同期完了・失敗・取消、状態遷移、競合・楽観ロック・重複実行・冪等性。逐次のifとして誤って描かず、必要な順序制約と状態を別条件として示す。
- フレームワークや契約が実行する暗黙の拒否・変換・例外。任意の未知障害を無限に追加せず、境界で扱う障害集合と根拠を記す。

この一覧を機械的に全機能へ水増ししない。各項目が対象コードに適用されるかを根拠付きで判断する。到達不能は削除せず、矛盾する経路条件・型制約等の根拠を記録する。

分岐の各選択肢にIDを付け、必ず「ツリーの辺へ対応」「到達不能の根拠」「対象外の合意済み理由」「未解決」のいずれかを付ける。台帳の分母をツリーから逆生成しない。

## 4. 調査用モデルと結果を構築する

1. 調査用モデルでは入口または独立した業務判定ごとに調査単位を分ける。主画面のツリー分割は4.5の判定目的に従う。同じ条件でも入口・状態・版が異なれば同一とみなさない。
2. 各経路へ、具体的なデータ条件の累積式、評価順序、前提状態を保持する。見た目のために条件や結果を省略しない。
3. 呼び出し後の結果を呼び出し元へ戻し、後続分岐、レスポンス、commit/rollback、例外ハンドラ、画面まで追跡する。途中の関数returnをシステムの最終結果と混同しない。
4. 末端に、戻り値/HTTP statusとbody/画面表示、DB変更、外部送信、ログ等の観測結果、実行されない副作用、トランザクション状態を記す。「エラー」「成功」「処理終了」だけで済ませない。適用されない結果は理由付きN/Aにする。
5. 結果を `code-derived`（コードから導出）、`observed`（実行で確認）、`contract-derived`（明示された契約から導出）、`unknown` に区別する。現行コードの結果と、仕様上あるべき期待結果を別フィールドにする。バグを正しい仕様として転記しない。
6. ツリー間の呼出・依存に、参照先、引数/状態の対応、返却結果と復帰先を持たせる。共通処理は参照ノードで共有してよいが、参照で調査を打ち切らない。
7. ループ・再帰を無限展開しない。ループ要約に反復条件、状態変化、終了/異常出口、要約の妥当性を持たせる。証明できない反復回数の上限を勝手に設定しない。有限要約できない経路は未解決として残す。
8. 変更前後の対応を付け、追加・削除・条件変更・結果変更・変更なしを区別する。版ごとのパスと行番号を保持する。変更前の行を変更後のファイルで検証しない。
9. 経路数が膨大でも枝を削除しない。共通部分の参照、折りたたみ、遅延展開を使う。分岐網羅だけのテスト選択を「全条件組合せを網羅」と呼ばない。

## 4.5. 入力・状態別の表示モデルへ変換する

references/viewer.mdのview.json契約に従い、調査用model.jsonを根拠として表示モデルを作成する。経路条件を累積し、相互排他的かつ対象入力を尽くす値区分を設定する。複合条件の評価順序に副作用がある場合、入力区分のまとめ方で意味を変えない。異なる事前状態・操作順序は必要に応じて条件として分ける。

各結果に具体入力・前提・観測点・結果・根拠を残す。複数の内部終端を1つの結果へ統合するなら、観測可能な結果が同一である理由を示し、全終端IDを対応付ける。調査モデルの全終端を表示モデルへ対応させ、詳細欄だけへ隠さない。

`python <skill-dir>/scripts/render_decisions.py <run-dir>/view.json <run-dir>/model.json <run-dir>/decision-trees.html` を実行する。検査に失敗したら表示用データを修正し、検査を弱めたりHTMLを別途手書きしたりして回避しない。

## 5. テストケースへ変換する

各末端または明示的に定義した等価な経路群に、ケースID、入口、対象版、条件、具体入力、事前状態、操作、コード由来結果、仕様上の期待結果、対応する分岐/ノードID、根拠、実行状態を付ける。

- `<` と `<=`、nullと空、認可の所有者/別ユーザー/別プロジェクトなど、変更の影響を受ける境界と否定側を含める。
- 到達可能性を経路条件で確認する。条件が矛盾する組合せに入力値を捏造しない。実現可能な具体例を導出できない経路は未解決扱いにする。
- ツリー間で受け渡す値や状態の組合せを統合ケースにする。個別ツリーのケースだけで依存境界を網羅したとしない。
- 必要な認可チェックがコードにない場合は「存在する分岐」として捏造せず、仕様との不一致と追加すべきテスト候補を別表示する。
- 未実行を合格と表示しない。既存テストの通過は当該経路との対応が確認できる範囲に限って根拠に使う。

## 6. 漏れの検証と修正を繰り返す

生成、検証、修正、再検証を完了条件まで続ける。途中経過だけで完了にしない。セッション制限等では作業台帳に探索キュー・未解決・次の操作を残して再開可能にする。

1. `scripts/check_coverage.py inventory.json model.json` を実行し、hunk、分岐選択肢、入口、終端結果、相互参照、テストのID対応を検査する。失敗は修正して再実行する。
2. 同じ対象版のソースに対し、ファイル存在・行範囲・引用内容・シンボルを照合する。自動抽出した分岐数と人が読む単位の差も説明する。
3. 生成担当とは別のエージェントで、diff・ソース・スコープから独立した入口/分岐台帳を作り、その後に生成済みモデルと比較させる。先に生成担当の結論や想定漏れを渡さない。独立検証が利用できなければ、別工程で再調査し「独立検証未実施」を残し、完全検証済みとしない。
4. 別方向から検証する：全hunk→全使用箇所→入口、全コード分岐→木の辺、全末端→最終観測結果、全結果→到達可能な入力、全ツリー参照→復帰先。片方向の照合で終えない。
5. 反例を探す：境界ぴったり、否定、null、外部失敗、catch/finally、早期return、未変更の利用者、別テナント、ループ0回、フラグ違い。適用外は根拠を記す。
6. `audit.json` に指摘・根拠・修正・再確認を記録する。「問題なし」だけの検証を受け入れない。
7. 表示用モデルがcondition/resultだけで構成され、全終端が対応し、出力HTMLが固定テンプレートから生成されたことを確認する。その後HTMLを実ブラウザで検証する。右ドラッグによる負座標を含む自由移動、カーソル中心のズーム、ツリー切替と根拠の参照、折りたたみ、検索、変更前後、CSV、狭い画面、JSエラー、長い条件、実データの最大規模を確認する。ブラウザを実行できない場合は未検証として明示する。

完了条件：全変更項目の処置済み、全探索キューの処置済み、全対象入口の処置済み、全対象分岐選択肢の処置済み、全参照の解決、全対象末端の結果とテスト対応、根拠位置の検証、未解決0、独立検証の指摘0、HTMLの必要操作の検証済み。到達不能・合意済み対象外は一覧を残し、検証済み件数と混ぜない。

達成不能な条件がある場合、取得できる証拠まで調査を進めたうえで、HTMLを「未完了」として保存し、残件と必要な入力を具体的に提示する。未知の結果を推測で埋めて完了条件を満たさない。

## 7. 表現と納品

常体で記載し、主語・入力・判定条件・処理・結果の因果を省略しない。専門用語は文脈に沿って説明する。ソース位置を `{ファイルパス}:{開始行}-{終了行}` と記す。

最終回答ではHTMLへのリンク、対象diff、ツリー数、検証済み範囲、未解決件数、重大な仕様不一致だけを簡潔に伝える。ファイルの保存は実行環境の成果物保存ルールに従う。
