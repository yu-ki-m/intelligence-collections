# リスク点数の付け方

## 点数の意味

点数は、**人がそのテーブルを見なかった場合に、問題を見逃したまま出荷するリスク**を0〜10の整数で表す。コードの良し悪しや複雑さではなく、「人の目がどれだけ必要か」を示す。

## 目安

| 点数 | HTML上の帯 | 目安 |
|---|---|---|
| 0 | 低 | 変更がなく、入口・戻り値など流れを理解するためだけに載せたテーブル。 |
| 1〜2 | 低 | 変更はないが、変更箇所へ値を渡す・処理を選ぶテーブル。または変更はあるが、表示・ログ・コメントなど業務の結果に影響しないもの。 |
| 3〜4 | 中 | 局所的な業務ロジックや運用設定の変更。誤っても影響が限定的で、テスト・画面・型で気付きやすい。 |
| 5〜6 | 5=中 / 6=高 | 分岐条件、状態遷移、入出力の形、複数の入口から使われる処理の変更。誤りが結果に出るが、テストがなければ気付きにくい。 |
| 7〜8 | 高 | 永続データの書き込み・更新・削除、金額・数量、認可・個人情報、外部システムへの送信、再実行や並行実行での重複。誤ると保存後まで気付きにくい。 |
| 9〜10 | 最優先 | 取り消せない損害(データ破壊、二重課金、権限昇格、情報漏えい)につながり得て、かつ気付きにくい。または備考で[バグ]と確認済みの重大なもの。 |

帯はHTML上の表示に使い、点数だけで決まる(0〜2 低 / 3〜5 中 / 6〜8 高 / 9〜10 最優先)。目安の行をまたぐ「5〜6」は、5が中、6が高になる。最終回答の帯ごとの件数もこの区切りで数える。

具体的な型と、全パターンの見本は [採点パターン集](scoring-patterns.md) を見る。

## 上げる要因・下げる要因

目安の範囲内で、次の要因により1〜2点動かす。

上げる:
- `callerCount`が2以上で、複数の入口から使われる。
- 例外にならず、誤った結果を返す(サイレントに壊れる)。
- 元に戻せない。
- 備考やコード上に、その変更を検証する手段(テスト、検証)が見当たらない。
- 備考に`[懸念点]`または`[考慮漏れ]`がある。

下げる:
- 型やコンパイラが誤りを防ぐ。
- 変更が1行で、意味が自明である。
- 変更を検証する既存のテストや確認が、備考などで示されている。

## 検証スクリプトが強制する規則

`scripts/validate-risk-scores.mjs`が次を検査し、違反があるとHTMLを生成しない。

- 備考に`[バグ]`がある → 7以上。`[懸念点]`または`[考慮漏れ]`がある → 5以上。
- 変更がなく、備考に指摘がない → 2以下。
- 変更がない → `category`は`文脈(変更なし)`。変更がある → `文脈(変更なし)`は使えない。
- 3以上 → `checkPoints`を1件以上。`checkPoints`は最大3件。
- `reason`は10文字以上。
- 全テーブルに1件ずつ採点する。

## category

主な観点を1つ選ぶ。

| category | 使う場面 |
|---|---|
| データ保存・更新 | DBやファイルへの書き込み・更新・削除、状態の永続化 |
| 認可・個人情報 | 権限判定、認証、個人情報の扱い |
| 金額・数量の計算 | 金額、数量、割合、丸め、税 |
| 外部連携・イベント | 外部API、メッセージ、イベントの送受信 |
| 並行・再実行 | 重複実行、排他、冪等性、リトライ |
| 失敗時の処理 | 例外、ロールバック、エラー応答 |
| 業務ルール・分岐 | 条件分岐、状態遷移、業務上の判定 |
| 入出力の互換性 | API・DTO・スキーマなど、他から見える形 |
| 設定・運用 | 設定ファイル、ログレベル、環境変数、ビルド設定 |
| 表示・整形 | 画面表示、ログ文言、フォーマット |
| 文脈(変更なし) | 変更のないテーブル |

## reason の書き方

「人が見なかったら何が起きるか」を1〜2文で書く。コードの動作の説明を繰り返さない。

- 良い例: `INSERT文に渡す値が増える。SQLの列やプレースホルダーと引数が合わないと登録が例外で失敗し、状態が誤って保存されても画面では気付きにくい。`
- 悪い例: `重要な変更である。`(何が起きるかがない)
- 悪い例: `INSERT文にstatusを追加している。`(コードの説明で、リスクが分からない)

## checkPoints の書き方

人が「この点を確認したので、チェックしてよい」と判断できる、具体的な確認事項を最大3件書く。名詞ではなく、確認する内容を疑問または動作で書く。

- 良い例: `INSERT_SQLがstatus列とプレースホルダーを持つか`
- 良い例: `statusがnullの注文を保存できるか`
- 悪い例: `動作を確認する`(何を見ればよいか分からない)

コードに書かれていない事実を確認済みのように書かない。確認できていないことは「〜か」の形で人に任せる。

## 採点後の見直し

- 変更のあるテーブルが全て同じ点数になっていたら、相対的な差を再検討する。ただし、実際に同程度のリスクなら、無理に散らさない。
- 変更のないテーブルが大半なら、0〜2が多いのは正常である。
- 最も高い3件を読み直し、`reason`が「人が見なかったら何が起きるか」になっているか確認する。
